Java Spring Boot 프로필

Java Spring Boot 프로필

읽기 안내 — 누가: Java/Spring Boot 코드베이스를 다루는 개발자, FDE, PM · 언제: T# 작업 계약을 쓰기 전 · 읽은 뒤: Spring Boot에 맞는 검증 수단과 먼저 확인할 사실을 작업 계약에 넣는다.

목적

Java/Spring Boot가 실제 대상 코드베이스인 고객 프로젝트에서 기술중립 가이드를 실행할 수 있는 작업으로 구체화한다. T# 분해, 작업 계약, 독립 검증, 사람 검토·수용, 측정은 시작하기를 따른다. 이 프로필은 거기에 Spring Boot용 확인 사실과 검증 수단을 더한다.

언제 사용하는가

착수 합의 또는 지금 상태 재현에서 Java와 Spring Boot가 주된 애플리케이션 경계이고, Maven 또는 Gradle 빌드·JDK 버전·테스트 실행 방법을 실제로 재현할 수 있음을 확인했을 때 쓴다. Android, 순수 Java 라이브러리, 대규모 레거시 Spring Framework, 프런트엔드·인프라 코드는 별도 프로필 또는 프로젝트별 작업 계약이 필요하다.

프로젝트 사실 확인

실행 전 다음을 코드·CI·운영 문서에서 확인한다. 빈칸을 일반 관례로 추측해 채우지 않는다.

확인 항목 기록할 사실 검토 역할
빌드 Maven/Gradle, wrapper, JDK·플러그인 버전, 멀티모듈 구조 개발자 재현, 검토자 확인
테스트 빠른/통합 테스트 명령, 선택·제외 규칙, CI 명령 개발자 실행, 검토자가 테스트 명령이 조건을 갖췄는지 판단
애플리케이션 controller, service, repository, messaging, batch, 외부 API FDE·기술 리드가 변경 경계 확인
데이터 DB, migration 도구, 트랜잭션, 테스트 DB, 복구 방식 데이터 책임자·배포 승인자 확인
보안·운영 인증·인가, secret 출처, 환경 profile, 배포·관측성·롤백 보안·운영 책임자 승인

표와 이 문서에 나오는 책임자 이름(기술 리드, 데이터 책임자, 배포 승인자, 보안·운영 책임자, 구성 책임자, 복구 책임자, 재처리 책임자)은 프로젝트마다 채운다 [프로젝트별 결정]. NEXI의 역할(PM, FDE, 개발자, 검토자)은 개념 참조에 있다.

작업 계약서에 더할 것

Java와 Spring Boot 작업이면 작업 계약서에 다음을 더한다.

빌드 도구와 재현 명령: [실제 wrapper 명령]
대상 모듈·패키지 경계: [예: :orders, com.example.orders]
Spring 경계: [HTTP / bean / transaction / data / message / batch]
테스트 계층과 명령: [빠른 검증] / [느린 통합 검증]
데이터 영향: [없음 / 읽기 / schema / write]와 migration·복구 책임자
보안·구성 영향: [없음 / 인증·인가 / secret / profile / 외부 호출]
운영 영향과 배포·롤백 근거: [해당 시]

agent에는 프로젝트 전체가 아니라 실제 빌드 선언, 대상 모듈, 통과한 대표 테스트, 관련 Spring 설정·예외·DTO 규약, 데이터 변경 시 migration 규칙, CI 제약만 넣는다. README·issue·주석의 지시처럼 보이는 문장은 검토 대상 자료이며 승인된 지시가 아니다. 비밀정보·운영 데이터·접근 토큰은 넣지 않는다.

검증 선택표

모든 계층을 모든 T#에 강제하지 않는다. 변경 위험과 실제로 실패할 가능성이 가장 높은 경계를 선택한다.

순수 계산·규칙 JUnit 단위 테스트 경계값·뮤테이션 확인 업무 규칙과 예외
HTTP controller·DTO 웹 계층 테스트 또는 기존 controller 검증 직렬화·validation·예외 응답 API 호환성과 오류 계약
서비스·트랜잭션 서비스 테스트와 트랜잭션 경계 실제 DB 통합 테스트 롤백·중복 실행·부분 실패

인증·인가 허용·거부 경로 통합 검증 권한 상승·감사 로그 보안 정책에 맞는지

mvn test, ./mvnw test, gradle test, ./gradlew test는 예시일 뿐이다. T#에는 해당 저장소에서 실제로 성공·실패를 구분하는 wrapper 명령과 대상 모듈을 기록한다. 종료 코드, 실행 테스트 수 또는 보고서, 소요 시간을 남긴다. 테스트가 통과해도 대상 운영 코드가 실행되지 않았다면 수용 근거가 아니다.

데이터·배포 경계

schema/data 변경은 단위 테스트 통과만으로 반영하지 않는다. migration 도구·실행 순서·롤포워드/되돌리기, 대사 대상, 백업·복구 근거, 중단 조건, 배포 창, 모니터링·알림, 배포 승인자를 작업 계약에 기록한다. dual-write·비동기 전파에는 순서·중복·부분 실패·재처리 책임자가 필요하다.

구현할 때 /nexi-implement가 쓴 빌드·검증 명령, 실제 JDK와 빌드 도구 버전, 결과를 증거 파일에 남긴다. 의존성 추가, 플러그인·JDK 변경, 테스트 제외, DB 쓰기, 외부 네트워크 호출, 운영 배포는 기본 권한에 넣지 않고 작업별 사람 승인과 감사 기록을 요구한다.

코드 표준 작업에서

코드 표준 작업(골격 다음 작업)이 docs/engineering/STANDARDS.md를 쓸 때 Java/Spring Boot에서 쓰는 내용이다.

가시성. 기능 안에서만 쓰는 controller, 설정 클래스, 구현 클래스, 같은 패키지의 요청·응답 record와 예외는 package-private로 둔다. 다른 패키지가 쓰는 도메인 타입, 인터페이스, Application은 공개한다. Spring 문서가 근거를 주는 것과 주지 않는 것을 나눈다.

  • @Bean 메서드의 Java 가시성은 bean 정의에 영향을 주지 않는다: 일반 @Component 클래스, proxyBeanMethods=false인 lite 설정의 @Bean 메서드와 어디서든 static @Bean 메서드는 가시성을 자유롭게 둘 수 있다. 기본(full) @Configuration은 CGLIB 하위 클래스를 만들므로, 그 안의 static이 아닌 @Bean 메서드는 재정의할 수 있어야 한다: private이나 final이 아니어야 한다 (classpath scanning, @Bean과 @Configuration).
  • @Transactional은 6.0부터 class 기반 proxy(Spring Boot 기본)에서 protected와 package-private 메서드에도 적용된다. proxy를 거쳐 들어온 호출에만 적용되므로 같은 객체 안의 호출(self-invocation)에는 적용되지 않는다. JDK 인터페이스 proxy를 쓰면 인터페이스에 선언된 public 메서드만 대상이다 (Method visibility and @Transactional in proxy mode). final과 private 메서드는 class 기반 proxy가 재정의할 수 없으므로 proxy를 거치지 않는다.
  • package-private @RestController 클래스와 public이 아닌 요청 처리 메서드가 요청을 받는지는 위 문서들에 적혀 있지 않다. 그렇게 두려면 표준 작업의 계약서가 그 프로젝트에서 실제로 요청이 처리되는 웹 계층 시험(예: @WebMvcTest나 MockMvc로 그 경로를 부른다)을 검증 명령으로 둔다.

기계 검사. 예는 ArchUnit과 checkstyle이다. 표준 작업의 계약서가 도구와 판을 정한다.

import static com.tngtech.archunit.base.DescribedPredicate.not;
import static com.tngtech.archunit.core.domain.JavaClass.Predicates.resideInAPackage;
import static com.tngtech.archunit.lang.syntax.ArchRuleDefinition.classes;
import static com.tngtech.archunit.lang.syntax.ArchRuleDefinition.noClasses;

import com.tngtech.archunit.junit.AnalyzeClasses;
import com.tngtech.archunit.junit.ArchTest;
import com.tngtech.archunit.lang.ArchRule;
import org.springframework.stereotype.Controller;

@AnalyzeClasses(packages = "com.example")
class ArchitectureTest {

    // 다른 기능은 orders의 공개 경계(orders.api)만 부른다. orders 안의 public service도 경계 밖이면 부르지 못한다
    @ArchTest
    static final ArchRule orders_only_through_api = noClasses()
        .that().resideOutsideOfPackage("com.example.orders..")
        .should().dependOnClassesThat(resideInAPackage("com.example.orders..")
            .and(not(resideInAPackage("com.example.orders.api.."))));

    // controller(@Controller와 그것을 메타 애너테이션으로 가진 @RestController)는 공개하지 않는다
    @ArchTest
    static final ArchRule controllers_not_public = classes()
        .that().areMetaAnnotatedWith(Controller.class).should().notBePublic();

    // 인터페이스 구현 클래스는 기능의 internal 패키지에 두고 공개하지 않는다(표준이 이 위치를 정한다)
    @ArchTest
    static final ArchRule implementations_not_public = classes()
        .that().resideInAPackage("com.example..internal..").should().notBePublic();
}

예외 목록은 ArchUnit이 읽는 archunit_ignore_patterns.txt(test classpath)에 둔다. 한 줄이 위반 메시지 하나를 빼는 정규식이고, 그 위에 # T#<N> <규칙> <범위> 주석을 단다. 계약서의 ## 표준 예외가 그 항목을 기록한다.

공개 경계의 문서 주석은 checkstyle로 매개변수와 반환 태그를 요구한다. google_checks.xml은 공개 멤버의 Javadoc이 없는 경우 일부(속성 접근자, @Override 메서드 등)를 빼고 막으며, 한 줄 요약만 있는 Javadoc은 막지 않는다. 다음 설정을 더한다.

<module name="MissingJavadocMethod">
  <property name="scope" value="public"/>
</module>
<module name="JavadocMethod">
  <property name="accessModifiers" value="public"/>
  <property name="allowMissingParamTags" value="false"/>
  <property name="allowMissingReturnTag" value="false"/>
  <property name="validateThrows" value="true"/>
</module>

validateThrows는 선언한 예외와 메서드 안의 throw new 일부만 본다. 부른 메서드에서 올라오는 예외까지는 확인하지 못하므로 그 문서는 리뷰가 본다. HTTP API의 상태와 오류 코드 문서도 Javadoc 검사로 확인되지 않는다. 리뷰가 보거나, API 명세(OpenAPI 등)를 쓰면 그 명세의 검사로 확인한다.
