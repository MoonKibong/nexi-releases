온톨로지 참조 아키텍처

읽기 안내 — 누가: 온톨로지를 쓸지 따져 보는 PM, FDE, 개발자 · 언제: 착수 합의에서 온톨로지를 쓸지 정할 때 · 읽은 뒤: 이 구조를 쓸지 판단하고, 쓴다면 무엇을 먼저 정해야 하는지 안다.

온톨로지 참조 아키텍처는 전달 약속이 아니다. 적용 조건이 충족될 때에만 이 구조를 사용하며, 쓸지는 착수 합의에서 정해 기록한다. 조건은 병렬 팀이 4개 이상이거나, 같은 업무 대상을 여러 시스템이 서로 다른 키로 보유하거나, agent가 원시 테이블명 때문에 같은 종류의 오류를 반복하는 경우다.

적용 조건을 갖추기 전에는 이 구조를 쓰지 않는다. 프로젝트 아키텍처는 범위를 합의한 뒤 ../architecture/에 작성한다. 적용 여부를 정하기 전에는 이 구조를 미리 구현하거나 약속하지 않는다.

채택하면 지킬 설계 원칙

어떤 기술로 구현할지는 다음 절 "실제 채택 시 결정할 사항"에서 정한다.

데이터를 옮기기 전에 late binding부터 한다. 온톨로지는 레거시 시스템을 현재 모습 그대로 연결한다. 레거시 정리나 대량 데이터 이동을 이 계층을 만들기 전에 먼저 갖출 조건으로 삼지 않는다.

action이 전달물이다. 읽기 전용 모델은 보기 좋은 ERD일 뿐 고객 프로젝트를 정당화하지 못한다. 각 object에는 적어도 하나의 action이 있거나, action이 없는 읽기 전용 참조 데이터임을 명시해야 한다.

write-back은 action마다 명시한다. write-back은 action이 바꾼 내용을 레거시 시스템에 다시 써서 반영하는 일이다. action마다 쓰기 대상인 모든 레거시 시스템, 쓰기 순서, 부분 실패 시 보상 동작을 적는다. 여러 시스템을 묶는 분산 트랜잭션이 없다는 문제를 전역 설정으로 감추지 않는다.

sequenceDiagram
    actor U as 이해관계자 또는 agent
    participant O as Ontology 계층
    participant B as 바인딩 맵
    participant L1 as 레거시 시스템 A
    participant L2 as 레거시 시스템 B

    U->>O: action 호출
    O->>O: 먼저 갖출 조건과 object 접근 정책 확인
    O->>B: 바인딩된 attribute 확인
    B-->>O: 레거시 키와 column 반환
    O->>L1: 쓰기 1
    L1-->>O: 확인
    O->>L2: 쓰기 2
    alt 쓰기 2 실패
        O->>L1: 보상 쓰기
        L1-->>O: 확인
        O-->>U: action 거절, object 상태 변경 없음
    else 모든 쓰기 확인
        O->>O: object 상태 변경 확정
        O-->>U: action 완료
    end

여러 시스템을 가로지르는 분산 트랜잭션은 없으므로 alt 분기는 action별로 설계한다. 보상 쓰기가 아직 없는 action은 배포하지 않는다.

정책은 object에 둔다. access policy를 object 수준에 한 번만 정의하고 애플리케이션, dashboard, agent가 함께 상속한다. 소비자마다 정책을 다시 구현하지 않는다.

agent는 원시 테이블이 아니라 온톨로지를 사용한다. 의미 계층이 agent의 인터페이스다. 따라서 온톨로지 투자 효과는 문서 분량으로 측정하지 않는다. agent의 오류율·재작업·검증 통과율로 측정한다.

옮기는 일은 object 단위로 한다. 한 increment에서 한 object의 system of record만 옮기고, 대사(reconciliation) 확인과 되돌리기 연습을 마친다. 시스템 전체를 한 번에 옮기지 않는다.
