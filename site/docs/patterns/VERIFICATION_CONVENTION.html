검증 명령 규약

검증 명령 규약

읽기 안내 — 누가: 작업 계약서를 쓰는 FDE, 승인하는 PM, 구현하는 개발자, 리뷰를 확인하는 검토자 · 언제: 작업 계약서의 검증 명령을 정하거나 승인하기 전 · 읽은 뒤: 명령이 요건을 갖췄는지 7절 체크리스트로 확인하고, 약한 부분을 고친다.

작업 하나(T#)에는 검증 명령이 하나 이상 붙는다. 작업 계약서의 ## 검증 명령에 적는 이 명령이 그 작업이 끝났는지를 판단하는 근거다. 명령이 약하면 agent가 만든 결과를 판단할 수단이 없다.

FDE가 /nexi-contract로 작업 계약서를 쓸 때 검증 명령도 함께 정하고, PM이 승인한다. 구현할 때 /nexi-implement가 새 검사마다 실패(red)와 통과(green)를 docs/evidence/T<N>.md에 남긴다. 이미 있던 동작을 지키는 검사는 regression, 이 작업이 더하는 동작의 검사는 new로 적힌다. 리뷰는 수용 기준과 검사 결과가 실제로 이어지는지 본다.

1. 검증 명령이 갖출 요건

다섯 가지를 모두 갖춰야 작업 계약에 넣을 수 있다.

# 요건 왜
1 종료코드로 판단한다 사람이 로그를 읽어 판단하면 자동화가 끊기고 라운드마다 사람이 병목이 된다
2 변경 전 탐지력을 확인한다 새 기능·결함 수정은 의도한 이유의 red를 확인한다. 기존 동작을 지키는 작업(마이그레이션·리팩터링)은 비교 기준이 되는 통과 결과를 남기고 뮤테이션 확인(3절)을 반드시 한다
3 빠른 피드백 시간이 합의돼 있다 빠른 작업별 검사와 긴 전체 회귀 검사를 나누고, 각각 언제 실행할지 작업 계약에 적는다. 빠른 검사의 기본 상한은 10분이다
4 대상 코드를 실제로 실행하거나 검사한다 테스트가 자기 사본을 검증하면 산출물은 검증되지 않는다 (4절)
5 결정론적이다 시간·네트워크·순서에 의존하면 실패가 신호가 아니라 잡음이 된다

7절 체크리스트로 작업 계약서를 승인하기 전과 구현한 뒤에 요건을 확인한다. 1번은 6절의 종료코드 금지 패턴에 걸리지 않는지 본다. 2번은 2절(red 확인)과 3절(뮤테이션 확인), 4번은 4-A절의 방법으로 확인한다.

수용 기준과 경계 조건

수용 기준마다 단언이나 점검 근거를 하나 이상 잇는다. 정상 경로가 통과했다는 것은 모든 수용 기준을 충족했다는 뜻이 아니다. 경계 조건은 위험에 맞게 고른다. 조인과 건수, null과 빈 값, 날짜와 시간대, 반올림, 권한, 페이지 나눔, 중복 전달이 흔한 경계다.

기능 검사가 통과해도 성능, 보안, 접근성, 관측성, 복구 가능성은 따로다. 작업마다 무거운 시험을 붙이지 않고, 품질 요구와 배포 위험에 맞춰 성능 예산, 보안 스캔, 접근성 점검, 로그·메트릭·알림, 복구 시험을 배포 계획에 넣는다. 담당자와 임계값을 정한다.

2. red 확인 — "실패했다"가 아니라 "맞는 이유로 실패했다"

새 기능·결함 수정에서 red를 볼 때 실패 메시지를 읽는다. 의도한 부재 때문에 실패해야 한다. 기존 동작을 보존하는 작업에서는 변경 전 통과 결과를 남기고, 별도 작업 공간에서 의도적으로 오류를 넣는다(3절).

red의 이유 판단
검증 대상이 없거나 값이 틀리다 조건을 갖췄다 — 이 명령은 그것을 본다
import 오류, 설정 오류, 목 실패 조건을 갖추지 못했다 — 배선이 안 됐다. 고치고 다시 red를 본다
파일 없음, 명령 없음 조건을 갖추지 못했다 — 환경 문제다

참조 예시 작업 (CRM 참고 예시, 2026-09-29). 이 작업은 리드 목록 조회 결과에 담당 팀 이름(teamName)을 더한 작업이다. red를 확인했을 때 실패 이유는 expected { id: 1, … } to have property "teamName" 였다. 즉 teamName 부재 때문이다. 만약 vi.mock 배선이 잘못돼 import 오류로 실패했다면 그 red는 무의미했다. 실패 메시지를 읽지 않으면 이 둘을 구별할 수 없다.

3. 강도 시험 — 뮤테이션 확인

red만으로는 부족하다. 산출물에 일부러 오류를 넣고 명령이 탐지하는지 본다. 비용이 적게 들고, 한 번만 해도 약한 검증을 드러낼 수 있다. 기존 동작을 지키는 작업(마이그레이션·리팩터링)에서는 필수다. 그 밖의 작업에서는 권장한다.

절차: 통과 상태에서 시작해 → 별도 작업 공간에 인접한 오류를 넣고 → 명령을 실행하고 → 이번 오류를 탐지했는지 기록하고 → 원상 복구하고 → 차이가 남지 않았는지 확인한 뒤 같은 명령을 다시 통과시킨다. 한 번의 뮤테이션은 그 오류 하나의 탐지력만 보여 준다.

참조 예시 작업의 뮤테이션 확인. leftJoin(salesTeams) → innerJoin으로 바꿨다.

종료코드=1
PASS (1) FAIL (1)
AssertionError: expected [ { id: 1, … } ] to have a length of 2 but got 1

잡았다. 팀 미배정 리드가 결과에서 빠진 것을 길이 단언이 잡아냈다.

그런데 2개 중 1개만 실패했다. 팀이 배정된 리드를 보는 첫 테스트는 innerJoin에서도 통과한다. 경계 사례 테스트가 없었다면 이 버그는 검증을 통과했을 것이다.

4. 검증이 산출물을 비껴가는 두 가지 방식

4-A. 자기 사본을 검증한다

테스트가 대상 코드를 호출하지 않고 같은 로직을 다시 구현해 검증하는 경우다. 통과해도 산출물은 검증되지 않는다.

실증 — CRM 참고 예시 저장소의 기존 테스트. src/__tests__/queries.test.ts는 인메모리 DB에 스키마를 만들고 drizzle 쿼리를 직접 재현해 단언한다. 서버 액션(@/actions/queries/*)을 import하지 않는다. 따라서 getLeads()를 바꿔도 이 테스트는 아무것도 말해주지 않는다.

참조 예시 작업은 그래서 vi.mock("@/db")로 인메모리 DB를 주입하고 getLeads()를 실제로 호출하는 새 패턴을 도입해야 했다. "테스트가 있다"가 "검증 수단이 있다"는 뜻이 아니다.

4-B. 대표 사례만 본다

정상 경로만 검증하면 경계에서 깨지는 변경을 통과시킨다. 3절이 그 실례다.

수용 기준마다 최소 한 개의 단언을 붙인다. 참조 예시 작업의 수용 기준 3번(팀 미배정 리드가 누락되지 않는다)이 innerJoin을 잡은 유일한 단언이었다.

5. 검증 수단이 없을 때 — 계층 선택

기존 검증 수단이 없으면 **만드는 것이 첫 T#**다. 어느 계층에서 만들지는 비용과 강도를 따져 선택한다.

계층 비용 강도 쓸 때
타입·컴파일 (build, tsc) 최저 낮음 — 형태만 항상 병행. 단독으로는 부족
린트·포맷 최저 낮음 — 규약만 항상 병행
단위 (순수 함수) 낮음 중간 로직이 순수하게 분리될 때
통합 (DB·의존성 주입) 중간 높음 대부분의 레거시 작업. 참조 예시 작업이 여기
계약·스키마 대조 중간 높음 마이그레이션 전후 동등성
E2E·브라우저 높음 높음 실제 사용자 흐름이 위험의 중심일 때

판단 기준: 변경이 가장 깨지기 쉬운 경계를 실제로 실행하는 계층을 고른다. 모든 계층을 모든 T#에 붙이지 않는다. 계산은 단위, DB·연동은 통합, 사용자 화면 흐름은 브라우저 검증을 우선 검토한다. 검사를 빨리 끝내려고 필요한 검증을 빼지 않는다. 전체 회귀 검사가 길면 실행 시점을 나눠 작업 계약에 적는다. 변경 유형별 예는 JAVA_SPRING_BOOT_PROFILE.md의 검증 선택표에 있다.

2주를 넘길 전망이면 범위를 교체한다. 대상 코드베이스에 테스트·CI가 없어 검증 수단을 만드는 데 일정이 잠식되는 위험을 막는 규칙이다. 검증할 수 있는 영역으로 범위를 바꾸는 것은 PM이 고객과 합의해 정한다 (범위를 바꾸는 수용 기준에는 고객이 동의한다). 검증 도구를 만드는 데 프로젝트 기간을 다 쓰면 개발 목표도 판단할 근거도 남지 않는다.

6. 금지 패턴

금지 왜
agent가 스스로 한 보고를 판단 근거로 쓴다 참조 예시 작업에서 agent는 스스로 검증했다고 보고했다. 구현하지 않은 agent가 다시 확인하는 리뷰가 있는 이유다
문자열 일부만 찾아 성공으로 판단한다 검증기는 대상·기대값·누락·실행 오류를 구분해야 한다. 실패하면 비정상 종료코드를 반환해야 한다
스냅샷을 검토 없이 갱신한다 틀린 출력을 기준으로 고정해 버린다
파이프라인 종료코드를 명령 종료코드로 쓴다 cmd | tail 의 $?는 tail의 것이다 (실제로 발생한 오류)
종료코드 0을 실행 증거로 쓴다 실행되지 않은 명령도 0을 낸다. 실행 건수와 소요 시간이 그럴듯한지 한 번은 본다
--force·--no-verify로 통과시킨다 게이트를 끄는 것이다

실패 신호

신호 대응
검사가 대상 모듈을 import하거나 호출하지 않는다 통합 접점이나 주입 지점을 만든다
종료코드 0인데 실행 건수나 시간이 이상하다 명령을 부른 방식과 리포트의 건수를 확인한다
불안정한(flaky) 검사 시간, 환경, 네트워크 의존을 떼어 내고, 안정되기 전에는 관문으로 쓰지 않는다
전체 검사가 너무 느리다 대상을 좁힌 빠른 관문과 따로 도는 회귀 관문을 두고 위험을 적는다
이전 시스템과의 동등성 검사가 실패한다 회귀로 단정하지 않는다. 기존 결함을 따라 할지 고칠지는 고객이 정한다

7. 작업 계약 작성 체크리스트

작업 계약서를 승인하기 전에 계획을 본다. 새 검사는 아직 만들어지지 않았다.

  • 명령마다 종료코드로 판단한다
  • 새 검사마다 구현 전에 어떤 확인 조건 때문에 실패해야 하는지 적혀 있다
  • 보존 작업(마이그레이션·리팩터링)은 비교 기준이 될 통과 결과를 남기고 뮤테이션 확인을 하도록 적혀 있다
  • 빠른 검사와 전체 회귀 검사의 실행 시점이 작업 계약서에 있다
  • 검사가 대상 코드를 실제로 호출하거나 검사한다(자기 사본이 아니다)
  • 수용 기준마다 확인 조건이 하나 이상 있다 — 특히 경계 사례
  • 기존 린트·빌드를 함께 돌리는 명령으로 넣었다
  • 결과가 매번 같게 나온다

구현한 뒤, 리뷰를 맡기기 전에 증거 파일 docs/evidence/T<N>.md에서 실행 결과를 본다.

  • 새 검사의 red가 적어 둔 확인 조건 때문에 실패했다(모듈 없음, 설정 오류가 아니다)
  • 보존 작업은 비교 기준이 된 통과 결과와 뮤테이션 확인 결과가 있다(그 밖의 작업은 권장)
  • 마지막으로 고친 뒤 모든 검사가 통과했다(green)

명령은 작업 계약서의 ## 검증 명령에 새 검사마다 하나씩 적는다. /nexi-implement가 명령마다 종료코드를 증거 파일에 남긴다.
