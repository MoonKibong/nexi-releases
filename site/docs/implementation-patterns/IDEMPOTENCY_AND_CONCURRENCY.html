멱등성과 동시성

멱등성과 동시성

읽기 안내 — 누가: 작업 계약을 쓰는 개발자, FDE · 언제: T#에서 이 문제를 풀 방법을 정할 때 · 읽은 뒤: 적용 전 결정을 고객·기술 책임자와 정하고, 반드시 지킬 조건을 수용 기준과 테스트에 넣는다.

해결하는 문제

사용자가 다시 시도하거나, 네트워크에서 응답이 사라지거나, 같은 요청이 여러 서버에서 동시에 처리되면 같은 업무 효과가 두 번 생길 수 있다. 이것을 막는다.

적용 전 결정

결정 정할 내용
적용 대상 어떤 행동에 멱등 처리가 필요한지
key 범위 key가 어느 tenant·사용자·업무 범위에 속하는지
보장 기간 중복 억제를 보장하는 기간(key 유효기간, TTL)과, 그 기간이 지난 뒤 같은 key가 오면 어떻게 처리할지
fingerprint 작업·대상·업무상 유효한 입력을 어떤 정규화 규칙으로 fingerprint에 담을지
원자성 경계 key·fingerprint·업무 변경·완료 결과를 함께 확정할 범위와 외부 효과의 경계
응답 규칙 같은 key로 다른 요청이 오면, 진행 중이거나 실패한 뒤 재시도가 오면 무엇을 응답할지
결과 불명과 인계 진행 중·완료·실패·결과 불명 기록을 누가 어떻게 확인하고 복구할지. 실행권(한 요청을 지금 처리하도록 한 작업자에게만 준 권한)의 만료 시간과 다른 작업자에게 넘기는 방법
외부 효과 트랜잭션과 변경 복구의 "외부 전달" 결정을 따른다. 수신 측 멱등 처리를 고르면 같은 key를 넘긴다
서로 다른 key의 경합 같은 업무 객체를 서로 다른 key로 바꿀 때 쓸 통제(version 비교, 잠금, 업무 유일성 제약 등), 충돌 오류와 재시도 조건

반드시 지킬 조건

  • 버튼을 비활성화하거나 프로세스 메모리 lock을 거는 것만으로 중복 실행을 막았다고 보지 않는다.
  • key와 요청 fingerprint를 함께 저장한다. fingerprint는 작업·대상·업무상 유효한 입력을 정한 정규화 규칙으로 나타낸다.
  • 같은 key로 뜻이 다른 요청이 오면 저장된 결과를 돌려주기 전에 거부한다.
  • 정한 보장 기간 안에는 같은 key의 업무 효과를 한 번만 만든다. 인스턴스가 여러 개여도 통하는 DB unique constraint나 공유 저장소의 원자적 연산을 쓴다. 다만 그것만으로 장애 뒤의 중복 효과를 막았다고 보지 않는다.
  • 같은 원자성 경계 안의 작업은 key·fingerprint·업무 변경·완료 결과를 함께 확정한다. 별도 예약 상태가 있으면 예약만 보고 업무가 끝났다고 판단하지 않는다.
  • 외부 효과의 전달 방식과 검증은 트랜잭션과 변경 복구에서 다룬다. 수신 측 멱등 처리를 고르면 같은 key를 넘긴다. 성공했는지 모르면 새 효과를 무조건 다시 실행하지 않는다.
  • 보장 기간이 지난 뒤 같은 key가 오면 정한 방식대로 처리한다. 진행 중이거나 결과를 모르는 기록은 보장 기간이 지났다는 이유만으로 지우거나 새 요청으로 실행하지 않는다.
  • 실행권을 다른 작업자에게 넘기면, 이전 작업자가 뒤늦게 효과를 확정할 수 없게 한다.
  • [보안] key에 tenant·주체·업무 범위를 넣거나, 그 범위 안에서만 key를 해석한다. key를 조회하거나 저장된 결과를 다시 돌려줄 때도 현재 인증과 권한을 확인한다.
  • 멱등 key는 같은 요청의 재전송을 알아보는 데 쓴다. 서로 다른 key로 같은 업무 객체를 바꾸는 경합은 version 비교, 잠금, 업무 유일성 제약 등으로 따로 막는다. 충돌하면 정한 오류와 재시도 조건을 따른다.

검증 계약

  • 정한 보장 기간 안에서 서로 다른 서버 인스턴스에 같은 key의 요청 N개를 동시에 보내고 응답 유실 후 재시도해도 업무 효과는 한 건을 넘지 않는다.
  • 보장 기간 안에서 같은 key와 뜻이 같은 입력(예: 필드 순서만 다른 입력)은 같은 요청으로 판별한다. 완료된 요청이면 저장 결과를 반환하고, 그 외 상태는 정한 응답·복구 규칙을 따른다.
  • key는 같은데 실제 값이 다른 payload는 저장된 결과를 받기 전에 거부된다.
  • 다른 tenant나 다른 주체가 같은 key 값을 보내면 서로의 결과를 받지 못한다. 각자의 범위에서 따로 처리된다.
  • 권한이 철회된 뒤 같은 key로 결과를 다시 요청하면 거부된다.
  • key 예약 전후, 업무 commit 전후, 응답을 보내기 전, 외부 효과가 성공한 직후에 각각 프로세스를 끝낸 뒤 재시도한다. 업무 효과와 외부 효과는 각각 한 건을 넘지 않는다. key만 예약하고 업무 commit 전에 끝난 요청은 완료로 응답되지 않는다. 기록은 정한 복구 상태로 남는다. 외부 효과의 재전송과 결과 확인은 트랜잭션과 변경 복구의 검증 계약대로 시험한다. 수신 측 멱등 처리를 선택한 경우에는 그 보장 기간 안에서 같은 key로 재전송해도 외부 효과가 추가되지 않는다.
  • 프로세스나 복구 담당 작업자를 재시작해도 진행 중·완료·결과 불명 상태가 정한 정책대로 복구된다.
  • 완료 기록은 보장 기간이 끝나기 직전에 재시도하면 저장 결과를 반환하고, 끝난 직후에는 정한 만료 후 규칙을 따른다. 진행 중·실패·결과 불명 기록은 각각 정한 응답·복구 규칙을 시험한다. 진행 중·결과 불명 기록은 보장 기간 경과만으로 삭제하거나 새 요청으로 실행하지 않는다.
  • 실행권이 만료돼 다른 작업자에게 넘어간 뒤 이전 작업자가 돌아와 효과를 확정하려 하면 거부된다. 효과는 더 생기지 않는다.
  • version 비교를 선택했으면 같은 version의 객체에 서로 다른 key로 변경을 요청해 한 건만 반영되고 나머지는 충돌하는지 확인한다. 잠금·업무 유일성 제약을 선택했으면 해당 경합 입력에서 정한 직렬 처리나 충돌 결과를 확인한다. 모든 경우에 변경 유실과 업무 제약 위반이 없어야 한다.

조건부 기술스택 프로필

DB unique index, optimistic lock, Redis atomic command, Spring transaction, Django constraint는 구현 선택지다. 근거 없이 "정확히 한 번 전달된다"고 약속하지 않는다.

출처와 제한

이 패턴은 일반적인 멱등성·동시성 원칙에서 나왔고, 참고한 프로젝트 구현은 없다. 그래서 첫 적용 때 이 문서의 검증 계약으로 직접 확인한다. 기준은 반드시 지킬 조건과 검증 계약이다. 특정 구현의 코드를 그대로 가져다 쓰지 않고, 나중에 참고할 구현이 생겨도 이 문서의 검증 계약을 통과해야 쓴다.
