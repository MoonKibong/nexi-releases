SSO와 계정 프로비저닝

SSO와 계정 프로비저닝

읽기 안내 — 누가: 작업 계약을 쓰는 개발자, FDE · 언제: T#에서 이 문제를 풀 방법을 정할 때 · 읽은 뒤: 적용 전 결정을 고객·기술 책임자와 정하고, 반드시 지킬 조건을 수용 기준과 테스트에 넣는다.

해결하는 문제

외부 IdP로 로그인한 사람을 내부 계정·조직·권한에 안전하게 연결한다. 퇴사하거나 권한이 바뀌면 그것도 반영한다.

적용 전 결정

고객과 다음을 정한다.

반드시 지킬 조건

  • [보안] 선택한 프로토콜 프로필의 필수 검증이 모두 성공한 뒤에만 외부 신원을 쓴다. 검증 계약이 없는 프로토콜과 흐름은 지원하지 않는다. 프로필은 아래 필수 프로토콜 최소 조건 절에 있다.
  • [보안] 외부 신원은 IdP와, 그 IdP가 보장하는 식별자의 조합으로 매핑한다. 이 식별자는 바뀌지 않고 다른 사람에게 다시 배정되지 않아야 한다. OIDC는 검증을 마친 (issuer, subject)를 쓴다. SAML은 합의한 영속 식별자와 식별자 범위를 쓴다.
  • [보안] email이 같다는 것만으로 기존 계정에 자동 연결하지 않는다. 일시적 NameID만으로 영속 계정을 연결하지도 않는다. 기존 계정의 연결과 해제는 권한 있는 확인 절차를 거친다.
  • [보안] 인증에 성공했다는 것만으로 조직에 가입시키거나 관리자 권한을 주지 않는다. membership과 역할은 승인한 출처에서 따로 확인한다.
  • [보안] 기본 범위인 요청 시작형 흐름의 callback은 처음 보낸 요청과 묶는다. 한 번만 쓸 수 있고, 시간이 지나면 만료된다. 요청 없는 IdP 시작 SAML 흐름은 승인한 별도 계약과 검증을 따른다.
  • 계정·외부 신원·membership 생성은 중복 요청과 동시 로그인에서도 일관되게 끝나게 한다. 계정이나 매핑이 중복되거나 일부만 생기지 않는다.
  • [보안] 동기화 입력은 인증·인가된 출처에서만 받는다. 같은 입력이 중복되거나 순서가 뒤바뀌어도 처리한다. 오래된 조직·역할 이벤트는 더 최신인 권한 상태를 덮어쓰지 않는다. 비활성화보다 오래된 활성화·역할 이벤트와 일반 로그인은 비활성 계정을 다시 활성화하지 않는다.
  • [보안] 계정 비활성화와 권한 철회는 정한 최대 반영 시간 안에 적용한다.
  • IdP 로그아웃, 앱 세션 종료, refresh token 철회, 계정 비활성화는 수명주기가 서로 다르다. 실제로 어디까지 지원하는지 작업 계약서에 적는다.
  • [보안] IdP에 장애가 나거나 검증에 실패하면 일반 로그인을 허용하지 않는다. break-glass는 정한 주체·범위·유효기간 밖에서는 쓸 수 없는 운영 절차다.
  • [보안] 로그인, 매핑, 프로비저닝, 권한 변경, break-glass 사용의 결과와 원인을 감사 기록에 남긴다. 토큰·assertion·code 원문 같은 비밀값은 넣지 않는다.

검증 계약

  • OIDC에서는 다음을 각각 시험한다. state·nonce 누락 또는 요청과의 불일치, PKCE verifier 누락·불일치, PKCE S256 미적용, 미등록·불일치 redirect URI, 잘못된 서명·허용하지 않은 알고리즘·신뢰하지 않는 키, 필수 claim 누락·issuer/audience 불일치·시간 조건 위반이다. 만료된 로그인 요청과 이미 소비한 callback/code의 재사용도 거부된다. 거부할 때 계정·세션·권한이 생기지 않는다. 서로 다른 정상 로그인에서 같은 issuer·audience·등록 redirect URI를 쓰는 것은 재사용 공격으로 판단하지 않는다.
  • 다른 브라우저 세션에서 시작한 로그인 요청의 callback, 응답 issuer가 처음 선택한 issuer와 다른 callback은 거부된다. 신뢰하지 않는 issuer도 거부된다.
  • SAML에서 다음 입력은 거부되고 계정·세션·권한이 생기지 않는다. 서명이 없거나 신뢰하지 않는 키로 서명한 응답, 서명한 부분과 실제로 소비하는 assertion이 다른 응답, audience·destination·recipient·시간 조건·InResponseTo가 틀리거나 만료된 응답, 이미 쓴 assertion이다. 선택한 SAML 프로필의 필수 audience·destination·recipient·시간 조건· InResponseTo를 각각 누락한 응답도 계정·세션·권한 부여 없이 거부된다.
  • 별도 계약 없이, 요청 없이 IdP가 시작한 SAML 흐름의 응답이 오면 거부된다.
  • 서로 다른 IdP에서 같은 식별자나 같은 email이 오면 다른 외부 신원으로 처리된다. 기존 계정에 자동으로 연결되지 않는다.
  • 같은 IdP에서 email만 바뀐 사용자는 원래 계정으로 로그인한다. email이나 일시적 NameID만 맞는 입력은 기존 계정에 연결되지 않는다.
  • 권한 있는 확인 없이 보낸 계정 연결·해제 요청은 거부된다.
  • 같은 외부 신원으로 최초 로그인과 JIT 가입을 동시에 보내면 계정·매핑·membership이 각각 하나만 생긴다.
  • 프로비저닝 중간에 저장 실패를 주입하면 계정·매핑·membership이 일부만 남지 않는다. 다시 시도하면 각각 하나로 끝난다.
  • 인증·인가되지 않은 출처의 동기화 입력은 거부된다. 같은 동기화 이벤트가 두 번 오면 한 번만 반영된다.
  • 활성 계정에 최신 역할 철회 이벤트를 먼저 반영한 뒤 더 오래된 역할 부여 이벤트를 보내도 철회된 권한이 복구되지 않는다.
  • 비활성화보다 오래된 활성화·역할 이벤트와 일반 로그인은 비활성 계정을 다시 활성화하지 않는다. 계정 수, membership, 최종 권한이 비활성화 직후와 같다.
  • 승인받지 않은 조직 가입과 권한 부여는 거부된다.
  • 비활성 계정의 새 로그인과 기존 세션은 모두 정한 최대 반영 시간 안에 차단된다. 권한 철회도 같은 시간 안에 반영된다.
  • 지원하는 수명주기 동작을 각각 실행하고, 약속한 범위와 시각에만 효과가 생기는지 확인한다. 로컬 로그아웃만으로 IdP 세션 종료나 refresh token 철회를 보장하지 않는다.
  • IdP timeout을 주입하면 일반 로그인이 성공하지 않는다. 같은 callback을 다시 보내면 두 번째 요청은 거부되고 계정과 세션이 더 생기지 않는다.
  • 만료됐거나 정한 주체·범위 밖의 break-glass 사용은 거부된다.
  • 위 사례마다 결과와 원인이 담긴 감사 이벤트가 남는다. 감사 기록과 로그에 토큰·assertion·code 원문이 없다.

필수 프로토콜 최소 조건

OIDC나 SAML을 쓰면 어느 라이브러리를 쓰든 아래 최소 프로필을 반드시 지킨다. OIDC, SAML, Spring Security, Django, Next.js 인증 라이브러리별 프로필은 아직 없다. 프로젝트가 라이브러리를 정하면 그 공식 보안 지침을 쓴다. XML 서명·JWT 검증은 직접 구현하지 않는다.

  • OIDC 기본 프로필: Authorization Code와 PKCE S256을 쓴다. 로그인 요청의 state·nonce·PKCE 정보를 그 요청을 시작한 브라우저 세션과 선택한 issuer에 묶는다. 등록한 redirect URI와 신뢰하는 키·알고리즘만 쓴다. ID token은 서명·issuer· audience·시간 조건·nonce를 검증한다. 응답의 issuer가 처음 선택한 issuer와 같은지 확인한다.
  • SAML 프로필: 신뢰하는 metadata와 키를 쓴다. 서명을 검증한 대상이 실제로 소비하는 assertion과 같은지 확인한다. audience·destination·recipient·시간 조건·InResponseTo를 검증하고, assertion 재사용을 막는다. 요청 없이 IdP가 시작하는 흐름은 기본 범위에서 뺀다. 필요하면 별도 계약으로 정한다.

출처와 제한

이 패턴은 이전 프로젝트들의 구현 경험에서 나왔다. 기준은 반드시 지킬 조건과 검증 계약이다. 특정 구현의 코드를 그대로 가져다 쓰지 않고, 참고한 구현도 이 문서의 검증 계약을 통과해야 쓴다.
