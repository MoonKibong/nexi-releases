상태 전이와 감사 기록

읽기 안내 — 누가: 작업 계약을 쓰는 개발자, FDE · 언제: T#에서 이 문제를 풀 방법을 정할 때 · 읽은 뒤: 적용 전 결정을 고객·기술 책임자와 정하고, 반드시 지킬 조건을 수용 기준과 테스트에 넣는다.

해결하는 문제

승인·취소·완료처럼 순서와 권한이 정해진 변경은 서버가 통제한다. 누가 언제 무엇을 했는지 추적할 수 있게 한다.

반드시 지킬 조건

  • [보안] 화면 단계나, status 문자열을 직접 PATCH하는 방식으로 권한을 통제하지 않는다. API 형태와 상관없이 서버가 전이 규칙을 집행한다.
  • [보안] 서버가 현재 상태·권한(권한 부여와 데이터 격리)·먼저 갖출 조건을 확인하고, 이 확인과 전이를 동시 변경으로부터 보호한다. version 계약을 쓰면 요청 version 비교, 상태 변경, version 증가를 원자적으로 처리한다.
  • 상태 전이와 필수 감사 기록은 같은 원자성 경계(트랜잭션과 변경 복구)에서 확정한다. 필수 감사 기록을 저장하는 데 실패하면 상태 전이도 확정하지 않는다. 외부 감사 시스템으로 보내는 일은 원자적으로 저장한 기록이나 전달 의도에서 재시도할 수 있다.
  • 같은 명령을 다시 보내도 전이나 업무 효과가 더 생기지 않는다(멱등성과 동시성). 이벤트가 중복되거나, 순서가 뒤바뀌거나, 재시도되거나, 승인과 취소가 동시에 들어오면 결과가 어떻게 되는지 적어 둔다.
  • [보안] 감사 기록의 주체·시간·행동·대상·결과는 검증된 서버 컨텍스트에서 만든다. 전후 상태와 version, 또는 그와 같은 순서 정보를 남긴다. 비밀값은 넣지 않고, 로그 삽입을 노린 입력은 안전하게 처리한다.
  • [보안] 일반 업무 권한으로는 감사 기록을 고치거나 지울 수 없게 한다. 감사 기록에도 조회 권한과 보존·폐기 절차를 적용한다.

검증 계약

  • 금지된 전이와 권한 없는 전이는 거부된다. 이때 상태가 바뀌지 않고, 성공으로 기록한 필수 감사 기록도 생기지 않는다.
  • 같은 version에 승인과 취소가 동시에 들어오면 한 건만 성공하고 다른 건은 충돌로 끝난다. stale version 요청은 아무것도 바꾸지 않는다. 같은 명령을 다시 보내도 효과가 더 생기지 않는다.
  • 필수 감사 저장 실패를 주입하면 상태·version·필수 업무 효과가 바뀌지 않는다. 외부 감사 전송만 실패하면 로컬 필수 기록이 남고, 다시 보내 복구된다.
  • 주체 위조, 다른 tenant의 감사 기록 조회, 무단 수정·삭제, 비밀값·줄바꿈이 든 입력을 시험한다. 감사 기록의 생성뿐 아니라 접근 통제와 변조 방지도 확인한다.

출처와 제한

이 패턴은 일반적인 상태 전이·감사 기록 원칙에서 나왔고, 이전 프로젝트의 구현과 대조해 핵심 조건을 확인했다. 기준은 반드시 지킬 조건과 검증 계약이다. 특정 구현의 코드를 그대로 가져다 쓰지 않고, 참고한 구현도 이 문서의 검증 계약을 통과해야 쓴다.
