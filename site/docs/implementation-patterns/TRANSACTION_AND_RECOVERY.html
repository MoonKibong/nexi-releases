트랜잭션과 변경 복구

트랜잭션과 변경 복구

읽기 안내 — 누가: 작업 계약을 쓰는 개발자, FDE · 언제: T#에서 이 문제를 풀 방법을 정할 때 · 읽은 뒤: 적용 전 결정을 고객·기술 책임자와 정하고, 반드시 지킬 조건을 수용 기준과 테스트에 넣는다.

해결하는 문제

데이터 변경이 중간에 실패해도 업무 상태와 필수 감사 기록이 서로 어긋나지 않게 한다. 외부 효과는 나중에 다시 처리할 수 있게 남긴다.

반드시 지킬 조건

  • DB transaction이 외부 HTTP·메일·object storage까지 자동으로 되돌려 준다고 가정하지 않는다.
  • 동시 실행에서도 지킬 업무 불변조건을 적는다. 선택한 격리 수준·잠금·조건부 갱신·제약으로 그 조건을 지킨다.
  • deadlock·직렬화 실패처럼 재시도해도 되는 오류가 나면 전체 트랜잭션을 정한 횟수와 시간 안에서 다시 실행한다. 재시도하면서 외부 효과를 중복 실행하지 않는다.
  • 업무 상태와 필수 감사 기록은 같은 원자성 경계 안에서 함께 저장한다.
  • "일부만 바뀐 상태가 남지 않는다"는 정한 원자성 경계 안에 적용한다. 외부 효과까지 그렇게 된다고 약속하지 않는다.
  • 외부로 보낼 일(전달 의도)은 DB 변경과 함께 durable record로 남긴다. 실제로 보내는 쪽(전달자)은 재시도와 중복을 고려한다.
  • 외부 효과는 중복 전달과 응답 유실을 전제로, 결정표에서 선택한 수신 측 멱등 처리 또는 결과 조회·대사 절차로 연결한다. 외부 효과에 관한 결정과 검증은 이 문서에서 다룬다. key와 중복 판별 규칙은 멱등성과 동시성을 따른다. 전달 의도를 남기는 것만으로 중복 소비를 막았다고 보지 않는다.
  • 순서가 중요한 작업은 순서를 알아볼 수 있게 하고, 순서가 뒤바뀌었을 때의 처리를 정한 대로 따른다.
  • 영구 실패와 결과 불명에는 재처리·보상·수동 복구 중 하나의 책임을 둔다. 보상이 원래 효과를 완전히 되돌린다고 가정하지 않는다.
  • 외부 호출이 오래 걸리면, 그동안 DB lock을 정한 상한보다 오래 잡고 있지 않는다.
  • 백업을 복원하면 외부 효과의 처리 기록이 과거로 돌아갈 수 있다. 그래서 복원한 뒤 외부로 다시 보내기 전에 대사한다.
  • 구·신 앱을 함께 운영하는 배포는 정한 버전 조합과 스키마 변경·되돌리기 조건 안에서만 한다.

검증 계약

  • 쓰기 단계마다 일부러 실패를 일으켜, 정한 원자성 경계 안에 일부만 바뀐 상태가 남지 않는지 확인한다.
  • 같은 자원을 소비하는 병렬 요청(예: 남은 수량이 1인 자원에 소비 요청 2건)을 보내면 업무 불변조건이 지켜진다. 경합에서 실패한 요청은 정한 응답을 받는다.
  • 변경 유실이나 write skew를 일으키는 동시 입력을 보내도 업무 불변조건이 지켜진다.
  • 재시도해도 되는 오류를 계속 일으켜 재시도를 다 쓰면 정한 오류 응답으로 끝난다. 일부만 바뀐 상태가 남지 않고, 재시도 중에 외부 효과가 중복 실행되지 않는다.
  • commit 직후 프로세스가 종료돼도 전달 의도와 복구 정보가 남아 있다.
  • 외부 작업이 성공한 뒤 응답이 유실되는 상황을 주입한다. 수신 측 멱등 처리 방식이면 같은 key의 재전송이 추가 효과를 만들지 않는다. 결과 조회·대사 방식이면 성공을 확인한 효과는 다시 실행하지 않는다. 미실행과 이전 요청의 뒤늦은 성공 가능성을 배제했다고 확인하기 전에는 새 실행을 하지 않는다.
  • 같은 메시지를 두 번 보내거나 순서를 바꿔 보내면 정한 중복·역전 처리대로 끝난다.
  • 영구 실패를 주입하면 정한 재처리·보상·수동 복구 책임자에게 넘어간다. 보상 실패를 주입하면 그 효과가 미해결로 남고 책임자가 볼 수 있다.
  • 결과 조회·대사로도 성공 여부를 확정할 수 없는 장애를 주입하면 결과 불명 상태와 담당자가 남는다. 근거 없이 재실행하거나 성공으로 처리하지 않는다.
  • 외부 호출 지연을 주입했을 때 DB lock을 잡고 있는 시간이 정한 상한을 넘지 않는다.
  • 알려진 변경과 외부 효과 집합을 만든 뒤 지정 시점으로 복원한다. 손실 범위와 소요 시간이 목표 이내인지 확인한다. 누락·중복·미해결 효과가 대사 결과와 일치하는지 확인한다. 대사 전에는 외부로 다시 보내지 않는지도 확인한다.
  • 버전 공존을 선택한 경우, 정한 스키마 변경·되돌리기 조건 안에서 지원하는 버전 조합마다 같은 스키마로 읽기·쓰기를 하고, 배포를 되돌리는 복구를 실제로 시험한다.

조건부 기술스택 프로필

Spring @Transactional, Django atomic, SQL transaction은 구현 수단이다. proxy·테스트 transaction·DB dialect에 따라 동작이 다를 수 있다. 이 차이를 확인하지 않고 어디서나 똑같이 동작한다고 가정하지 않는다.

출처와 제한

이 패턴은 일반적인 트랜잭션·복구 원칙에서 나왔고, 참고한 프로젝트 구현은 없다. 그래서 첫 적용 때 이 문서의 검증 계약으로 직접 확인한다. 기준은 반드시 지킬 조건과 검증 계약이다. 특정 구현의 코드를 그대로 가져다 쓰지 않고, 나중에 참고할 구현이 생겨도 이 문서의 검증 계약을 통과해야 쓴다.
