입력 검증과 오류 응답 계약

읽기 안내 — 누가: 작업 계약을 쓰는 개발자, FDE · 언제: T#에서 이 문제를 풀 방법을 정할 때 · 읽은 뒤: 적용 전 결정을 고객·기술 책임자와 정하고, 반드시 지킬 조건을 수용 기준과 테스트에 넣는다.

해결하는 문제

사용자·agent·외부 시스템이 보낸 입력을 안전하게 해석한다. 실패한 요청은 사용자와 다음 시스템이 처리할 수 있도록 일관된 오류로 돌려준다.

언제 사용하는가

생성·수정 API, 폼, 파일 업로드, webhook, agent tool 입력처럼 외부에서 들어오는 값을 받는 모든 작업에 적용한다. 파일 내용 검사나 webhook 진위 확인처럼 형식 검증 밖의 요건은 별도 계약이 필요하다.

적용 전 결정

결정 정할 내용
입력 의미 create/update에서 누락·null·빈 문자열·빈 배열이 각각 무엇을 뜻하는지
오류 형식 HTTP 상태, 안정된 오류 코드, 사용자 메시지, field 오류, trace ID
자원 상한 요청 전체 크기, 컬렉션 원소 수, 중첩 깊이, 파싱·검증에 허용할 자원 상한
중복 제출 같은 요청을 다시 보냈을 때 거부, 덮어쓰기, 멱등 처리(멱등성과 동시성) 중 무엇을 할지
내부 진단 사용자에게 보여 주지 않을 로그 항목과 보존 위치

반드시 지킬 조건

  • [보안] 클라이언트 검증은 편의 기능이다. 최종 검증은 서버가 한다.
  • 허용하는 필드·형식·길이·enum·관계를 적어 둔다. 알 수 없는 입력을 무시할지 거부할지는 계약으로 정한다.
  • [보안] 작업·주체별로 바꿀 수 있는 필드를 제한한다. 요청을 저장 객체에 그대로 바인딩하지 않는다. 알 수 없는 필드를 무시하기로 했으면 저장·후속 처리 전에 제거한다. 권한·tenant·소유권 같은 보호 필드는 승인된 변경 경로에서만 바꾼다. 관계 객체의 범위와 권한은 서버가 권한 부여와 데이터 격리에 따라 검증한다.
  • [보안] 입력 검증은 쿼리 바인딩이나 출력 인코딩을 대신하지 않는다.
  • [보안] 형식이 잘못됐거나 자원 상한을 넘은 입력은 업무 효과를 만들기 전에 거부한다.
  • [보안] 비밀값·SQL·내부 경로·stack trace는 사용자 메시지뿐 아니라 field 오류·상세 필드·헤더를 포함한 외부 오류 응답 전체에서 뺀다. 오류 로그에도 비밀번호·토큰 원문을 남기지 않는다.
  • 오류 코드는 클라이언트가 분기할 수 있을 만큼 안정적으로 유지한다. 오류 문구만 보고 분기하지 않는다.
  • 수정 요청이 의도하지 않게 관계를 지우거나 기본값을 덮어쓰지 않도록, 누락·null·빈 값의 의미를 구분한다.

구현 절차

  1. FDE가 입력 필드마다 업무 규칙과, 오류가 났을 때 사용자가 다음에 할 일을 정리한다.
  2. 개발자가 서버 schema와 오류 응답 형식을 쓴다.
  3. 프런트엔드는 field 오류와 일반 오류를 구분해 보여 주고, 실패한 입력을 불필요하게 지우지 않는다.
  4. 개발자가 인증·권한·검증·충돌·내부 오류 응답이 서로 구분되는지 확인하는 검사를 만들고 결과를 증거 파일에 남긴다. 리뷰에서 그 결과를 대조한다.

검증 계약

  • 공백만 있는 값, 길이 초과, 잘못된 enum, 누락·null·빈 값, 서로 의존하는 두 필드가 모순되는 경우를 확인한다. 입력 사례마다 상태 코드, 안정된 오류 코드, 저장 결과를 적는다.
  • update에서 누락된 필드는 기존 값을 유지한다. null은 허용된 필드만 해제한다. 빈 값은 필드별 결정대로 처리한다. 잘못된 enum이나 서로 모순되는 관계는 아무것도 바꾸지 않고 거부한다.
  • 상한 직전의 값·상한과 같은 값·상한을 넘는 값과 파싱에 실패하는 입력마다 성공 또는 정한 오류 코드가 나온다. 거부된 입력은 데이터를 바꾸지 않는다.
  • create와 update가 관계 필드와 기본값을 계약대로 다룬다.
  • 중복 제출, stale version, 권한 없음, 존재하지 않는 객체, 내부 오류에는 정한 오류 코드와 안전한 메시지를 돌려준다. 인증·권한·충돌·내부 오류 응답은 오류 형식 결정에서 정한 코드와 대조한다.
  • 오류 응답의 메시지·field 오류·상세 필드·헤더와 오류 로그에 비밀값·내부 경로·stack trace·토큰 원문이 나오지 않는다.
  • 클라이언트를 거치지 않고 API를 직접 호출해도 서버가 같은 규칙으로 거부한다.
  • 보호 필드나 다른 tenant의 관계 ID를 넣은 직접 API 요청으로 권한 상승, 관계 연결, 보호 필드 변경이 일어나지 않는다. tenant·권한 사례는 권한 부여와 데이터 격리의 검증 계약과 맞춘다.

조건부 기술스택 프로필

Zod/react-hook-form, Spring Bean Validation, Rust serde validator는 구현 선택지다. schema를 한 언어에서 공유할지는 프로젝트의 빌드·배포 구조를 보고 정한다.

출처와 제한

이 패턴은 이전 프로젝트들의 구현 경험에서 나왔다. 기준은 반드시 지킬 조건과 검증 계약이다. 특정 구현의 코드를 그대로 가져다 쓰지 않고, 참고한 구현도 이 문서의 검증 계약을 통과해야 쓴다.
