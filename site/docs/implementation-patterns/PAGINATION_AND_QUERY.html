페이지네이션과 조회

페이지네이션과 조회

읽기 안내 — 누가: 작업 계약을 쓰는 개발자, FDE · 언제: T#에서 이 문제를 풀 방법을 정할 때 · 읽은 뒤: 적용 전 결정을 고객·기술 책임자와 정하고, 반드시 지킬 조건을 수용 기준과 테스트에 넣는다.

해결하는 문제

많은 데이터를 목록으로 조회할 때 권한을 지킨다. 조건이 같으면 순서와 페이지 결과를 예측할 수 있게 한다.

언제 사용하는가

목록 결과가 한 화면·한 응답을 넘거나, 검색·다중 필터·정렬·내보내기 기능이 있으면 적용한다. 수십 건짜리 고정 참조 데이터처럼 한 번에 다 보내는 편이 더 단순하면 적용하지 않는다.

적용 전 결정

결정 정할 내용
페이지 방식 offset/page와 cursor 중 데이터 규모·변경 빈도에 맞는 방식
기본·최대 크기 기본 page size, 허용 최소·최대, 최대를 넘었을 때 거부할지 제한할지
정렬 허용 필드, 기본 순서, 정렬 값이 같을 때 순서를 정할 유일키, null 정렬 규칙
필터 허용 필드·연산자, 다중 필터의 AND/OR 의미, 빈 배열의 의미
일관성 페이지를 넘기는 동안 데이터가 바뀔 때 허용할 중복·누락·최신성, 조건이 바뀐 cursor를 거부할지 처음부터 다시 할지
count와 export total count·export의 비용을 어떻게 제한할지(권한·기본 필터는 아래 조건대로 items와 같게 건다)

반드시 지킬 조건

  • page와 page size는 숫자 범위와 상한을 검사한다. 정수가 아니거나 최소보다 작은 값(0·음수 포함)은 정한 검증 오류로 거부한다. 최대를 넘는 값은 결정표에서 정한 대로 거부하거나 최대로 제한한다.
  • 정렬 기준 맨 마지막에 유일키를 넣는다. 그래야 같은 요청을 다시 보내도 결과 순서가 제멋대로 바뀌지 않는다.
  • [보안] items, total count, export는 같은 tenant·권한·기본 필터를 쓴다.
  • [보안] total count는 items와 같은 권한 범위와 사용자 필터를 적용한 전체 건수다. 범위가 다른 집계나 export가 필요하면 이름과 계약을 따로 둔다.
  • [보안] cursor의 형식과 현재 조회 조건에 맞는지를 검증한다. cursor에 든 tenant·권한 값은 믿지 않는다. 다음 페이지 요청에서도 서버가 권한을 다시 확인한다.
  • [보안] 정렬·필터 필드와 연산자는 allowlist로 제한하고, 쿼리 값은 바인딩한다.
  • [보안] 사용자 필터가 권한 필터를 대신하지 않는다. 권한 필터를 먼저 걸고, 그 위에 사용자가 고른 조건을 더한다.
  • 데이터가 바뀌지 않는 동안에는 유일키를 포함한 정렬로 페이지 사이의 중복·누락을 막는다. 페이지를 넘기는 동안 데이터가 바뀌면 중복·누락·최신성을 어디까지 허용할지 API 계약에 따로 정한다. cursor만으로 snapshot 일관성이 보장된다고 보지 않는다. 같은 시점의 데이터를 빠짐없이 순회해야 하면 snapshot이나 그와 같은 효과를 내는 조회 기준을 유지한다.

구현 절차

  1. FDE가 화면·API마다 무엇을 조회하려는지, 어떤 필터·정렬이 필요한지 정리한다.
  2. 개발자가 요청·응답 형식, 기본값, 오류 응답을 작업 계약에 적는다.
  3. 개발자가 items/count/export의 모든 쿼리에 권한 조건이 들어갔는지 확인한다.
  4. 개발자가 정렬 값이 같은 데이터와 다른 tenant 데이터를 넣고 페이지를 넘기는 검사를 만들고, 결과를 증거 파일에 남긴다. 리뷰에서 그 결과를 대조한다.

검증 계약

  • 첫 페이지, 마지막 페이지, 빈 결과, page size 최소·최대·0·음수·초과값을 확인한다. page와 page size에 정수가 아니거나 최소보다 작은 값이 오면 정한 검증 오류로 거부한다. 최대 크기를 넘으면 결정표대로 거부하거나 제한한다.
  • 데이터를 고정한 채 같은 조건으로 다시 요청하거나 페이지를 넘기면, 정렬 값이 같은 데이터가 중복·누락·순서 변경 없이 나온다.
  • 페이지 사이에 삽입·삭제·정렬 값 변경이 일어나면, 정한 일관성 계약에 적은 기대 결과대로 나온다.
  • 허용하지 않은 정렬·필터 필드와 연산자는 거부된다. 필터 값에 ' OR 1=1 -- 같은 주입 문자열을 넣었을 때 타입에 맞지 않으면 검증 오류를 돌려준다. 타입에 맞는 문자열이면 고른 연산자의 데이터 값으로만 처리한다. 내부 쿼리 오류 내용은 응답에 드러나지 않는다.
  • 다른 tenant·권한의 데이터가 items, count, export 어디에도 섞이지 않는다.
  • total count·export가 정한 비용 상한을 넘으면 결정한 대로 동작한다.
  • 필터를 바꾼 뒤, 다른 tenant에서, 권한이 철회된 뒤 cursor를 다시 쓰면 거부되거나 명시한 재시작 동작을 한다. 어느 경우에도 다른 범위의 데이터가 드러나지 않는다.
  • 필터를 바꾸면 페이지를 처음으로 되돌릴지 등, UI·API가 약속한 동작을 확인한다.

조건부 기술스택 프로필

SeaORM/Loco pagination, Spring Data Pageable, SQL cursor, React data table은 구현 선택지다. 복잡한 검색에 POST /search를 쓸지 GET query를 쓸지는 캐시·URL 공유·필터 복잡도를 보고 프로젝트에서 정한다.

출처와 제한

이 패턴은 이전 프로젝트들의 구현 경험에서 나왔다. 기준은 반드시 지킬 조건과 검증 계약이다. 특정 구현의 코드를 그대로 가져다 쓰지 않고, 참고한 구현도 이 문서의 검증 계약을 통과해야 쓴다.
