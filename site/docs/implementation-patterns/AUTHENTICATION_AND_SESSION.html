인증과 로그인 세션

인증과 로그인 세션

읽기 안내 — 누가: 작업 계약을 쓰는 개발자, FDE · 언제: T#에서 이 문제를 풀 방법을 정할 때 · 읽은 뒤: 적용 전 결정을 고객·기술 책임자와 정하고, 반드시 지킬 조건을 수용 기준과 테스트에 넣는다.

해결하는 문제

요청을 보낸 사람이 누구인지 확인한다. 로그인한 뒤에도 같은 사용자인지 안전하게 판단한다.

언제 사용하는가

사용자마다 다른 화면·데이터·권한이 있거나, 외부 IdP/SSO나 초대 기반 가입을 쓰는 서비스에 적용한다. 공개 정보만 주는 API에는 로그인 세션을 억지로 넣지 않는다.

적용 전 결정

결정 정할 내용
로그인 방식 비밀번호, 기업 SSO, 초대, 또는 이들의 조합. SSO를 쓰면 OIDC와 SAML 중 무엇을 쓰는지
세션 방식 서버 세션, HttpOnly cookie에 담는 토큰, 플랫폼 IdP 토큰 중 하나. 서명 토큰이면 허용할 알고리즘, 신뢰할 키, 발급자·대상·용도 값
세션 식별자 발급 사용할 생성기와 난수부 엔트로피 기준
만료·갱신 유휴 만료와 절대 만료 시간, 갱신 조건. refresh token을 쓰면 회전·재사용 탐지 방식과 같은 token으로 동시에 갱신할 때의 정책
로그아웃·철회 반영 로컬 로그아웃, 서버 세션 폐기, refresh token 철회, 접근 토큰 만료, 권한 변경 반영 각각의 차단 대상과 무효화 방법, 최대 반영 시간과 이미 실행 중인 요청의 처리 경계
가입 정책 공개 가입, 관리자 초대, SSO 자동 가입 중 무엇을 허용하는지. 초대 토큰의 만료 시간
비밀번호 보호 비밀번호를 지원하면 저장 방식(해시 알고리즘과 설정), 로그인 실패 횟수 한도와 그 한도를 넘었을 때의 처리, 계정이 있는지 드러내지 않는 응답 형태
HTTPS와 도메인 cookie의 Secure, HttpOnly, SameSite, domain·path 정책
CSRF 방어 cookie 인증의 상태 변경 경로에 적용할 방어 방식과 허용 출처. SSO callback에 적용할 별도 프로토콜 검증

반드시 지킬 조건

  • [보안] 인증(authentication)과 권한 부여(authorization)를 나눈다. 로그인했다고 모든 기능을 쓸 수 있는 것은 아니다.
  • [보안] 보호 대상인 모든 요청에서 서버가 선택한 인증 방식에 맞게 자격증명을 검증한다.
    • 서버 세션은 서버가 발급한 식별자가 있는지, 만료되거나 폐기되지 않았는지 확인한다.
    • 서명 토큰은 허용한 알고리즘과 신뢰하는 키로 서명을 확인한다. 발급자·대상·만료·용도도 검증한다.
  • [보안] 세션 식별자는 암호학적으로 안전한 난수 생성기로 정한 엔트로피 기준에 맞게 발급해 예측하기 어렵게 한다. 로그인할 때와 권한이 올라갈 때 식별자를 바꾼다. 이전 식별자로는 올라간 권한을 쓸 수 없게 한다.
  • [보안] 유휴 만료와 절대 만료는 서버가 집행한다.
  • [보안] refresh token을 쓰면 회전과 재사용 탐지, 또는 그와 같은 수준의 탈취 대응을 둔다. 같은 refresh token으로 동시에 갱신할 때의 정책도 정해서 따른다.
  • 로컬 로그아웃, 서버 세션 폐기, refresh token 철회, 접근 토큰 만료, 권한 변경 반영을 서로 다른 동작으로 다룬다. 동작마다 최대 반영 시간과 이미 실행 중인 요청을 어디까지 처리할지 정한다.
  • 자체 검증 토큰은 철회를 따로 확인하는 수단이 없으면 만료 전까지 유효할 수 있다. 이 한계를 작업 계약서에 적는다.
  • [보안] 권한 철회는 세션이 끝났는지와 상관없이 권한 부여와 데이터 격리의 계약을 따른다.
  • [보안] 비밀번호 인증을 지원하면 비밀번호를 안전한 해시 방식으로 저장하고, 로그인 시도 횟수를 제한한다. 로그인 응답으로 계정이 있는지 드러내지 않는다.
  • [보안] 초대 토큰은 대상·용도·만료에 묶는다. 한 번만 쓸 수 있게 원자적으로 소비한다.
  • [보안] 인증에 실패하면 세션이나 권한을 주지 않는다.
  • [보안] 브라우저 JavaScript에 장기 자격증명이나 refresh token을 돌려주지 않는다.
  • [보안] cookie로 인증하면 HTTPS에서 Secure와 HttpOnly를 쓴다. 교차 사이트 요청을 막는 SameSite·CSRF 방어도 함께 설계한다.
  • [보안] 비밀번호·토큰·세션 식별자·인증 header를 로그와 오류 응답에 남기지 않는다.
  • [보안] SSO는 처음 로그인 요청과 응답을 묶고, 선택한 프로토콜의 필수 검증 계약대로 응답을 검증한다. SSO와 계정 프로비저닝을 따른다. 검증이 끝나기 전에는 계정·조직 권한을 주지 않는다.

구현 절차

  1. FDE가 사용자 유형과 보호할 기능을 정리하고, 가입·로그인·로그아웃·권한 철회 흐름을 그린다. 위 적용 전 결정 표의 값을 작업 계약에 적는다.
  2. 개발자가 로그인 응답, cookie 또는 header, 만료 오류, 세션 식별자 교체, 갱신의 API 계약을 쓴다.
  3. 개발자가 인증 다음에 적용할 역할·객체 접근 패턴을 권한 부여와 데이터 격리에 따라 연결한다.
  4. 개발자가 개발·시험·운영 환경마다 HTTPS와 cookie 설정이 어떻게 다른지 증거 파일에 적는다. 운영 환경의 설정은 배포 전에 운영 권한을 가진 사람이 확인한다.

검증 계약

  • 유효한 자격증명으로 보호 기능을 쓸 수 있다.
  • 자격증명이 없거나, 위조됐거나, 만료됐으면 같은 보호 기능을 쓸 수 없다.
  • 다음을 하나씩 넣으면 보호 기능 접근이 거부된다. 서버가 발급하지 않은 세션 ID, 폐기한 세션 ID, 허용하지 않은 알고리즘이나 신뢰하지 않는 키로 서명한 토큰, issuer가 다른 토큰, audience가 다른 토큰, 용도가 다른 토큰(예: refresh token을 접근 토큰 자리에 넣음)이다.
  • 세션 식별자 생성 코드와 설정을 확인해 암호학적으로 안전한 난수 생성기를 쓰고 정한 엔트로피 기준을 충족하는지 확인한다. 시간·순번·사용자 입력만으로 식별자를 만들지 않는다. 발급 표본에 중복이 없다는 것만으로 식별자를 예측할 수 없다고 판단하지 않는다.
  • 로그인 전 식별자와 교체 전 식별자로 보호 기능을 호출하면 거부된다. 권한이 올라가기 전 식별자로는 올라간 권한의 기능을 쓸 수 없다.
  • 유휴 만료 시간이 지나면 요청이 거부된다. 절대 만료 시점 뒤에는 그 사이에 요청이 계속 있었어도 거부된다.
  • 같은 refresh token을 동시에 쓰거나, 회전한 뒤 이전 refresh token을 다시 쓰면 정한 갱신·폐기 정책대로 처리된다.
  • 동작별 차단 대상과 시점을 시험한다. 로컬 로그아웃은 해당 클라이언트의 로그인 상태가 제거되는지, 서버 세션 폐기는 해당 세션의 접근이 거부되는지, refresh token 철회는 갱신이 거부되는지 확인한다. 접근 토큰은 정한 철회 확인 또는 만료 시점부터 거부된다. 권한 변경은 변경 후 권한 행렬대로 판단한다. 각 경계 시각 전후와 이미 실행 중인 요청의 처리 결과를 확인한다.
  • 정한 로그인 실패 한도까지는 시도할 수 있고, 한도를 넘은 시도는 정한 대로 막힌다. 한도 직전과 직후를 시험한다.
  • 없는 계정과 있는 계정에 틀린 비밀번호를 보내면 같은 응답을 받는다. 저장된 비밀번호 값은 원문이 아니고 정한 해시 방식으로 만든 값이다.
  • 같은 초대 토큰으로 가입 요청을 동시에 보내면 한 건만 성공한다. 만료됐거나, 이미 썼거나, 대상이나 용도가 다른 초대 토큰은 거부된다.
  • 인증에 실패한 응답에는 세션 cookie나 토큰이 없고, 서버에 세션도 생기지 않는다.
  • 실제 응답의 Set-Cookie에서 Secure·HttpOnly·SameSite 플래그와 domain·path가 정한 값인지 확인한다.
  • cookie 인증의 일반 상태 변경 경로에서 허용하지 않은 출처의 요청과 선택한 CSRF 방어를 통과하지 못한 요청은 변경 없이 거부된다. CSRF token 방식을 선택했으면 token 누락·불일치를 시험한다. SSO callback은 SSO 문서의 요청 결합·응답 검증 계약으로 시험한다.
  • SSO 응답 검증에 실패한 사례(예: state 불일치)는 SSO와 계정 프로비저닝의 검증 계약대로 거부된다.
  • 로그인 성공·실패, 만료, 거부 사례에서 모든 로그와 오류 응답에 비밀번호·접근 토큰·refresh token·세션 ID·인증 header 값이 없다.
  • 응답 본문과 JavaScript가 읽을 수 있는 브라우저 저장소에 금지한 장기 자격증명이나 refresh token이 없다.

조건부 기술스택 프로필

Rust/Loco, Spring Security, Node middleware 등은 세션을 구현하는 방식이 저마다 다르다. 프로젝트가 프레임워크를 정한 뒤, 그 프레임워크의 공식 보안 지침을 함께 보며 프로필을 쓴다.

출처와 제한

이 패턴은 이전 프로젝트들의 구현 경험에서 나왔다. 기준은 반드시 지킬 조건과 검증 계약이다. 특정 구현의 코드를 그대로 가져다 쓰지 않고, 참고한 구현도 이 문서의 검증 계약을 통과해야 쓴다.
