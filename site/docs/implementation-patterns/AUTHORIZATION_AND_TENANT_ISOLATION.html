권한 부여와 데이터 격리

읽기 안내 — 누가: 작업 계약을 쓰는 개발자, FDE · 언제: T#에서 이 문제를 풀 방법을 정할 때 · 읽은 뒤: 적용 전 결정을 고객·기술 책임자와 정하고, 반드시 지킬 조건을 수용 기준과 테스트에 넣는다.

해결하는 문제

로그인한 사람이 자기 역할과 소속 범위 안에서만 기능과 데이터를 보거나 바꾸게 한다.

언제 사용하는가

역할마다 메뉴·행동이 다르거나, 여러 고객·조직·workspace의 데이터가 한 서비스에 함께 들어 있으면 적용한다. 단일 사용자 도구라도 운영자와 일반 사용자의 권한이 다르면 권한 부여 규칙을 분명히 적는다.

적용 전 결정

결정 정할 내용
주체 요청하는 쪽이 사용자, 서비스 계정, 외부 연동 중 무엇인지
범위 전사, 조직, 자기 항목, 특정 객체 중 어디까지 허용할지
권한 행렬 역할 × 행동 × 범위 표(역할 이름 자체는 프로젝트마다 정한다)
데이터 경계 customer/tenant/organization/workspace 중 실제로 데이터를 격리하는 단위와, 믿을 수 있는 ID를 어디서 가져오는지
권한 변경 역할 변경·탈퇴·조직 이동을 언제부터 적용할지, 전파 지연을 얼마까지 허용할지, 실행 중인 작업을 어디서 중단하거나 끝낼지, 기존 세션과 캐시를 무효화하는 방법

반드시 지킬 조건

  • [보안] 권한 검사는 서버가 한다. 화면에서 버튼만 숨긴 것은 권한 검사가 아니다.
  • [보안] 기본은 거부다. 분명히 허용한다고 정하지 않은 행동은 할 수 없다. 권한 저장소에 장애가 나거나 membership 조회에 실패해도 거부한다.
  • [보안] 목록, 상세 조회, 생성, 수정, 삭제, 내려받기, export, background job에 같은 데이터 경계를 적용한다.
  • [보안] items·count·집계·export·첨부 조회의 모든 경로에 서버의 tenant·권한 조건을 건다. 사용자 필터의 OR 조건도 이 경계를 넓힐 수 없다.
  • [보안] tenant ID는 인증된 자격증명이나 검증된 membership에서 가져온다. 요청 body·query에 담긴 tenant ID를 그대로 믿지 않는다.
  • [보안] 객체 ID를 바꾸거나 조인·집계·첨부 파일을 거쳐 다른 tenant 데이터를 읽거나 바꿀 수 없어야 한다.
  • [보안] 생성·수정 요청에 든 관계 객체의 tenant와 접근 권한을 확인한다. 검사한 뒤 실제로 쓰기 전까지 생긴 변경으로 권한·소유권 조건을 우회할 수 없게 한다.
  • [보안] 권한 변경을 언제부터 적용할지, 전파 지연을 얼마까지 허용할지, 실행 중인 작업을 어디서 중단하거나 끝낼지 정한다. 세션·캐시·비동기 작업은 그 경계가 지나면 예전 권한으로 보호된 동작을 시작할 수 없다. 작업을 등록할 때뿐 아니라 실제로 실행하거나 재시도할 때도 유효한 권한을 확인한다.

구현 절차

  1. 고객이 역할 × 행동 × 범위 표를 정해 요구사항 결정 문서에 넣는다. FDE가 그 표를 작업 계약서에 옮기고 PM이 승인한다.
  2. 개발자가 인증 컨텍스트에서 주체와 tenant를 한 번 만들고, controller·service·repository가 이 값을 넘겨받아 쓰게 한다.
  3. 객체별 검사와 목록 조회 필터를 같은 정책 함수나 명확한 규칙으로 연결한다.
  4. 개발자가 "다른 사용자/다른 tenant"로 실제 요청을 보내 거부되는지 확인하는 검사를 만들고, 결과를 증거 파일에 남긴다. 리뷰에서 그 검사와 결과를 대조한다.

검증 계약

  • 허용된 역할은 자기 범위 안에서만 각 행동을 한다.
  • 각 주체·행동·범위 조합을 권한 행렬과 대조한다. 분명히 허용된 조합만 성공하고, 정의되지 않은 역할·행동과 범위를 벗어난 요청은 거부된다. 허용되지 않은 요청은 데이터를 바꾸지 않는다.
  • tenant가 서로 다르면 목록·상세·count·첨부 다운로드·집계 결과가 섞이지 않는다.
  • 객체 ID와 tenant ID를 바꾼 요청은 거부되거나 안전하게 중단된다.
  • 다른 tenant의 객체·관계 ID를 생성·수정·삭제 요청에 넣거나 export와 OR 필터를 요청해도, 정보가 드러나지 않고 데이터도 바뀌지 않는다.
  • 기존 세션·캐시가 남은 상태와 권한 철회 전에 등록한 background job으로 시험한다. 정한 적용 시점 이후에는 접근과 재시도가 막힌다. 철회할 때 이미 실행 중인 작업은 정한 경계에서 멈추거나 끝나고, 그 뒤 보호된 동작을 새로 하지 않는다.
  • 권한 저장소 장애나 membership 조회 실패를 주입하면 요청이 거부된다.
  • 권한을 검사한 뒤 쓰기 전에 소유권이나 권한을 바꾸면, 그 쓰기는 거부되거나 바뀐 조건으로 다시 판단된다.

조건부 기술스택 프로필

DB 기반 permission table, JWT claim, Spring Security authorization, Rust extractor는 구현 선택지다. 구체적인 역할 이름, claim 이름, legacy tenant의 NULL 처리 방식은 프로젝트마다 정하는 설정이며, 다른 프로젝트의 규칙으로 옮기지 않는다.

출처와 제한

이 패턴은 이전 프로젝트들의 구현 경험에서 나왔다. 기준은 반드시 지킬 조건과 검증 계약이다. 특정 구현의 코드를 그대로 가져다 쓰지 않고, 참고한 구현도 이 문서의 검증 계약을 통과해야 쓴다.
