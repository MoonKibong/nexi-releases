배포와 장애 대응

읽기 안내 — 누가: PM, 운영 권한을 가진 사람, 보안·데이터 담당자 · 언제: 수용된 작업을 운영 환경에 내보내거나 데이터를 옮길 때, 보안·데이터 사고 신호가 나왔을 때 · 읽은 뒤: 배포 전에 갖출 것을 확인하고, 사고가 나면 멈추고 넘긴다.

작업을 수용했다고 배포해도 된다는 뜻은 아니다. 배포와 운영 환경 변경은 운영 권한을 가진 사람이 따로 정한다 (사람과 AI가 정하는 것).

배포하거나 데이터를 옮길 때

검사를 통과했다는 것만으로 운영 환경을 바꾸지 않는다. 다음이 모두 있어야 한다.

  • 승인된 변경 시간대와 배포 담당자
  • 백업과 복원이 되는 증거
  • 모니터링과 알림
  • 되돌릴 조건과 되돌리는 순서
  • 고객의 승인
  • 배포 뒤에 무엇을 얼마 동안 지켜볼지

일부만 반영되거나 두 시스템의 데이터를 맞춰 본 결과가 다르면 배포를 멈추고 변경 담당자에게 넘긴다. 데이터를 옮길 때 비교하고 맞춰 보는 법은 레거시 저장소에서 시작하기를 따른다.

배포할 commit

배포는 승인한 최종 보고를 main에 넣은 commit에서 한다. main의 가장 새 commit에는 보고서가 검증하지 않은 변경이 있을 수 있다. 그 commit은 docs/FINAL.md를 바꾼 가장 새 commit이다(혼자 모드는 보고서 commit, 팀 모드는 최종 보고 PR의 병합 commit). 그 부모는 보고서에 적힌, 검증한 main commit이다. PM이 이 commit에 태그를 단다. 태그 이름의 <T12>는 검증한 main commit의 앞 12자다.

git fetch origin
C=$(git log -1 --format=%H origin/main -- docs/FINAL.md)
git show -s --format=%P "$C"
git tag nexi-final-<T12> "$C"
git push origin nexi-final-<T12>
git ls-remote --tags origin nexi-final-<T12>

git show 명령이 보이는 부모 해시가 보고서에 적힌 검증한 commit과 다르면 태그를 달지 않고 멈춘다. 마지막 명령이 $C의 전체 해시를 보이면 끝이다. 같은 이름의 태그가 이미 있으면 지우거나 덮어쓰지 않고, 그 태그가 가리키는 commit을 PM이 확인한다. 배포 담당자는 이 태그를 배포한다.

이미 배포된 작업을 바꿀 때는 변경 작업을 만든다. 그 작업 계약서에 배포 뒤의 확인과 되돌리는 방법을 넣는다.

보안·데이터 사고나 되돌릴 수 없는 작업이 보일 때

비밀 값이 드러났거나, 허가 없이 데이터에 접근했거나, 지우거나 덮어쓰는 명령처럼 되돌리기 어려운 일이 보이면 이렇게 한다.

  1. agent 실행과 밖으로 쓰는 일을 바로 멈춘다. 로그와 작업 트리는 그대로 두되, 비밀 값과 고객 데이터를 새 문서에 옮겨 적지 않는다.
  2. 보안·데이터 담당자에게 넘긴다. 작업 번호, 시각, 권한, 영향이 미칠 수 있는 범위, 이미 한 조치를 이슈나 정한 경로로 알린다.
  3. 접근 권한 회수, 비밀 값 교체, 통지, 증거 보존은 고객의 사고 대응 절차와 권한을 따른다. 개발 팀이 혼자 정하지 않는다.
  4. 원인을 짐작한 것만으로는 다시 시작하지 않는다. 승인된 차단 조치와 안전하게 다시 시작할 기준이 있어야 한다.
