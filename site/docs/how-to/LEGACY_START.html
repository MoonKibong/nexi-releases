레거시 코드가 있는 저장소에서 시작하기

읽기 안내 — 누가: FDE와 PM · 언제: 이미 코드가 있는 저장소를 고치거나, 예전 시스템을 새 기술로 옮길 때 · 읽은 뒤: 아래 순서대로 저장소를 준비하고 백로그까지 만든 뒤 작업 순환으로 간다.

빈 폴더에서 시작할 때와 세 가지가 다르다.

  • 고치기 전에 지금 코드가 실제로 설치되고 돌아가는지 먼저 확인한다.
  • /nexi-init은 이미 있는 파일을 건드리지 않는다. 기존 AGENTS.md가 있으면 NEXI에 필요한 줄을 따로 채워야 한다.
  • 기능보다 먼저, 바꿀 코드의 지금 동작을 지키는 검사를 만든다.

시작하기 전에 착수 합의가 끝나 있어야 한다. 특히 검토자(코드베이스 소유자)와 주당 리뷰 시간, 저장소와 실행 환경에 들어갈 권한, 고칠 범위, AI가 명령을 실행해도 되는 환경, 운영 환경과 고객 데이터를 어디까지 다룰지가 정해져 있어야 한다. 하나라도 없으면 시작하지 않는다. 키트 설치는 준비와 같다.

1. 혼자로 할지 팀으로 할지 정한다

저장소 고를 것
한 사람이 일하고, main에 직접 push할 수 있다 혼자: /nexi-init <프로젝트 이름>
여러 사람이 일하거나, main을 PR로만 바꿀 수 있다 팀: PM을 정하고, PM이 /nexi-init <프로젝트 이름> team을 넣는다

혼자 방식은 요구사항 승인과 작업 병합 때 main에 직접 push한다. main이 PR로만 바뀌는 저장소에서는 막히므로 팀 방식을 쓴다. 팀 방식은 요구사항과 작업을 branch에서 하고 PR로 병합한다. 팀 방식이면 2를 마친 뒤 이미 있는 저장소에 팀 모드 들이기를 함께 따른다. 설정 변경을 넣는 법과, 끝내기가 예전 commit에서 멈추지 않게 하는 기준선 작업이 거기에 있다.

/nexi-init은 main에 키트가 만들지 않은 commit이 있으면 그것을 알리고, 기존 이력을 검토하는 작업을 다른 작업보다 먼저 만들라고 안내한다. 그 작업의 이슈 본문에 검토한 외부 commit 범위: 끝 <B> · 시작 <A> · <개수>개 줄을 넣는다. B는 init 파일을 main에 들인 commit(팀이면 그 PR의 병합 commit)이고, A와 개수는 AI가 알려 주는 명령으로 구하며, AI가 그 줄을 검사한다. 작업 계약서에도 같은 줄을 그대로 넣고 보통의 작업 순환으로 수용한다. 그러면 끝내기가 그 범위의 commit에서 멈추지 않는다.

2. 저장소를 받고 지금 코드를 돌려 본다

git clone <저장소 주소>
cd <저장소 폴더>
claude

Claude Code에 이렇게 넣는다. 아직 아무것도 고치지 않는다.

이 저장소의 README, build 파일, CI 설정에서 설치, build, test 명령을 찾아 적힌 순서대로 돌려라. 코드와 설정은 고치지 마라.
먼저 명령을 돌려도 되는 환경인지 나에게 확인받아라. 어느 부분을 고칠지 정해지지 않았는데 많은 의존성을 설치해야 하면 설치하지 말고 물어라.
기본 branch가 main이고 로컬 main이 GitHub의 main을 따라가는지 먼저 알려 줘. 지금 commit 해시를 적고, 명령마다 실행 시각, 폴더, 종료코드, 걸린 시간을 표로 보여 줘. 실패한 명령은 마지막 출력과 빠진 것(환경 변수, DB,
외부 서비스, 권한)을 적어라.

cucu를 사용하는 경우, rroot를 활용해 다음과 같이 요청한다.

rroot를 이용해 저장소 전체의 구조를 분석하고 README, build 파일, CI 설정 등을 조사해서 설치, build, test 명령을 찾아 적힌 순서대로 돌려라. 코드와 설정은 고치지 마라.
명령을 돌려도 되는 환경인지 먼저 확인받아라. 기본 branch가 main인지 확인하고 지금 commit 해시를 적어 줘. 실행 결과(시각, 폴더, 종료코드, 소요시간)를 표로 정리하고, 실패 시 원인(환경 변수, DB, 권한 등)을 명시해라.

표를 보고 다음 중 하나를 고른다.

결과 할 일
모두 통과했다 3으로 간다
환경 변수, DB, 외부 서비스, 권한이 없어서 실패했다 빠진 것을 고객에게 요청하고, 받으면 2를 다시 한다. 받을 수 없으면 무엇이 없는지 적고 3으로 간다
코드 결함으로 실패했다 고치지 않는다. 어떤 결함인지 적고 3으로 간다
원인을 가리지 못했다 로그와 질문, 조사할 사람을 적는다. 그 사람의 답을 받은 뒤 2를 다시 하거나 3으로 간다
기본 branch가 main이 아니다(예: master, develop) NEXI 키트는 main을 쓴다. 저장소 소유자와 main을 어떻게 준비할지(이름 바꾸기, 새로 만들기) 정한 뒤 2를 다시 한다
명령을 찾지 못했다 고객의 개발자에게 실행 방법을 묻는다. 답을 받으면 2를 다시 한다

다른 절차나 다른 agent(예: CuCu)로 개발하던 저장소에 중간부터 NEXI를 쓰면, /nexi-init 전에 키트와 겹치는 것을 확인한다. Claude Code에 이렇게 넣는다.

이 저장소에서 NEXI 키트와 겹칠 수 있는 것을 찾아 표로 보여 줘. 아무것도 고치거나 닫지 마라.
1. docs/requirements/, docs/contracts/, docs/evidence/, docs/reviews/, docs/design/, docs/screens/, docs/FINAL.md에 이미 있는 파일
2. 라벨 task가 붙은 GitHub 이슈(열린 것과 닫힌 것)
3. 병합되지 않은 branch와 열린 PR. 이름이 t와 숫자이거나 req인 branch는 따로 표시해라
4. AGENTS.md와 CLAUDE.md 말고 다른 agent의 규칙 파일(예: CuCu, Cursor, Copilot 설정)

표를 보고 항목마다 정한다. 맞는 것은 살린다. 한꺼번에 닫거나 이름을 바꾸지 않는다.

항목 겹치면 생기는 일 정할 것 정하는 사람
겹치는 문서 경로 NEXI skill은 이 경로에 정해진 형식의 파일을 쓰고 읽는다. 같은 이름의 다른 파일이 있으면 skill이 그 파일을 고치거나 NEXI 문서로 읽는다 겹치는 파일만 다른 경로로 옮길지 FDE와 검토자
라벨 task가 붙은 이슈 /nexi-backlog는 이 라벨의 이슈를 이미 만든 작업으로 보고 같은 작업을 만들지 않는다. next는 선행 작업: 줄이 있고 그 선행 작업이 모두 수용된 열린 이슈 가운데 번호가 가장 작은 것을 다음 작업으로 고른다. 이 라벨의 열린 이슈가 하나라도 남아 있으면 끝내기가 멈춘다 이슈마다 NEXI 작업으로 살릴지(선행 작업: 줄을 더한다), 라벨을 바꿀지, 닫을지 PM(혼자면 FDE)과 검토자
병합되지 않은 branch와 열린 PR 진행 중인 변경이 NEXI 작업과 같은 코드를 고칠 수 있다. 팀 방식은 branch t<N>과 req를 쓰므로 같은 이름이 있으면 섞인다 먼저 끝낼지, 멈출지, NEXI 작업으로 옮길지 검토자
다른 agent의 규칙 파일 같은 저장소에 절차가 두 벌 생긴다 4에서 AGENTS.md와 함께 맞춘다. 부딪히는 규칙은 어느 쪽을 따를지 사람이 정한다 FDE와 검토자

정한 내용은 3에서 만드는 요청 파일의 수행사 실행 기록에 적는다.

3. 요청 파일을 만들고 /nexi-init을 넣는다

요청 파일은 저장소 밖에 만든다. 저장소 안에 두면 commit하지 않은 파일로 남아 다음 skill을 멈추게 할 수 있다. 파일은 두 부분으로 나눈다.

  • 고객 요청 원문: 이번에 바꿀 내용으로 고객이 준 글을 그대로 붙인다.
  • 수행사 실행 기록: 2에서 돌린 명령의 실제 결과 표와 아직 풀지 못한 문제.

1에서 고른 방식으로 /nexi-init을 넣는다. 팀이면 이름 뒤에 team을 붙인다.

/nexi-init <프로젝트 이름>
요구사항 원문:
<저장소 밖 요청 파일의 경로>

AI가 만든 파일과, 이미 있어서 건드리지 않은 파일을 목록으로 보여 준다. commit 이력이 있는 저장소라서 새로 만든 파일도 commit하지 않는다.

4. 기존 파일을 맞추고 main에 넣는다

AGENTS.md나 CLAUDE.md가 "이미 있음"으로 나왔으면 이렇게 넣는다. 다른 skill은 AGENTS.md의 Mode: 줄과, 팀이면 PM: 줄을 읽는다.

기존 AGENTS.md를 nexi-init skill이 AGENTS.md에 쓰는 내용(Mode 줄, 팀이면 PM 줄, 명령, 문서 위치, 작업 규칙, 팀이면 팀 규칙)과 대조해라.
빠진 것만 끝에 더하고, Mode 줄은 하나만 둬라. 기존 규칙과 부딪히는 것이 있으면 바꾸지 말고 어느 규칙을 따를지 나에게 물어라.
CLAUDE.md가 AGENTS.md를 가리키는 링크가 아니면 두 파일의 내용을 보여 주고, 내가 승인하면 AGENTS.md로 합친 뒤 CLAUDE.md를 AGENTS.md를
가리키는 링크로 바꿔라.

Makefile과 README.md는 지금 고치지 않는다. 백로그의 첫 작업(골격)이 맡는다.

그다음 새 파일과 고친 파일을 저장소의 원래 절차대로 main에 넣는다.

초기 설정용 branch를 만들어 nexi-init이 만든 파일과 고친 AGENTS.md, CLAUDE.md를 commit하고 push한 뒤 PR을 만들어라.

고객의 검토자가 PR을 병합하면 이렇게 넣는다.

main으로 돌아와 GitHub의 최신 main을 받아라. commit하지 않은 파일이 남아 있지 않은지 보여 줘.

남은 파일이 없으면 5로 간다.

5. 요구사항을 확정한다

요구사항대로 한다. 분석 결과(REQ-ANALYSIS.md)에서 두 가지를 더 본다.

  • 바뀌는 동작과 그대로 둘 동작이 나뉘어 있는가
  • 지금 동작이 원문과 다르거나 결함으로 보이는 곳이 질문으로 올라와 있는가. 예전 결함을 그대로 둘지 고칠지는 고객이 정한다.
  • 로컬에 설치할 수 없거나 바꿀 수 없는 구성 요소(원격 API, 개발계나 테스트계 서버, 다른 팀의 DB)가 외부 시스템으로 적혀 있는가. 고칠 것이 프론트엔드나 서비스 일부뿐이면 나머지는 외부 시스템이다. 허용되는 조작과 설정 준비 방법도 결정에 넣고, 그 시스템으로만 확인할 수 있는 수용 기준은 그 시스템에서 확인한다.

6. 확인 방법을 정하고 백로그를 만든다

먼저 FDE와 검토자가 바꿀 동작마다 무엇을 넣고 무엇을 확인할지 정한다. 이미 그 동작을 실제로 실행하는 검사가 있으면 그것을 쓴다.

바꿀 동작 확인 방법
계산 규칙 경계값을 포함한 단위 검사
DB, API, 큐처럼 바깥과 연결된다 실제 연결이나 승인된 시험용 데이터(fixture)를 쓰는 통합 검사
예전 시스템을 새 시스템으로 옮긴다 같은 입력으로 예전과 새 결과를 비교하는 명령
화면 흐름 승인된 시나리오와 사람이 볼 기준
확인할 방법이 없다 그 방법을 만드는 작업을 그 기능의 선행 작업으로 둔다

그다음 백로그의 /nexi-backlog에 다음 메모를 붙인다.

/nexi-backlog
레거시 저장소다. 첫 골격 작업은 기존 앱 구조를 그대로 두고, 실행 환경과 기존 설치·build·test 명령을 make build, make test, make lint로
묶고 README에 순서를 적는 작업으로 만들어라.
요청 파일의 실행 기록에 있는 환경 문제나 코드 결함 때문에 골격의 검사를 통과할 수 없거나 하루를 넘을 것 같으면, 이슈를 만들기 전에
골격의 범위와 나누는 방법을 나에게 물어라.
둘째 코드 표준 작업에서는 이 작업 전의 코드를 적용 범위에서 빼는 방법(경로 목록이나 기준 commit)을 정하게 하고, 새 코드의 규칙은
지금 코드의 관례를 참고하되 요구사항과 적용 패턴에 맞게 정하게 해라.
기능 작업마다, 그 코드의 지금 동작을 지키는 회귀 검사를 만드는 작업을 따로 두고 기능 작업의 선행 작업으로 적어라.

결과에서 다음을 본다.

  • 첫 작업이 골격(기존 명령을 묶고 실행 환경을 갖추기)인가
  • 둘째 작업이 코드 표준이고, 기존 코드를 적용 범위에서 빼는가
  • 기능 작업마다 그 동작을 지키는 검사 작업이 선행 작업으로 적혀 있는가
  • 첫 기능 작업은 반나절에서 하루 안에 끝나고, 되돌릴 수 있고, 동작 하나만 바꾸는가. 여러 모듈을 한꺼번에 바꾸는 리팩터링, 고객 데이터 변경, 운영 배포, 되돌릴 수 없는 DB 변경은 첫 작업으로 두지 않는다

그다음은 작업 순환과 같다. 작업 계약서를 승인할 때, 검사가 바꿀 코드를 실제로 실행하는지 한 번 더 본다. 실행하지 않는 검사는 끝냈다는 근거가 되지 못한다. 검사가 갖출 조건은 검증 명령 규약에 있다.

예전 시스템을 옮길 때

데이터의 원본, 스키마, API, 데이터 모양, 쓰는 경로, 운영 책임 가운데 하나라도 바뀌면 5와 6에서 다음을 더한다.

  1. 무엇이 같아야 하는지 고객과 정해 요구사항 결정 문서에 적는다. 값, 정렬, 건수, null과 기본값, 반올림과 시간대, 성능, 예전부터 있던 결함을 어떻게 할지.
  2. 예전 시스템을 비교 기준으로 쓴다. 비교하면서 예전 시스템에 데이터를 쓰지 않고, 같은 입력의 결과를 비교한다. 또는 승인된 스냅샷을 쓴다. 이 비교 명령을 만드는 작업을 기능 작업의 선행 작업으로 둔다.
  3. 객체, 테이블, 모듈을 한 조각씩 옮긴다. 조각마다 두 시스템의 데이터를 맞춰 보는 쿼리와 허용할 오차를 작업 계약서에 적는다.
  4. 데이터를 옮겨 쓰는 작업은 여러 번 실행해도 결과가 같아야 한다(멱등성). 그리고 백업과 복원이 되는 증거, 전환 시간대, 모니터링, 되돌릴 조건, 승인할 사람을 둔다. 운영 반영은 배포와 장애 대응을 따른다.
  5. 예전과 새 시스템에 함께 쓰는 방식(dual-write)은 쓰는 순서, 일부만 실패했을 때, 다시 처리할 때, 데이터가 충돌할 때를 누가 맡을지 정해졌을 때만 쓴다.
  6. 복구와 되돌리기를 실제로 연습하고, 전환 뒤 모니터링을 맡을 사람을 정한다.
  7. 예전과 다르게 동작하게 할 부분은 고객의 승인을 받고 수용 기준에 적는다.

중요한 아키텍처 선택은 결정 기록(ADR 양식)으로 남긴다. 배경, 선택지, 결정한 사람, 영향, 확인 방법, 되돌릴 조건을 적는다. 범위가 정해지기 전에 아키텍처를 약속하지 않는다. Java와 Spring Boot면 실행 프로필의 확인표를 채운다. 여러 팀이 같은 업무 개념을 다르게 다루거나 여러 시스템의 식별자가 어긋날 때만 온톨로지를 검토한다.

저장소를 어떻게 둘지

예전 시스템을 새 기술 스택으로 옮길 때는 저장소를 어떻게 둘지 착수 합의에서 정한다. FDE와 검토자가 의견을 내고 고객 결정권자가 정한다. 두 방식이 있다.

방식 이렇게 한다 맞는 경우 더 할 것
새 저장소 새 시스템은 빈 폴더에서 시작하기대로 만든다. 예전 저장소는 고치지 않고 옆에 받아 두고 비교에만 쓴다 예전 시스템을 따로 유지보수하는 사람이 있다. 새 시스템의 구조가 크게 다르다 요청 파일과 AGENTS.md에 예전 저장소의 주소와 비교 기준을 적는다
같은 저장소 새 앱을 기존 코드 옆의 새 폴더(예: app-new/)에 만든다. 이 문서의 1~6을 따른다 고객이 저장소 하나를 원한다. 예전과 새 코드를 함께 build하거나 배포한다 예전 코드를 고치지 않는 작업이면 작업 계약서의 하지 않을 일에 적는다

어느 방식이든 비교 기준을 고정한다. 예전 시스템의 commit 해시나 스냅샷을 고객 결정권자가 승인하고, 비교 명령은 그 기준으로 돌린다. 예전 시스템이 그 뒤에 바뀌어도 기준은 그대로 둔다. 기준을 바꾸려면 고객이 승인한다. 고른 방식과 비교 기준은 착수 합의 기록에 적는다.

예전 코드를 legacy/ 같은 폴더로 옮겨 얼리는 방식은 기본으로 쓰지 않는다. 경로가 바뀌어 예전 build, 설정, 링크가 깨질 수 있다. 비교 기준은 앞에서 정한 commit 해시나 스냅샷으로 이미 고정된다.

막혔을 때

증상 먼저 할 일 그다음
build나 test가 안 된다 요청 파일의 실행 기록에 명령, 로그, 빠진 것을 적는다 고객에게 요청한다. 골격 작업에서 풀 수 있는지 정한다
무엇을 구현할지 모르겠다 원문과 질문을 나눠 적는다 업무를 아는 사람과 결정권자에게 묻는다(요구사항)
검사가 바꿀 코드를 실행하지 않는다 기능 구현을 멈춘다 그 코드를 실행하는 검사를 만드는 작업을 먼저 한다
새 요구가 들어왔다 지금 작업 계약서에 덧붙이지 않는다 다른 일과 맞바꿀지, 다음 작업으로 둘지 정한다
어느 코드를 고칠지 모르는데 AI가 의존성을 설치하려 한다 멈추게 한다 고칠 범위를 먼저 정한다. 저장소 전체를 "분석하고 고쳐라"라고 시키지 않는다
