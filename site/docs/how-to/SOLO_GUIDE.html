혼자 진행하기

혼자 진행하기

읽기 안내 — 누가: 혼자 프로젝트를 맡는 사람 · 언제: 요구사항을 받아 새 프로젝트를 시작할 때 · 읽은 뒤: 요구사항 승인부터 작업 반복, 최종 확인까지 진행한다.

혼자는 한 사람이 PM·FDE·개발자 역할을 맡는다. 구현을 리뷰하는 agent는 구현한 agent와 달라야 한다. 작업의 변경은 로컬 main에 두고, APPROVE 뒤 nexi-merge가 commit하고 push한다.

단계별 프롬프트와 연습용 요구사항은 혼자 CRM 만들어 보기에 있다.

준비

키트 배포 상태를 먼저 본다. 공개 다운로드가 준비되지 않았으면 키트를 받은 뒤 진행한다. 설치와 계정 준비는 준비, 버전·환경 확인은 공통 규칙을 따른다.

준비물은 요구사항 원문, GitHub 계정, 구현과 리뷰에 쓸 agent다. 고객 프로젝트면 먼저 착수 합의를 마친다. 코드가 있는 저장소면 기존 저장소에서 시작하기를 따른다.

1. 새 저장소를 시작한다

본인이 빈 프로젝트 폴더에서 Claude Code를 열고 넣는다.

/nexi-init <프로젝트 이름>
요구사항 원문:
<고객이 준 글 또는 저장소 밖 파일 경로>

결과의 비공개 GitHub 저장소를 연다. AGENTS.md의 Mode: solo와 docs/requirements/REQUEST.md의 원문을 본다. 다르거나 빠진 것이 있으면 다음 단계로 가지 않고 agent에게 알린다. 상세는 프로젝트 시작에 있다.

연습용 원문이 필요하면 아래처럼 작은 요구로 시작한다. 고객 요청으로 쓰려면 고객이 범위를 정해야 한다.

개인용 할 일 목록을 만든다. 제목을 넣어 할 일을 만들고 완료로 바꾼다.
전체와 미완료 목록을 볼 수 있다. 새로 열어도 저장한 내용이 남는다.
실제 고객 데이터와 외부 서비스는 쓰지 않는다. 스택과 화면, 저장 위치는 질문으로 정한다.

2. 요구사항을 승인한다

본인이 다음 프롬프트를 하나씩 넣는다. 앞 단계의 결과를 읽은 뒤 다음 것을 넣는다.

프롬프트 확인할 결과
/nexi-requirements analyze 원문의 범위와 질문이 분석에 있고, 빠진 결정이 질문으로 남는다.
/nexi-requirements answers 고객 답을 넣는다. 연습이면 제안된 답을 읽고 고친 뒤 저장하도록 답한다.
/nexi-requirements decide REQ-CONTEXT의 범위, 기술 스택, 검증 방법과 수행사 결정을 읽는다.
/nexi-requirements approve 다음 줄에 받아들이지 않는 수행사 결정: <번호 또는 없음>을 넣는다. 보여 준 파일을 읽고 맞으면 승인한다고 답한다.

REQ-CONTEXT.md가 상태: 승인이고 원격 main에 들어간 뒤 진행한다. 구현을 막는 질문이 남으면 답과 결정을 먼저 정한다. 상세는 요구사항에 있다.

3. 작업 목록을 만든다

본인이 /nexi-backlog를 넣는다. 결과 표에서 골격, 코드 표준, 화면이 있으면 디자인 시스템, 기능 순서인지 본다. 각 작업은 하루 안에 끝나는 크기이고 실제로 필요한 작업만 선행 작업:에 있어야 한다. 크거나 의존 관계가 틀리면 작업을 고르기 전에 고치도록 요청한다. 상세는 백로그에 있다.

4. 작업 하나를 끝낸다

<N>은 /nexi-backlog next가 고른 실제 이슈 번호로 바꾼다. 아래 순환은 작업마다 반복한다.

차례 넣는 프롬프트 다음으로 갈 조건
고르기 /nexi-backlog next 선행 작업이 수용된 이슈가 선택된다.
계약서 /nexi-contract <N> 산출물, 수용 기준과 검사, 하지 않을 일을 읽는다.
화면 기준 디자인 시스템·디자인 변경 작업이면 /nexi-design <N> BRIEF의 화면과 상태를 읽는다.
승인 /nexi-contract <N> approve 보여 준 계약서를 승인한다. BRIEF도 승인하려면 그 내용도 명시적으로 승인한다.
구현 /nexi-implement <N> 마지막 변경 뒤 검사 결과와 증거, 화면 작업의 PNG가 남는다.
독립 리뷰 다른 agent에서 nexi-review skill로 T#<N>을 리뷰해라. 현재 변경과 증거를 읽은 판정이 나온다. 리뷰는 읽기 전용이다.
기록 구현 대화에서 /nexi-review <N> record와 판정을 붙인다. 판정 기록이 추가된다.
수용 APPROVE면 /nexi-merge <N> 원격 main의 변경이 리뷰한 것과 같고 이슈에 NEXI 수용이 남는다.

REVISE면 기록한 지적을 /nexi-implement <N>으로 고치고 다시 리뷰한다. BLOCK이나 세 번째 연속 REVISE면 공통 규칙의 원인 결정으로 간다. 승인한 범위로 끝낼 수 없으면 계약서를 고치고 다시 승인받는다. 상세는 작업 순환에 있다.

Claude Code에서 구현·리뷰·기록을 이어서 하려면 nexi-run을 선택할 수 있다. APPROVE여도 자동으로 병합하지 않으므로 본인이 판정과 증거를 읽는다.

5. 최종 확인을 한다

열린 작업이 없으면 본인이 /nexi-finish를 넣는다. 새 사본 검사 결과와 docs/FINAL.md의 둘러보기 목록을 읽는다. 준비가 통과해 앱이 뜨면 직접 써 보고 각 행에 실제 결과를 적는다.

  • 결함이 있으면 /nexi-finish reject <결함 내용>으로 작업을 만들고 작업 순환으로 돌아간다.
  • 빈 행과 이상 있음이 없으면 /nexi-finish approve로 보여 준 보고를 승인한다.
  • 실패·미실행 단계가 있으면 고객 결정권자의 수용이 필요하다. 끝내기를 따른다.

승인된 최종 보고 뒤의 변경은 끝난 작업 바꾸기, 운영 반영은 배포와 장애 대응으로 간다.
