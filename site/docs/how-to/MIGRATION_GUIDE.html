새 저장소로 시스템 옮기기

새 저장소로 시스템 옮기기

읽기 안내 — 누가: 전환을 맡은 PM, FDE와 개발자 · 언제: 예전 시스템을 비교 기준으로 두고 새 저장소에 시스템을 만들 때 · 읽은 뒤: 기준을 고정하고, 비교 검사와 전환 작업을 계약서로 나눠 진행한다.

새 시스템은 빈 저장소에서 만들고 예전 시스템은 옆의 별도 폴더에 둔다. 같은 저장소에서 바꾸는 경우와 저장소 선택 기준은 기존 저장소에서 시작하기에 있다. 이 경로로 앱을 끝까지 실행한 기록은 아직 없다.

준비

PM은 착수 합의에서 저장소 방식, 고칠 범위와 운영 책임을 고객 결정권자와 정한다. 비교 기준, 실행을 허용한 환경, 예전 코드를 읽고 실행할 권한과 담당자도 정한다. 실제 고객 데이터 대신 승인된 가짜 데이터나 시험용 스냅샷을 준비한다. 인증 정보는 저장소 밖에서 준비한다.

키트 배포 상태를 먼저 본다. 공개 다운로드가 준비되지 않았으면 키트를 받은 뒤 진행한다. 설치는 준비, 팀 버전 맞추기는 공통 규칙을 따른다.

1. 비교 기준을 받을 수 있는지 확인한다

PM 또는 혼자 맡은 사람이 고객 결정권자가 승인한 저장소 주소와 전체 commit 해시를 준비한다. 아래 자리표시자를 그 값으로 바꿔 별도 폴더에 받는다. 기존 작업 폴더에서 checkout하지 않는다.

git clone <권한이 있는 예전 저장소 주소> legacy-reference
cd legacy-reference
git fetch origin
git branch -r --contains <승인한 전체 commit 해시>

출력에 원격 branch가 없으면 진행하지 않는다. 소유자에게 다른 사람도 받을 수 있는 기준 commit을 요청한다. 받을 수 있는 기준이면 그 새 폴더에서 다음을 실행한다.

git checkout --detach <승인한 전체 commit 해시>
git rev-parse HEAD

출력이 승인한 전체 해시와 같아야 한다. 예전 시스템이 나중에 바뀌어도 이 기준은 그대로 두고, 바꾸려면 고객이 다시 승인한다.

2. 예전 시스템의 실행 결과를 남긴다

PM 또는 혼자 맡은 사람이 예전 시스템 폴더의 agent에 넣는다.

README, build 파일과 CI에서 설치·build·test 명령을 찾아라. 코드와 설정은 고치지 마라.
명령이 닿는 데이터와 서비스를 먼저 보여 주고, 내가 허용한 환경에서만 실행해라.
지금 commit과 명령별 실행 시각, 폴더, 종료코드, 걸린 시간을 표로 남겨라.
실패하면 마지막 출력과 빠진 환경·권한을 적고, 통과하도록 코드를 바꾸지 마라.

사람이 실행할 환경을 허용한 뒤 결과를 읽는다. 실패와 미실행은 그대로 요청 파일에 남긴다. 기준 폴더에 추적 파일 변경이 생겼으면 다음 단계로 가지 않고 변경 목록을 소유자와 검토한다. 예전 시스템에 대한 쓰기는 비교 절차에 넣지 않는다.

3. 요청 파일과 새 저장소를 만든다

PM 또는 혼자 맡은 사람이 저장소 밖 요청 파일을 만든다. 고객 요청 원문과 수행사 실행 기록을 나눈다. 실행 기록에는 기준 저장소·해시·폴더, 실행 결과와 빠진 환경, 예전 시스템을 고치지 않는다는 범위를 적는다. 새 저장소에 남겨도 되는 주소와 기록만 넣는다. 비밀 주소나 인증 정보가 필요하면 저장소 밖 설정으로 준비하는 방법을 적는다.

예전 시스템 폴더 옆의 새 빈 폴더에서 시작한다. 혼자는 첫 줄의 team을 뺀다.

/nexi-init <새 프로젝트 이름> team
요구사항 원문:
<저장소 밖 요청 파일 경로>

저장소와 모드가 맞으면 혼자 진행하기 또는 팀으로 진행하기의 요구사항 단계로 간다.

4. 같아야 할 것과 달라도 되는 것을 정한다

FDE는 /nexi-requirements analyze, 답을 받은 뒤 answers와 decide로 비교 조건을 결정 문서에 올린다. PM 또는 혼자 맡은 사람은 approve에서 다음 항목을 읽고 승인한다.

결정 정할 내용
동등성 값, 건수, 정렬, null·기본값, 반올림, 시간대, 오류와 성능의 비교 기준·허용 오차.
의도한 차이 예전 결함을 유지할지 고칠지, 새 요구 때문에 달라질 결과와 고객 승인.
데이터 가짜 데이터·스냅샷의 출처, 준비·삭제 방법, 격리된 DB와 서비스, 허용되는 조작.
전환 옮길 조각, 반복 실행, 백업·복원, 모니터링, 되돌릴 조건과 승인할 사람.
외부 시스템 이 프로젝트가 고치지 않는 API·DB·서비스의 주소 준비 방법, 담당자와 검증 환경.

정해지지 않은 조건은 질문으로 남긴다. 자세한 전환 조건은 예전 시스템을 옮길 때를 따른다.

5. 비교 검사를 먼저 작업으로 만든다

PM 또는 혼자 맡은 사람이 /nexi-backlog 다음 줄에 승인된 전환 범위를 넣는다.

승인된 비교 기준과 예전 시스템 폴더를 읽기만 해서 확인하는 명령을 골격 작업에 넣어라.
같은 시험 입력으로 예전 결과와 새 결과를 비교하는 명령을 만드는 작업을 기능 작업보다 먼저 둬라.
객체·테이블·모듈 한 조각씩 옮기는 하루 이하 작업으로 나누고 실제 선행 작업을 적어라.
운영 반영은 별도 승인된 범위로 다뤄라. 동등성 비교만으로 배포가 끝났다고 처리하지 마라.

FDE는 작업 계약서에 비교할 입력, 두 결과, 허용 오차와 실제 구현을 실행하는 검증 명령을 적는다. 사람은 검사 대상이 고정된 기준인지, 가짜 데이터와 DB가 격리됐는지 읽고 계약서를 승인한다. 검사 조건은 검증 명령 규약, 데이터 격리는 구현 패턴을 따른다.

6. 조각마다 구현·리뷰·수용한다

담당자는 작업 순환을 따른다. 전환 작업의 증거에는 비교 명령과 결과, 차이와 허용 오차를 남긴다. 원래 있던 동작은 구현 전·후 회귀 검사로 지킨다. 비교가 실패하면 원인과 의도한 차이를 고객 결정과 대조한다. 계약서의 기준을 바꿔야 하면 구현을 멈추고 다시 쓰고 승인받는다.

운영 데이터에 쓰는 작업이면 반복 실행의 멱등성, 백업·복원과 되돌리기를 실제로 검증할 작업을 둔다. 실행 환경과 승인 조건은 배포와 장애 대응을 따른다.

7. 최종 확인과 운영 전환을 구분한다

열린 작업이 없으면 PM 또는 혼자 맡은 사람이 /nexi-finish로 새 사본 검사를 하고 최종 보고를 검토한다. 사람이 앱을 써 본 결과와 실패·미실행을 채운 뒤 approve 또는 reject를 고른다. 상세는 끝내기에 있다.

비교 검사 통과와 최종 보고 승인은 운영 전환의 완료를 뜻하지 않는다. 운영 반영은 승인한 전환 시간대와 담당자, 되돌릴 조건에 따라 실행하고 실제 결과를 남긴다.
