팀으로 진행하기

읽기 안내 — 누가: PM, FDE, 개발자와 검토자 · 언제: 여러 사람이 같은 프로젝트를 역할을 나눠 진행할 때 · 읽은 뒤: 자기 차례를 수행하고 원격 기록으로 다음 사람에게 넘긴다.

팀은 GitHub 저장소 하나를 각자의 폴더에 받아 쓴다. 작업마다 t<N> branch를 쓰고 PM이 PR을 병합한다. 역할과 branch의 상세 규칙은 개념 참조와 팀으로 일하기에 있다.

단계별 프롬프트와 연습용 요구사항은 다섯 명이 CRM 만들어 보기에 있다.

준비

PM은 착수 합의에서 범위와 검토할 사람, 접근 권한과 실행 환경을 정한다. 팀원은 키트 배포 상태를 보고 같은 키트를 준비한다. 공개 다운로드가 준비되지 않았으면 키트를 받은 뒤 진행한다. 설치는 준비를 따른다. 키트 버전과 ZIP의 SHA-256이 다르면 먼저 공통 규칙대로 맞춘다.

PM은 역할마다 맡을 사람의 GitHub 아이디를 정한다. 한 사람이 역할을 겸해도 리뷰는 구현하지 않은 사람이 맡는다. 기존 이력이 있는 저장소는 이미 있는 저장소에 팀 모드 들이기를 먼저 따른다.

1. PM이 저장소를 만든다

PM은 빈 폴더에서 넣는다.

/nexi-init <프로젝트 이름> team
요구사항 원문:
<고객이 준 글 또는 저장소 밖 파일 경로>

PM은 agent가 보여 준 팀원 표를 읽고 빠진 사람이 없는지 답한다. 결과의 AGENTS.md에 Mode: team, PM의 GitHub 아이디를 담은 PM: 줄과 팀원 표가 있어야 한다. 팀원은 초대를 받아 자기 컴퓨터에 clone하고 그 폴더에서 agent를 연다. 상세와 로그인 문제는 프로젝트 시작을 따른다.

2. 요구사항을 함께 확정한다

요구사항 단계는 branch req에서 한다. 각 단계가 끝나면 실행한 사람이 결과와 commit 해시를 다음 사람에게 알린다.

차례 실행하는 사람 프롬프트 넘길 결과
분석 FDE /nexi-requirements analyze 분석과 질문 → PM
답 PM /nexi-requirements answers 고객 답 또는 검토해 저장한 제안 → FDE
결정 FDE /nexi-requirements decide REQ-CONTEXT 초안과 req 해시 → PM
승인 PM /nexi-requirements approve 받아들이지 않을 결정 번호 또는 없음을 넣고, 보여 준 파일을 읽어 승인한다.

PM은 승인된 요구사항이 PR로 원격 main에 들어간 결과를 모두에게 알린다. 막는 질문이 있으면 승인하지 않고 답과 결정을 다시 정한다. 상세는 요구사항에 있다.

3. PM이 백로그와 담당을 정한다

PM이 /nexi-backlog를 넣는다. 골격, 코드 표준, 화면이 있으면 디자인 시스템, 기능 순서와 실제 선행 관계를 읽는다. PM은 작업마다 담당 FDE 한 명을 정한다. 역할·모듈별로 나눌 때의 기준은 여러 FDE가 나눠 맡기를 따른다. 담당을 바꿀 때는 /nexi-backlog assign <N> <아이디>를 쓴다.

4. 작업마다 차례를 넘긴다

<N>은 실제 작업 이슈 번호다. 한 작업 branch는 한 번에 한 사람만 다룬다.

누가 프롬프트 다음 사람과 원격 기록
담당 FDE /nexi-backlog next, /nexi-contract <N> t<N>의 계약서 초안. 디자인 작업이면 /nexi-design <N>도 쓴 뒤 PM에게 넘긴다.
PM /nexi-contract <N> approve 계약서와 필요한 BRIEF를 읽고 명시적으로 승인. 이슈의 개발자 차례를 본다.
개발자 /nexi-implement <N> 코드·증거·PNG를 push하고 PR을 연다. 이슈에 리뷰 차례와 head가 남는다.
검토자 /nexi-review <N> prepare 준비된 commit을 다른 agent가 읽기 전용으로 리뷰한다. 자동 기록 또는 수동 record를 고른다.
검토자 수동이면 /nexi-review <N> record와 판정 판정을 그대로 기록한다. APPROVE는 PM, REVISE는 개발자, BLOCK은 PM에게 넘긴다.
PM APPROVE면 /nexi-merge <N> 리뷰한 base와 변경 그대로 squash 병합한다. 원격 수용을 확인하고 이슈를 닫는다.

개발자가 nexi-run으로 판정까지 기록했으면, 개발자가 아닌 검토자가 /nexi-review <N> confirm으로 근거를 읽고 PM에게 넘긴다. 리뷰 지적과 반복 중단은 작업 순환을 따른다.

5. main이 움직였을 때 차례를 다시 본다

PM이 병합하면 다른 리뷰 대기·승인 작업이 새 main을 반영하고 다시 리뷰를 받아야 할 수 있다. nexi-merge가 자동 반영한 작업은 이슈에 main 반영 — 리뷰 차례를 남긴다. 검토자가 새 head를 리뷰한다. main 이동 — 개발자 구현 차례가 남으면 개발자가 /nexi-implement <N>으로 이어 간다.

누가 다음인지 불분명하면 /nexi-backlog status를 넣는다. 이 명령은 저장소와 이슈를 읽어 차례를 보여 주고 바꾸지 않는다. 자동 반영의 중단과 동시 실행은 팀의 충돌·반영 절차를 따른다. 요구사항 자체가 바뀌었으면 계약서를 다시 쓰고 승인받는다.

6. PM이 끝내기를 진행한다

열린 작업이 없으면 PM이 /nexi-finish를 넣는다. 새 사본 검사와 최종 보고 초안을 고객과 읽는다. 사람이 앱을 써 보고 둘러보기 결과를 채운다. 결함이면 PM이 /nexi-finish reject <결함 내용>으로 작업을 만든다. 문제가 없으면 PM이 /nexi-finish approve로 보여 준 보고를 승인한다. 빈 결과·실패·미실행 단계의 처리는 끝내기를 따른다.

최종 보고는 final-<commit> PR로 들어간다. 운영 배포는 배포와 장애 대응, 전달은 인수인계를 따른다.
