이미 있는 저장소에 팀 모드 들이기

읽기 안내 — 누가: PM, 그리고 PM과 함께 저장소를 준비하는 FDE · 언제: commit 이력과 예전 기획 문서가 있는 저장소에서 NEXI 팀 모드를 시작할 때 · 읽은 뒤: 아래 순서대로 설정을 main에 넣고, 기존 이력을 받는 기준선 작업을 기능 작업보다 앞에 둔다.

이미 있는 저장소에는 키트가 만들지 않은 것이 셋 있다. 예전 commit, 예전 문서, 그리고 NEXI 설정을 넣는 변경이다. 이 셋을 정리하지 않으면 agent가 예전 문서를 기준으로 삼거나, 끝내기가 멈춘다. 저장소를 받고 지금 코드를 돌려 보는 일은 레거시 코드가 있는 저장소에서 시작하기 2까지와 같다. 이 글은 그다음, 팀 모드로 정한 저장소에서 할 일이다.

1. 있는 것을 목록으로 만든다

PM이 Claude Code에 이렇게 넣는다.

이 저장소에서 다음을 찾아 표로 보여 줘. 아무것도 고치거나 옮기거나 닫지 마라.
1. 문서: 요구사항, 기획, 설계, 회의록, 예전 계획처럼 사람이 쓴 문서. 경로와 첫 제목, 마지막 commit 날짜
2. docs/requirements/, docs/contracts/, docs/evidence/, docs/reviews/, docs/design/, docs/screens/, docs/FINAL.md에 이미 있는 파일
3. AGENTS.md, CLAUDE.md, 다른 agent의 규칙 파일(예: CuCu, Cursor, Copilot 설정)
4. 라벨 task가 붙은 이슈, 병합되지 않은 branch와 열린 PR. 이름이 t와 숫자, req, final-로 시작하는 branch는 따로 표시해라
5. main의 첫 부모 줄기에 있는 commit 수(git rev-list --first-parent --count origin/main)

표의 항목마다 남길지, 옮길지, 뺄지를 정한다. 2~4의 처리는 레거시 코드가 있는 저장소에서 시작하기의 "다른 방식으로 진행하던 저장소라면" 표를 따른다.

2. 어떤 문서가 무엇의 기준인지 정한다

팀 모드에서 기준이 되는 문서는 아래뿐이다. 예전 문서는 이 가운데 하나에 내용이 옮겨졌을 때만 기준이 된다.

무엇의 기준인가 문서 예전 문서를 쓰는 법
무엇을 만들고 바꾸는가 docs/requirements/REQ-CONTEXT.md(승인된 것) 요구사항 원문(요청 파일)에 붙여 요구사항 분석에 넣는다. 결정은 REQ-CONTEXT에 적는다
작업 하나의 범위와 확인 docs/contracts/T<N>.md(승인된 것) 계약서가 직접 인용한 부분만 쓴다
화면 docs/design/BRIEF.md(승인된 것) 디자인 시스템 작업에서 BRIEF에 옮긴다
agent가 따르는 규칙 AGENTS.md(CLAUDE.md는 이 파일을 가리키는 링크) 다른 agent의 규칙 파일과 부딪히는 규칙은 PM이 하나로 정해 AGENTS.md에 둔다
설치, build, 실행 방법 README.md(골격 작업이 고친 것) 골격 작업의 계약서가 옮길 명령을 정한다
팀 구성원 AGENTS.md의 PM: 줄과 ## 팀 표 정보용이다. 권한은 PM: 줄만 정한다

3. 예전 문서를 agent가 읽는 곳에서 뺀다

agent는 저장소의 파일을 찾아 읽는다. 어느 파일이 기준인지 모르면 예전 문서도 기준으로 읽는다. 팀 모드를 시작한 저장소에서 CuCu가 docs/legacy/의 예전 기획 문서를 읽고, 다른 작업의 PR에서 그 문서를 지운 일이 있었다.

  1. 기준이 아닌 예전 문서는 main에서 뺀다. 지우는 commit은 아래 4의 설정 변경에 함께 넣는다. 지운 문서는 git 이력에 남고, 필요하면 git show <지우기 전 commit>:<경로>로 꺼낸다. 고객이 원본을 따로 보관하기를 원하면 저장소 밖의 정한 곳에 둔다.
  2. 저장소에 꼭 남겨야 하면 한 폴더에 모으고, AGENTS.md에 이렇게 적는다. "<폴더>는 참고 자료다. 요구사항, 작업 계약서, BRIEF가 그 파일을 가리킬 때만 읽는다. 그 폴더의 파일을 고치거나 지우지 않는다." 저장소 전체를 찾는 agent는 이 줄이 있어도 그 폴더를 읽을 수 있다. 그러니 1을 먼저 고른다.

4. 설정 변경을 main에 넣는다

/nexi-init <프로젝트 이름> team을 넣고, 이미 있던 AGENTS.md를 맞추는 일은 레거시 코드가 있는 저장소에서 시작하기의 3과 4를 따른다. 팀 모드에서는 AGENTS.md에 Mode: team, PM: 줄, 팀 규칙, ## 팀 표가 들어가야 한다. 이 변경은 키트의 작업 흐름 밖에서 들어가므로 저장소의 원래 절차(PR과 그 저장소의 검토자)로 넣는다. PM이 Claude Code에 이렇게 넣는다.

nexi-setup branch로 설정 변경을 main에 넣어라. 먼저 지금 상태를 이 순서로 확인하고, 이미 된 단계는 다시 하지 마라.
1. nexi-setup에서 main으로 병합된 PR이 있으면(gh pr list --head nexi-setup --state merged) 아무것도 만들지 말고 그 병합 commit의 전체 해시를 보여 주고 멈춘다. 병합 뒤 branch가 지워졌어도 이것으로 찾는다.
2. 열린 PR이 있으면 그 PR을 쓴다.
3. origin에 nexi-setup branch가 있으면 새로 만들지 말고 그 branch를 이어 쓴다.
4. 로컬에만 nexi-setup branch가 있으면 그 commit을 보여 주고, 설정 변경만 들어 있으면 push한다. 다른 것이 들어 있으면 멈추고 나에게 물어라.
5. 어느 것도 없으면 origin/main에서 nexi-setup branch를 만들어, nexi-init이 만든 파일, 고친 AGENTS.md와 CLAUDE.md, 3에서 정한 문서 정리만 commit하고 push한다.
열린 PR이 없으면 main으로 가는 PR을 연다. branch 이름에 t와 숫자, req, final-을 쓰지 마라. 키트가 쓰는 이름이다.
PR 번호와 head commit의 전체 해시를 보여 줘.

저장소의 검토자가 PR을 병합하면 다시 넣는다.

nexi-setup PR의 병합 commit 전체 해시를 보여 주고, main으로 돌아와 GitHub의 최신 main을 받아라. commit하지 않은 파일이 남아 있지 않은지 보여 줘.

중간에 멈췄으면 같은 프롬프트를 다시 넣는다. branch와 PR이 이미 있으면 이어 쓰므로 결과는 같다. 이 병합 commit의 해시를 아래 6에서 쓴다. PM: 줄이 main에 들어간 뒤부터 승인과 병합 같은 PM만 하는 일이 동작한다.

5. 요구사항과 백로그를 만든다

요구사항과 백로그대로 한다. 백로그 메모는 레거시 코드가 있는 저장소에서 시작하기의 6과 같고, 아래 6의 기준선 작업을 더한다.

6. 기존 이력을 받는 기준선 작업을 둔다

끝내기(/nexi-finish)는 main의 첫 부모 줄기에 있는 commit을 하나씩 본다. 키트가 만든 commit(첫 설정 commit, req PR로 들어간 요구사항, 수용된 작업의 병합, 최종 보고서)이 아니면 멈춘다. 예전 commit과 4의 설정 병합 commit은 키트가 만들지 않았다. 설정 PR도 예외가 아니다. 이런 commit은 수용된 작업이 검토했다고 적은 것만 통과한다. 그 작업의 이슈 본문과, 리뷰를 받은 그 작업 계약서에 같은 줄이 있어야 한다. 줄은 commit 하나를 적는 검토한 외부 commit: <전체 해시>와, 범위를 적는 줄 두 가지다.

검토한 외부 commit 범위: 끝 <B> · 시작 <A> · <개수>개

범위 줄은 git rev-list --first-parent <B>에서 B부터 A까지(둘 다 포함)의 commit을 뜻한다. A가 그 안에 없거나 개수가 다르면 아무것도 풀지 않는다. git의 A..B와 달리 A도 들어간다.

그래서 백로그를 만들 때 기준선 작업을 하나 둔다. 백로그의 첫 작업은 골격 작업, 둘째는 코드 표준 작업이고, 화면이 있는 제품이면 셋째는 디자인 시스템 작업이다. 기준선 작업은 그다음, 기능 작업보다 앞에 둔다. /nexi-backlog 메모에 이렇게 더한다(<설정 병합 commit>은 4에서 받은 전체 해시다).

코드 표준 작업(화면이 있으면 디자인 시스템 작업까지) 다음, 기능 작업보다 앞에 "기존 이력을 기준선으로 받기" 작업을 만들어라. 이 작업은 골격 작업이 만든 것만 쓰므로 선행 작업은 골격 작업이다. 이슈 본문 끝에 아래 명령의 출력 한 줄을 그대로 붙여라.
B=<설정 병합 commit>; A=$(git rev-list --first-parent --max-parents=0 "$B") && C=$(git rev-list --first-parent --count "$B") && [ ${#A} = 40 ] && printf '검토한 외부 commit 범위: 끝 %s · 시작 %s · %s개\n' "$B" "$A" "$C"
이 작업의 산출물은 docs/BASELINE.md 하나다. 그 파일에 "설정 병합 commit: <전체 해시>" 줄, 이슈 본문과 같은 범위 줄, 요청 파일의 실행 기록에 있는 설치·build·test 결과 표, 그리고 "이 commit들의 코드는 고치지 않고 지금 그대로를 시작점으로 받는다"를 적는다. 코드는 고치지 않는다.

기준선 작업은 보통 작업과 같은 순서로 간다. 작업 계약서는 같은 범위 줄을 적고, 그 범위의 commit 전체를 고치지 않고 시작점으로 받는다고 적는다. 새 검사는 범위 줄을 다른 기준과 맞춰 본다. 계약서에 그대로 넣을 수 있는 명령이다(<N>은 이 작업 번호).

f=docs/BASELINE.md; s=$(sed -n 's/^설정 병합 commit: //p' "$f") && l=$(grep '^검토한 외부 commit 범위: ' "$f") &&
p=$(gh pr list --head nexi-setup --state merged --json mergeCommit --jq '.[0].mergeCommit.oid') &&
a=$(git rev-list --first-parent --max-parents=0 "$s") && n=$(git rev-list --first-parent --count "$s") &&
[ ${#s} = 40 ] && [ "$s" = "$p" ] && [ ${#a} = 40 ] && [ "$n" -gt 0 ] &&
[ "$l" = "$(grep '^검토한 외부 commit 범위: ' docs/contracts/T<N>.md)" ] && [ "$l" = "검토한 외부 commit 범위: 끝 $s · 시작 $a · ${n}개" ]

설정 병합 commit은 설정 PR의 병합 commit과 같아야 하고, 범위 줄은 그 commit에서 첫 부모 줄기의 첫 commit까지 전부여야 한다. 파일이 없거나, git이나 gh가 실패하면(예: 설정 병합 commit이 이 폴더에 없다) 실패하고, 쓴 뒤 통과한다. 검토자는 범위가 설정 병합 commit에서 끝나는지 본다. PM이 병합하고 수용하면 그 범위의 commit은 끝내기에서 통과한다.

  • 팀 모드를 시작한 뒤에도 누가 main에 직접 push하거나 키트 밖의 PR을 병합하면, 그 commit은 범위 밖이라 끝내기에서 멈춘다. 그때마다 PM이 같은 방식의 작업을 하나 더 만들어 그 commit을 검토하고, 남길지 되돌릴지 정한다. 한 개면 검토한 외부 commit: 줄로 적는다.
  • 수용한 뒤에 이슈 본문이나 main의 계약서를 고쳐 범위를 넓혀도, 끝내기는 리뷰를 받은 계약서의 줄만 센다.

이럴 때는

  • 설정 PR이 병합되기 전에 백로그를 만들었다. 기준선 작업의 범위가 설정 병합 commit에서 끝나지 않는다. 그 작업이 아직 수용되지 않았으면 PM이 위 명령으로 범위 줄을 다시 만들어 이슈 본문의 줄을 바꾼다(gh issue edit <N> --body-file <파일>). 작업 계약서가 이미 있으면 PM이 그 이슈에 "계약서 수정 요청: 검토한 외부 commit 범위를 이슈 본문의 새 범위 줄로 바꾼다" 댓글을 남긴다. 담당 FDE가 /nexi-contract <N>으로 계약서를 다시 쓰고, PM이 다시 승인한다. 이미 승인된 계약서도 승인 뒤의 수정 요청 댓글이 있으면 다시 쓴다.
  • 끝내기가 "키트를 거치지 않은 commit"으로 멈췄다. 멈춘 목록의 commit마다 위 6과 같은 작업을 만든다. 이미 수용한 작업의 이슈에 줄만 더하지 않는다. 그 작업의 계약서와 리뷰가 그 commit을 본 적이 없기 때문이다.
