백로그

읽기 안내 — 누가: PM(혼자 하면 그 사람) · 언제: 요구사항 결정 문서를 승인한 뒤 · 읽은 뒤: 하루 단위 작업 목록과 작업 사이의 순서를 갖추고 작업 순환으로 간다.

백로그는 GitHub의 작업 이슈(라벨 task) 목록이다. 이슈 하나가 작업 하나(T#<N>)이고, 하루 안에 구현하고 검토할 수 있는 크기다.

예제는 1인 Step 3과 5인 Step 3다.

순서

/nexi-backlog를 넣는다. 우선순위에 대해 할 말이 있으면 다음 줄에 적는다. AI가 이슈를 이 순서로 만든다.

  1. 골격 작업. 정한 버전의 런타임과 도구를 갖추고, 앱의 기본 구조와 make build, make test, make lint를 만든다. 설치부터 실행까지의 순서를 README에 적는다. 늘 첫 작업이다.
  2. 코드 표준 작업. 골격 다음 작업이다. 패키지와 가시성, 기능 사이의 의존 방향, 공용 코드를 두는 곳, 로깅, 문서 주석의 규칙을 docs/engineering/STANDARDS.md에 쓰고, 기계로 확인할 수 있는 규칙은 make lint의 검사로 만든다. 이미 코드가 있는 저장소면 그 코드는 적용 범위에서 뺀다. 이 뒤의 작업은 모두 이 작업에 기댄다.
  3. 디자인 시스템 작업. 화면이 있는 제품이면 셋째 작업이다. 디자인 기준 문서(BRIEF)를 쓰고, 그대로 색과 글꼴 같은 토큰, 화면 틀, 기본 구성 요소, 기준 화면 하나를 만든다. 스크린샷을 찍는 make screenshots도 만든다. 이 뒤의 화면 작업은 스크린샷으로 리뷰받는다.
  4. 기능 작업. 기능마다 하나씩, 앞 작업 위에 쌓이는 순서로 만든다.

이슈마다 요구사항 인용, 건드리는 곳, 끝났다고 볼 기준 한 문장, 선행 작업: 줄이 있다. 선행 작업:은 이 작업보다 먼저 끝나야 하는 작업이다.

결과 표를 보고 확인한다.

  • 골격, 코드 표준, 디자인 시스템, 기능 순서인가. 디자인 시스템과 기능 작업의 선행 작업:에 코드 표준 작업이 있는가
  • 선행 작업이 실제로 필요한가(앞 작업이 만든 코드, 데이터, 화면을 쓰는가)
  • 하루를 넘을 것 같은 이슈가 없는가

팀으로 할 때

백로그는 PM이 만든다. FDE가 여럿이면 AI가 작업마다 누가 맡을지 묻는다. 같은 파일이나 화면을 건드리는 작업은 되도록 한 사람에게 준다. 그래야 다른 FDE의 작업을 기다리는 일이 줄어든다. 나중에 담당을 바꾸려면 /nexi-backlog assign <N> <아이디>를 넣는다.

FDE가 한 명이면 담당을 정하지 않아도 된다. FDE가 다음 작업을 고를 때 자기에게 지정된다.

이럴 때는

  • 하루를 넘을 것 같은 이슈가 있다. AI가 표시한다. 쪼개 달라고 하면 다시 만든다. 작업을 시작한 뒤에 너무 크다는 것을 알았으면 작업 순환의 작업 나누기로 한다.
  • 선행 작업이 서로 꼬리를 물거나 없는 이슈를 가리킨다. 다음 작업을 고를 때 AI가 그 이슈를 고르지 않고 목록으로 보여 준다. 이슈의 선행 작업: 줄을 고친다.
  • 화면이 없는 제품이다. 디자인 시스템 작업을 만들지 않고, 스크린샷 리뷰도 없다.
  • 백로그를 다시 짜고 싶다. /nexi-backlog를 다시 넣는다. 이미 있는 이슈는 그대로 두고 빠진 것만 만든다. 요구사항이 바뀌어서라면 요구사항의 결정과 승인부터 다시 한다.
  • 요구사항이 아직 승인되지 않았다. AI가 아무것도 만들지 않고 멈춘다. 요구사항을 먼저 마친다.
