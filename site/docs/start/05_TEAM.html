팀으로 일하기

읽기 안내 — 누가: 팀으로 시작한 프로젝트(/nexi-init <이름> team)의 모든 사람 · 언제: 작업 순환의 작업을 역할을 나눠 할 때 · 읽은 뒤: 자기 차례에 프롬프트를 넣고, 이슈 댓글로 다음 사람에게 넘긴다.

팀으로 할 때는 여러 사람이 각자의 컴퓨터에서 GitHub 저장소 하나를 같이 쓴다. 작업 순환의 단계를 역할마다 나눠 맡는다. 단계가 끝나면 AI가 commit과 push를 하고, 이슈에 다음 차례를 댓글로 남긴다.

예제는 5인 Step 4와 멈췄을 때다.

역할과 차례

단계 누가 넣는 프롬프트 끝나면
1 작업 고르기 FDE /nexi-backlog next 고른 작업이 나에게 지정된다
2 작업 계약서 FDE /nexi-contract <N>, 디자인 시스템 작업이나 디자인 변경 작업이면 /nexi-design <N>도 이슈에 "PM 승인 차례" (디자인 작업은 BRIEF까지 쓴 뒤)
2 승인 PM /nexi-contract <N> approve 이슈에 "개발자 구현 차례"
3 구현 개발자 /nexi-implement <N> PR이 열리고 이슈에 "리뷰 차례"
4 리뷰 검토자 /nexi-review <N> prepare(백그라운드 리뷰와 자동 기록, 또는 클립보드 복사 뒤 리뷰 agent에서 리뷰하고 /nexi-review <N> record) 판정이 기록되고 PR에 댓글
5 병합 PM /nexi-merge <N> main에 들어간 것을 확인하고 이슈를 닫는다

작업 하나의 차례는 아래 그림처럼 넘어간다. 열이 사람이고, 위에서 아래로 시간이 흐른다. 화살표 위의 글은 이슈에 남는 차례 댓글이다.

    Note over PM: 리뷰를 기다리거나 승인된 다른 작업에 main을 반영한다

  • 각자 GitHub 이슈와 PR의 알림을 켜 둔다. 이슈 댓글이 다음 차례와 그때의 commit 해시를 알려 준다. 리뷰 판정은 PR 댓글로 온다. 아직 이슈가 없는 요구사항 단계에서는 메신저로 알린다.

  • 누가 무엇을 할 차례인지는 /nexi-backlog status로 본다. 열린 작업마다 상태, 담당자, 다음에 할 사람과 넣을 프롬프트, 근거를 보여 주고 아무것도 바꾸지 않는다. 이슈 댓글이 저장소 기록과 다르면 상태는 저장소 기록을 따른다. 예외는 하나다. 판정이 원인 후보: 계속으로 끝나고 PM이 그 판정을 기록한 commit 뒤에 결정: 계속 — 개발자 차례 댓글을 달았으면, 그 작업은 REVISE이고 다음은 개발자다.

  • 한 작업은 한 번에 한 사람만 손댄다. 작업은 branch t<N>에서 하고, main에는 PM이 병합할 때만 들어간다.

  • 승인, 병합, 백로그 만들기, 작업 나누기와 변경, 끝내기는 PM만 할 수 있다. AI가 AGENTS.md의 PM: 줄과 프롬프트를 넣은 사람을 비교해서 확인한다.

  • 검토자는 prepare가 준비해 준 폴더에서, 지정된 commit을 리뷰한다. prepare는 리뷰할 수 있는 agent를 보여 주고 두 가지 중에 고르게 한다.

    1. 지금 백그라운드로 리뷰 agent를 돌리고 판정을 자동으로 기록한다. 판정을 복사해 붙여 넣지 않는다. 기본 agent는 그 작업을 구현하지 않은 agent다. CuCu도 고를 수 있고(CuCu에 키트를 설치했을 때), 작업의 commit을 받은 임시 사본에서 리뷰한다. 리뷰가 그 사본을 바꾸면 판정을 쓰지 않는다.
    2. 리뷰 프롬프트를 클립보드에 복사한다. 리뷰 agent를 따로 열어 붙여 넣고, 나온 판정을 /nexi-review <N> record에 붙여 넣는다.

    1은 리뷰가 끝날 때까지 최대 30분 걸린다. CuCu는 1로만 리뷰한다. prepare는 Claude Code나 Codex에서 연다.

  • 개발자가 /nexi-run <N>으로 구현부터 판정 기록까지 한 번에 할 수도 있다. APPROVE로 멈추면 이슈에 "검토자 확인 차례"가 남는다. 개발자가 아닌 검토자가 /nexi-review <N> confirm을 넣고 기록된 판정과 근거(수용 기준마다의 판단, PNG마다의 대조)를 읽는다. 근거가 빠졌으면 확인하지 않고 prepare부터 리뷰를 다시 받는다. 확인하면 이슈에 "검토자 확인 — PM 병합 차례"가 남고, PM은 그 확인을 보고 병합한다. 확인한 뒤 branch가 바뀌면 그 확인은 쓰지 않고, PM이 병합할 때 직접 확인한다.

여러 FDE가 나눠 맡기

일을 동시에 더 하려면 FDE를 늘린다. 한 사람이 여러 작업을 동시에 돌리지는 않는다.

  1. PM이 백로그를 만들 때 작업마다 맡을 FDE를 정한다. 같은 파일이나 화면을 건드리는 작업은 되도록 한 사람에게 준다. 나중에 바꾸려면 /nexi-backlog assign <N> <아이디>를 넣는다.
  2. FDE는 /nexi-backlog next로 자기 작업 가운데 시작할 수 있는 것을 고른다. 자기 작업이 없으면 아무도 맡지 않은 작업을 골라 자기에게 지정한다. 이미 작업을 맡은 적이 있는 FDE만 그렇게 할 수 있다. 개발자나 검토자가 넣으면 PM에게 넘긴다. 남의 작업은 고르지 않는다.
  3. 남의 작업에 /nexi-contract를 넣으면 AI가 멈춘다. 담당을 바꿔야 하면 PM에게 말한다.

FDE는 맡은 작업이 병합될 때까지 그 작업을 이어 간다. 그 사이 next를 넣으면 그 작업을 다시 보여 준다. 개발자나 검토자에게 여러 작업이 한꺼번에 오면 이슈 번호 순서로 처리하고, 순서를 바꿔야 하면 PM이 정한다.

FDE가 한 명이어도 PM이 백로그를 만들 때 담당을 정한다. 작업 나누기, 변경, 끝내기 거절로 새로 생긴 이슈도 PM이 그때 담당을 정한다. 담당이 없는 작업에는 /nexi-contract와 /nexi-design이 멈춘다.

팀을 나눌 때

팀을 나누는 곳은 백로그다. 요구사항까지는 팀이 하나로 일하고, PM이 /nexi-backlog로 작업을 만들 때 작업마다 어느 팀의 누가 맡을지 정한다. 그 뒤로는 작업마다 같은 차례(계약서, 승인, 구현, 리뷰, 병합)를 돈다. 팀은 작업의 담당과 선행 작업으로만 나뉘고, 다른 절차는 없다. 팀을 나누는 기준은 둘이다. 백엔드와 프런트엔드처럼 계층으로 나누거나, 고객 관리와 작업 배정처럼 모듈로 나눈다.

단계 누가 팀을 나누는가
시작, 요구사항 PM, FDE 한 명 나누지 않는다. 결정 문서 하나를 같이 승인한다
백로그 PM 여기서 나눈다. 작업마다 담당 한 사람과 선행 작업을 정한다
공통 기반 작업: 골격, 코드 표준, 디자인 시스템, 승인된 요구사항에 있는 로그인과 권한, 여러 팀이 쓰는 데이터 모델 작업마다 담당 한 사람 나누지 않는다. 백로그의 앞에 두고, 그것을 쓰는 기능 작업만 선행 작업으로 기다린다
기능 작업 작업을 맡은 팀 팀마다 자기 작업을 next로 골라 동시에 진행한다
리뷰, 병합 검토자, PM 모든 팀의 작업을 같은 사람이 같은 방식으로 한다
끝내기 PM 나누지 않는다

어느 기준으로 나누든 백로그를 만들 때 지킬 것:

  • 작업 하나의 담당은 한 사람이다. 담당이 둘인 작업은 /nexi-contract가 멈춘다.
  • 다른 팀의 작업이 만든 것을 쓰는 작업은 그 작업을 선행 작업에 적는다. next는 선행 작업이 main에 수용된 작업만 고른다.
  • 팀 사이의 약속은 그것을 만드는 작업의 계약서에 적는다(주소, 요청과 응답의 모양, 오류, 데이터의 모양). 쓰는 쪽 계약서는 그것을 바꾸지 않고 인용한다. 바꿔야 하면 만드는 쪽 작업(이미 병합됐으면 변경 작업)으로 바꾼다.
  • 여러 팀이 같이 고치는 파일은 한 팀이 맡도록 작업을 나눈다. 그래도 겹치면 아래 충돌 규칙을 따른다.
  • 끝에 몰아서 하는 "전체 테스트" 작업이나 모두가 맡는 작업은 만들지 않는다. 검사는 작업마다 계약서에 들어가고, 마지막 확인은 끝내기가 한다.
  • 디자인 기준(BRIEF)은 하나다. 모든 팀의 화면이 그 기준을 따르고, 공통 구성 요소를 바꾸는 일은 디자인 변경 작업 하나로 한다.
  • FDE가 자기 작업의 구현까지 맡아도 된다. 리뷰는 구현하지 않은 사람이 한다.

기준마다 다른 것:

계층 팀(백엔드, 프런트엔드) 모듈 팀(예: 고객 관리, 작업 배정)
작업을 자르는 법 API와 화면을 모두 새로 만드는 기능은 API 작업과 화면 작업으로 나눈다. 이미 있는 API를 쓰는 화면은 나누지 않는다 기능을 API와 화면으로 나누지 않는다. 한 팀이 자기 모듈의 API, 화면, 검사를 한 작업으로 맡는다
팀 사이의 약속 API 작업의 계약서 다른 모듈이 쓰는 API나 데이터를 만드는 작업의 계약서
기다리는 곳 화면 작업은 그 API 작업이 병합된 뒤에 시작한다 다른 모듈의 것을 실제로 쓰는 작업만 기다린다. 대부분 동시에 진행한다
공통 기반의 담당 골격과 코드 표준은 백엔드 팀, 디자인 시스템은 프런트엔드 팀 공통 기반을 맡을 사람(공통 담당이나 첫 팀)을 정한다. 대부분의 모듈 작업이 이것을 쓰므로 먼저, 빨리 끝낸다
자주 겹치는 파일 API 타입 정의, 라우팅과 메뉴, seed 데이터 DB 스키마와 마이그레이션, 메뉴, seed 데이터. 모듈은 자기 테이블만 더하고, 여러 모듈이 쓰는 테이블을 바꾸는 일은 담당 한 사람의 작업으로 한다

모듈 팀에서 두 모듈이 서로의 것을 계속 필요로 하면 경계가 잘못 그어진 것이다. 그 일을 한 모듈로 모은다. 모듈 팀 안을 다시 백엔드와 프런트엔드로 나누면, 모듈 경계를 먼저 긋고 모듈 안에서 계층 팀의 규칙을 쓴다.

팀이 많아질수록 PM이 병합하는 순서가 중요하다. 한 팀의 작업이 병합되면 다른 팀의 리뷰가 끝난 작업이 main을 다시 합치고 리뷰를 다시 받아야 할 수 있다. 같은 main 위에서 승인을 받은 작업이 둘이면, 어느 쪽을 먼저 병합해도 다른 쪽은 다시 확인과 리뷰를 받는다.

  1. PM이 /nexi-backlog status로 승인된 작업을 보고 다음에 병합할 작업을 하나 고른다. 그동안 다른 작업의 개발과 리뷰는 계속한다. 다른 작업을 먼저 병합하거나 이 병합을 미루려면 /nexi-merge <N>을 넣기 전에 같은 대화에서 AI에게 그렇게 말한다.
  2. PM이 /nexi-merge <N>을 넣는다. AI는 병합하기 전에 다른 작업을 세 무리로 보여 준다. 이 병합 때문에 다시 리뷰를 받는 작업, 이미 main보다 뒤처진 작업, 상태를 알 수 없는 작업이다. AI는 이 목록을 보여 준 뒤 기다리지 않고 병합한다.
  3. 병합과 수용이 끝나면 AI가 리뷰를 기다리거나 승인된 작업마다 새 main을 그 branch에 합치고 검사와 증거를 다시 만든다. 개발자는 아무것도 다시 넣지 않는다. 끝난 작업의 이슈에는 "main 반영 — 리뷰 차례"가 남고, 검토자가 그 작업을 다시 리뷰한다.
  4. AI가 반영하지 못한 작업의 이슈에는 "main 이동 — 개발자 구현 차례"와 이유가 남는다. 작업 파일 밖의 충돌, 검사 실패, 반영하는 도중의 개발자 push, CuCu로 병합한 경우다. 개발자가 /nexi-implement <N>으로 main을 합친다. 반영을 시작하기 전에 개발자가 이미 push했으면 AI는 그 작업을 건드리지 않고 댓글도 남기지 않으며, 보고에 "건너뜀"으로만 적는다. 그 작업은 개발자가 이어 간다.
  5. AI가 "반영 상태 확인 필요"와 실행 이름을 보고하면 다른 반영이 돌고 있거나 중단된 것이다. PM은 그 반영이 더는 돌고 있지 않은지 확인한 뒤, AI에게 그 실행을 끝내라고 한다(nexi-refresh-claim.sh release). 그다음 /nexi-implement <N> refresh를 넣거나 개발자에게 넘긴다. 중단된 반영이 이미 push했으면 refresh가 거기서 이어 간다.

PM은 /nexi-backlog 다음 줄에 팀 구성에 맞는 글을 붙여 넣는다. 계층 팀이면:

/nexi-backlog
백엔드 팀(FDE: <아이디>)과 프런트엔드 팀(FDE: <아이디>, <아이디>)으로 나눠 일한다. API와 화면을 모두 새로 만드는 기능은 API 작업과
화면 작업으로 나누고, 화면 작업의 선행 작업에 그 API 작업을 적어라. 이미 있는 API를 쓰는 화면은 나누지 않는다. 작업마다 담당은 한 사람이다.
골격과 코드 표준은 백엔드 팀, 디자인 시스템은 프런트엔드 팀이 맡는다.

모듈 팀이면:

/nexi-backlog
<모듈 이름> 팀(FDE: <아이디>), <모듈 이름> 팀(FDE: <아이디>)으로 모듈마다 나눠 일한다. 기능은 API와 화면을 나누지 않고 그 모듈 팀의
작업 하나로 만든다. 다른 모듈의 API나 데이터를 쓰는 작업은 그것을 만드는 작업을 선행 작업에 적어라. 골격, 코드 표준, 디자인 시스템, 그리고 승인된 요구사항에 있으면 로그인과 권한, 여러 모듈이 쓰는 데이터 모델을 이 순서로 공통 기반 작업으로 먼저 두고, 담당은 <아이디>다. 각 작업은 실제로 쓰는 공통 기반 작업만 선행 작업에 적어라. 작업마다 담당은 한 사람이다.

이럴 때는

AI·하네스 운영자(agent 실행 환경을 맡은 사람)가 있는 팀이면 PM은 그 사람과 함께 정한다. 없으면 PM이 정한다.

  • 선행 작업이 아직 병합되지 않았다. next가 그 작업을 고르지 않는다. 다른 작업을 하거나, 선행 작업이 병합되기를 기다린다.
  • 리뷰를 받은 뒤 다른 작업이 먼저 병합됐다. PM의 /nexi-merge가 멈춘다. 개발자가 /nexi-implement <N>을 다시 넣으면 AI가 최신 main을 합치고(rebase는 하지 않는다) 검사와 스크린샷을 다시 만든다. 그다음 검토자가 다시 리뷰한다.
  • 병합 충돌이 났다. 이 작업의 파일 안에서 생긴 충돌은 구현하면서 해결한다. 이 작업이 이미 바꾼 파일이나 작업 계약서에 적힌 파일이 아닌 곳에서 충돌하면 AI가 합치기를 취소하고 멈춘다. 어느 작업에서 그 파일을 고칠지 PM이 정한다. 정한 작업의 FDE가 계약서에 그 파일을 적어 고치고, PM이 다시 승인한 뒤, 개발자가 /nexi-implement <N>을 다시 넣는다.
  • 리뷰 뒤에 무언가 바뀌었다. 판정 기록 말고 코드, 작업 계약서, 증거, 스크린샷이 바뀌었으면 병합하지 않고 리뷰를 다시 받는다.
  • 병합은 됐는데 확인에서 걸렸다. 예를 들어 병합 직전에 다른 작업이 먼저 들어가, 리뷰한 상태 위에 병합되지 않았다. AI가 이슈를 닫지 않고(닫혔으면 다시 열고) 멈춘다. 이 작업은 끝난 것이 아니다. 이미 main에 들어간 변경을 어떻게 할지(예: 되돌리는 새 작업) PM이 정한다.
  • push가 실패했다. 이슈와 PR을 열어 둔다. 원인을 해결한 뒤 같은 프롬프트를 다시 넣는다. AI가 이미 만든 commit을 push한다.
  • REVISE가 세 번 이어졌거나 BLOCK이 나왔다. PM이 판정의 원인 후보를 보고(세 번째 REVISE나 예전 형식의 BLOCK이면 원인을 모두 따져 보고) 원인을 정해 이슈에 결정: <원인> — <다음 사람> 차례 댓글을 단다. 원인이 리뷰 독립성이면 댓글 없이 다른 agent가 같은 파일을 다시 리뷰한다. 원인별 다음 차례는 작업 순환의 표와 같고, 팀에서는 이렇게 나눈다.
    • 계약서: 댓글은 정확히 결정: 계약서 — 개발자 차례다. 개발자가 /nexi-implement <N>을 넣으면 AI가 작업을 push하고, 개발자가 이슈 담당자(FDE)면 고친 계약서 초안까지 올린다. 담당자가 아니면 계약 변경 필요 — FDE 차례 댓글을 달고 FDE가 /nexi-contract <N>으로 고친다. PM이 /nexi-contract <N> approve로 승인한다.
    • 작업 크기: PM이 /nexi-backlog split <N>으로 나눈다. AI가 그 작업의 PR을 병합하지 않고 닫는다. 개발자는 옛 폴더를 그대로 두고 /nexi-init clone으로 받은 새 폴더에서 이어 간다. 나눈 작업은 FDE가 next로 골라 작업 계약서부터 다시 시작한다.
    • 디자인 기준: PM이 /nexi-backlog change(디자인)와 /nexi-backlog split <N>을 한다.
    • 요구사항: FDE가 /nexi-requirements decide를 하고 PM이 승인한 뒤 계약서 원인처럼 한다.
    • 계속: 판정이 원인 후보: 계속으로 끝날 때만 PM이 고른다. 판정이 기록된 뒤에 다는 댓글만 인정된다. 댓글은 정확히 결정: 계속 — 개발자 차례이고, 개발자가 /nexi-implement <N>으로 그 판정의 지적을 고친다. 다음 REVISE에는 새 결정이 필요하다.
  • 구현하다가 승인된 작업 계약서대로 끝낼 수 없다는 것이 드러났다. 리뷰를 기다리지 않는다. 개발자가 /nexi-implement <N>을 다시 넣으면 AI가 작업을 push하고, 위의 계약서 원인과 같은 순서로 고친 계약서가 PM 승인 차례가 된다.
  • 누가 자리를 비웠다. 그 단계를 다른 사람이 이어받아야 하면 PM이 정한다. 같은 사람이 돌아오면 하던 단계의 프롬프트를 다시 넣는다.

누가 무엇을 정했는지는 이슈 댓글로 남긴다.
