시작하기

시작하기

읽기 안내 — 누가: NEXI로 프로젝트를 하는 PM, FDE, 개발자 · 언제: 고객의 요구사항을 받고 개발을 시작하기 전 · 읽은 뒤: 준비부터 차례로 읽으며 프로젝트를 진행한다.

NEXI는 AI agent와 함께 개발하면서도 끝까지 동작하는 시스템을 만들기 위한 작업 방법이다. AI로 코드를 빨리 만들기만 하면 업무 규칙을 빠뜨리거나 기존 기능을 망가뜨리기 쉽다. 누가 무엇을 승인했는지도 알기 어려워지고, 뒤로 갈수록 고칠 일과 검토할 일이 쌓인다.

그래서 NEXI는 이렇게 일한다.

  • 요구사항은 결정 문서로 확정하고 사람이 승인한다.
  • 일은 하루 안에 끝나는 작업으로 나눈다.
  • 작업마다 무엇을 만들고 무엇으로 확인할지 작업 계약서에 적고 사람이 승인한다.
  • 구현하기 전에 검사부터 만들어 실패하는 것을 보고, 구현한 뒤 통과하는 것을 본다.
  • 구현하지 않은 다른 agent가 리뷰하고, 통과한 변경만 main에 들어간다.

사람은 프롬프트를 넣고, 결과를 읽고, 승인한다. 명령은 AI가 실행한다. 지금 쓰는 AI agent는 Claude Code와 Codex다. CuCu 지원은 준비 중이다(P#275). 단계마다 할 일은 NEXI 키트의 skill(단계별 작업 절차를 담은 파일)에 들어 있고, 사람은 /nexi-init 같은 프롬프트로 그 skill을 부른다(CuCu에서는 !nexi-init).

전체 흐름

단계 하는 일
준비 키트와 도구를 설치한다
프로젝트 시작 저장소와 작업 규칙을 만든다
요구사항 요구사항을 분석하고, 질문하고, 결정 문서를 승인한다
백로그 하루 단위 작업 목록을 만든다
작업 순환 작업 하나를 계약서부터 병합까지 끝낸다
팀으로 일하기 역할을 나누고 차례를 넘긴다
끝난 작업 바꾸기 이미 끝난 작업을 바꿀 때 새 작업을 만든다
끝내기와 넘기기 마지막으로 검증하고 최종 보고를 승인한다

skill마다 넣는 값과 멈추는 경우는 skill 참조, 낱말의 뜻은 개념 참조, 파일 형식은 산출물 참조에 있다.

팀으로 하면 차례는 아래 그림처럼 넘어간다. 열이 사람이고, 위에서 아래로 시간이 흐른다. 혼자 하면 한 사람이 모든 열의 일을 한다.

    participant PM
    participant FDE
    participant DEV as 개발자
    participant REV as 검토자
    Note over PM,REV: 모두 키트를 설치한다 (준비)
    Note over PM: /nexi-init 이름 team (프로젝트 시작)
    PM->>FDE: 저장소와 작업 규칙
    Note over FDE: /nexi-requirements analyze (요구사항)
    FDE->>PM: 분석과 질문
    Note over PM: /nexi-requirements answers
    PM->>FDE: 답
    Note over FDE: /nexi-requirements decide
    FDE->>PM: req의 commit 해시
    Note over PM: /nexi-requirements approve
    Note over PM: /nexi-backlog (백로그)
    PM->>FDE: 작업과 담당

        Note over FDE: /nexi-backlog next 와 /nexi-contract N
        opt 디자인 작업이면
            Note over FDE: /nexi-design N
        end
        FDE->>PM: PM 승인 차례
        Note over PM: /nexi-contract N approve
        PM->>DEV: 개발자 구현 차례
        Note over DEV: /nexi-implement N
        DEV->>REV: 리뷰 차례
        Note over REV: /nexi-review N prepare 와 리뷰 기록
        loop REVISE가 나올 때마다
            REV->>DEV: 개발자 구현 차례
            Note over DEV: /nexi-implement N 으로 고친다
            DEV->>REV: 리뷰 차례
            Note over REV: 다시 리뷰하고 기록한다
        end
        REV->>PM: APPROVE면 PM 병합 차례
        Note over PM: /nexi-merge N
    end
    opt 끝난 작업을 바꿀 때
        Note over PM: /nexi-backlog change 로 변경 작업을 만든다
        PM->>FDE: 변경 작업은 작업 순환부터 다시 돈다
    end
    Note over PM: /nexi-finish 와 approve (끝내기)

예: 요청 하나를 끝내기까지

고객이 "지연 주문을 조회하는 화면이 필요하다"고 요청했다고 하자. 먼저 업무 규칙과 예외를 고객에게 묻고, 이번에 만들지 않을 것도 정한다. 그다음 하루 안에 끝나는 작업으로 나누고, 작업마다 작업 계약서를 써서 사람이 승인한다. agent가 구현하면 다른 agent가 리뷰하고, 통과한 변경만 main에 들어간다. 마지막에 고객이 결과를 써 보고 받아들이거나 보완을 요청한다.

원칙

NEXI는 단순하게 일하되, 동작하는 시스템을 끝까지 만드는 것을 목표로 한다. 이를 위해 네 가지를 지킨다 (개념 참조).

  1. 단계마다 skill이 조건을 확인한다. skill은 앞 단계가 제대로 끝났는지 먼저 보고, 아니면 멈추고 무엇을 할지 알려 준다.
  2. 망가진 작업은 살리지 않고 작게 다시 한다. 너무 커서 끝나지 않는 작업은 나눠서 main에서 새로 시작한다.
  3. 끝난 작업은 고치지 않는다. 바꿀 것이 생기면 새 작업(변경 작업)을 만든다. 끝난 작업의 기록은 그대로 둔다.
  4. 일을 동시에 늘리려면 사람을 늘린다. 한 사람이 여러 작업을 동시에 돌리지 않는다. 처리량은 리뷰할 수 있는 시간이 정한다.

어느 단계에서도 다음은 바뀌지 않는다.

  • 요구사항 결정 문서와 작업 계약서는 사람이 승인한다. AI가 대신 승인하지 않는다.
  • 새 검사는 구현 전에 먼저 실패해야 한다. 그 실패는 확인하려는 기준 때문이어야 한다.
  • 리뷰는 구현한 agent와 다른 agent가 한다. 다른 agent를 쓸 수 없는 급한 경우에만 사람이 골라 같은 agent가 새 세션에서 리뷰한다. 데이터 삭제와 덮어쓰기, 권한, 데이터 이전, 밖의 서비스에 닿는 명령처럼 위험한 변경은 예외가 아니다.
  • 리뷰에서 APPROVE를 받은 그대로만 main에 들어간다.
  • 끝낼 때 저장소를 새로 받아 설치부터 lint까지 다시 돌린다.
  • 마지막에 사람이 앱을 직접 써 본다.

일하는 내내 이렇게 한다.

  • AI가 끝났다고 해도 그 말만 믿지 않는다. 검사 결과, 리뷰 판정, 변경 이력을 보고 판단한다.
  • 검증하기 어려우면 검증을 느슨하게 하지 않고 범위를 줄인다.
  • 비교할 기준이 없으면 "더 빨라졌다", "더 싸졌다"고 말하지 않는다. 그런 효과는 "미판정"(아직 판단할 수 없음)으로 남긴다.
  • 실패하면 누구 탓인지 따지지 않고, 무엇이 왜 안 됐고 무엇을 고쳤는지 적는다.
  • 고객이 우리 없이 혼자 할 수 있게 하는 일은 마지막이 아니라 처음부터 한다. 고객이 혼자 작업 하나를 끝낸 기록이 있어야 넘긴 것이다.

사람과 AI가 정하는 것

결정 정하는 사람 AI가 하는 일
범위, 우선순위, 업무 규칙 고객 결정권자와 PM 선택지, 영향, 남은 질문을 정리한다
요구사항 결정 문서와 작업 계약서(수용 기준과 확인 방법) 승인 PM(혼자 하면 그 사람). 범위가 바뀌면 고객 결정권자도 동의한다 초안을 쓰고 스스로 점검한 결과를 보여 준다
리뷰 판정 구현하지 않은 agent가 판정하고, 사람이 근거를 확인한다 정해진 형식으로 판정과 근거를 쓴다
병합 PM(혼자 하면 그 사람) APPROVE와 병합 조건을 확인한 뒤에만 병합한다
결과를 받아들일지, 남은 위험을 감수할지 고객 결정권자 최종 보고와 확인하지 못한 항목을 정리한다
배포와 운영 환경 변경 운영 권한을 가진 사람 승인된 명령의 실행을 돕는다

AI가 "성공했다"고 해도 그것은 승인이 아니다. AI는 자기 권한을 스스로 넓히거나 우회하지 않는다.

시작해도 되는 때

다음이 갖춰지면 시작한다.

  1. 결정할 사람과 검토할 사람이 정해졌다.
  2. 변경을 확인할 검사가 있거나, 첫 작업(골격)에서 만들 수 있다.
  3. AI가 읽고 쓰고 실행할 범위와 데이터를 다루는 조건이 정해졌다.
  4. 첫 결과를 작게 잘라 2주 안에 검토하고 받아들일 수 있다.

다음 가운데 하나라도 해당하면 구현을 시작하지 않는다. 그 문제부터 고객과 푼다.

  • 고객의 목표나 수용 기준을 확인할 방법이 없다.
  • 변경을 확인할 검사도, 사람의 검토도 만들 수 없다.
  • 운영 환경과 민감한 데이터를 안전하게 다룰 방법이 없다.
  • 결정할 사람이 막힌 일을 풀어 줄 수 없다.

일은 2주(10영업일) 단위로 한다. 처음 12일에 질문과 작업 계약서를 정하고, 중간에 구현하고 리뷰하고, 마지막 23일에 병합과 고객 확인을 마친 뒤 다음 범위를 정한다. 두세 번 해 본 뒤 실제로 기다린 시간을 보고 주기를 고친다.
