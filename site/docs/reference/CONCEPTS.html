개념 참조

개념 참조

읽기 안내 — 누가: NEXI 키트로 프로젝트를 하는 사람 · 언제: 시작하기나 skill의 답에 나온 말의 정확한 뜻을 알고 싶을 때 · 읽은 뒤: 그 말이 가리키는 규칙대로 판단한다.

NEXI는 몇 가지 원칙과 약속한 말 위에서 움직인다. 말마다 그것을 정하거나 확인하는 skill이 있다. 진행 경로는 혼자, 팀, 새 저장소 전환에서 고른다. 명령별 입력과 산출물은 skill 색인, 버전과 중단 처리는 공통 규칙에 있다.

원칙

원칙 뜻
단계마다 skill이 조건을 확인한다 skill은 시작할 때 앞 단계가 제대로 끝났는지 보고, 아니면 멈춘다. 같은 규칙을 따로 검사하는 도구는 두지 않는다
망가진 작업은 살리지 않고 작게 다시 한다 너무 큰 작업은 나누고, 나눈 작업은 main에서 새로 구현한다. 하다 만 코드는 참고용으로만 남긴다
끝난 작업은 고치지 않는다 수용된 작업의 작업 계약서, 증거, 판정은 그대로 둔다. 바꿀 것은 변경 대상: 줄을 단 새 작업이 된다
일을 동시에 늘리려면 사람을 늘린다 처리량은 리뷰할 수 있는 시간이 정한다. 여러 작업을 함께 하려면 FDE를 늘린다. 한 사람이 작업을 동시에 돌리는 기능은 없다

혼자와 팀, 역할

AGENTS.md의 Mode: 줄이 혼자 하는지(solo) 팀인지(team) 정한다. /nexi-init에 team을 붙이면 팀이다.

  • 혼자(solo): 한 사람이 한 폴더의 main에서 일한다. 작업의 변경은 리뷰에서 APPROVE를 받은 뒤 nexi-merge가 한 번에 commit한다.
  • 팀(team): 여러 사람이 각자의 컴퓨터에서 GitHub 저장소 하나를 같이 쓴다. 작업마다 branch를 쓰고, 단계가 끝나면 skill이 commit과 push를 하고 이슈에 댓글을 남긴다. 병합은 PR로 한다.

팀의 역할은 다음과 같다.

역할 하는 일
PM 저장소 만들기, 요구사항·작업 계약서·디자인 기준 승인, 백로그와 담당 정하기, 작업 나누기와 변경, 병합, 끝내기(nexi-finish의 검증, reject, approve)
FDE 요구사항 분석과 결정 문서, 작업 계약서, 디자인 기준
개발자 구현, 리뷰 지적 반영, PR
검토자 리뷰 agent로 리뷰하고 판정을 기록한다
AI·하네스 운영자 키트 설치와 막힌 사람 돕기. 일이 멈췄을 때 PM과 함께 정한다. 없으면 PM이 정한다

PM 몫의 일은 AGENTS.md의 PM: 줄에 적힌 GitHub 아이디의 사람만 할 수 있다.

담당: FDE가 여럿이면 PM이 작업마다 맡을 FDE를 GitHub 이슈의 담당자로 정한다. nexi-backlog next는 나에게 지정된 작업을 먼저, 그다음 아무도 맡지 않은 작업을 고른다. nexi-contract는 남에게 지정된 작업이면 멈춘다.

branch(팀)

branch 쓰임
main 승인된 문서와 수용된 작업만 들어간다. 직접 commit하지 않고 PR 병합으로만 바뀐다
req 요구사항 문서. nexi-requirements approve가 PR로 병합한 뒤 GitHub의 req를 지운다. 로컬 branch는 req-done-<승인 commit 앞 12자리>로 남긴다
t<N> 작업 T#<N>의 작업 계약서, 디자인 기준, 코드, 증거, 판정 기록. 병합한 뒤에도 남는다
final-<commit> 최종 보고. <commit>은 시험한 main commit의 앞 12자리다. nexi-finish approve가 PR로 병합한다

main의 변경은 각 branch에 merge로 받는다. 어느 skill도 rebase나 force push를 하지 않는다.

작업

  • 작업(T#<N>): 라벨 task가 붙은 GitHub 이슈 하나. 하루 안에 끝나는 크기다. 백로그는 골격, 코드 표준, 디자인 시스템(화면이 있으면), 기능 순서다.
  • 골격 작업: 백로그의 첫 작업. 기술 스택의 도구와 make build, make test, make lint, 실행 방법을 적은 README를 만든다.
  • 디자인 시스템 작업: 화면이 있는 제품의 셋째 작업(골격, 코드 표준 다음). 디자인 기준(BRIEF)대로 디자인 토큰, 화면 틀(layout shell), 기본 구성 요소, 기준 화면 하나를 만들고 make screenshots를 만든다. 이보다 앞선 작업에는 스크린샷이 없다.
  • 선행 작업: 이 작업이 쓰는 코드, 데이터, 화면을 만드는 작업. 이슈의 선행 작업: 줄에 적는다. 선행 작업이 모두 수용돼야 이 작업을 고른다.
  • 나눈 작업: 너무 큰 작업을 nexi-backlog split으로 나눠 생긴 작업(나눔 출처: 줄). 원래 작업은 "나눔"으로 닫히고 수용으로 치지 않는다.
  • 변경 작업: 끝난 작업을 바꾸는 작업(변경 대상: 줄). 요구사항이 바뀌면 결정 문서를 먼저 다시 승인한다. 디자인이 바뀌면 디자인 변경 작업이 먼저 오고, 화면마다의 변경 작업이 그 뒤를 잇는다.

검증

  • 새 검사: 이 작업이 더하는 동작을 확인하는 검사. 구현 전에 돌리면 확인하려는 기준 때문에 실패해야 한다(red). 모듈이 없거나, 타입 오류가 나거나, 시간이 넘어서 실패한 것은 red로 치지 않는다.
  • 회귀 검사: 이미 있던 동작이 그대로인지 확인하는 검사(make test, make lint, make build 등). 작업 전과 뒤 모두 통과한다. 작업 전부터 통과하는 검사가 기준을 제대로 확인한다면, 그 동작이 이미 있다는 뜻이므로 회귀 검사로 분류하고 구현 전의 실행 결과를 증거에 남긴다. 골격 작업에서는 이 명령들이 아직 없으므로 새 검사다.
  • 통과(green): 마지막으로 고친 뒤 새 검사와 회귀 검사가 모두 통과한 결과. 증거에 남긴다.
  • 새 사본 검증: nexi-finish가 저장소를 새로 받아 README 순서대로 설치부터 lint까지 돌리는 것. 이 폴더에만 있는 파일에 기대지 않는지 확인한다.

리뷰와 수용

  • 리뷰 agent: 구현한 agent와 다른 agent가 읽기 전용으로 리뷰한다. Claude Code가 구현했으면 Codex, Codex가 구현했으면 Claude Code다. 다른 agent를 쓸 수 없는 급한 경우에만 사람이 골라 같은 agent가 새 세션에서 리뷰하고, 판정의 reviewer: 줄에 그 사실과 이유를 남긴다.
  • 판정: APPROVE(모든 기준을 근거와 함께 충족), REVISE(작업 계약서 안에서 고칠 것이 있음), BLOCK(사람이 정해야 판단하거나 이어 갈 수 있음). 형식은 판정 형식에 있다. 같은 작업에서 세 번째 연속 REVISE가 나오면 되풀이하지 않고 사람이 정한다(작업 나누기나 작업 계약서 수정). 세 번째나 네 번째 REVISE에서 리뷰가 앞의 지적이 모두 고쳐지고 새 지적만 있다고 보면 원인 후보: 계속을 적고, 사람이 그 판정 하나에 한해 계속 고치게 할 수 있다. 다섯 번째에는 계속이 없다.
  • 지문(혼자 할 때): scripts/nexi-fingerprint.sh가 만드는 해시다. 코드 지문은 commit하지 않은 변경 전체(증거와 판정 기록 제외)의 해시로, 증거가 바로 그 코드를 검사했는지 확인하는 데 쓴다. 리뷰한 파일 지문(--reviewed <N>)은 판정 기록 docs/reviews/T<N>.md 하나만 뺀 모든 변경의 해시로, 리뷰 뒤에 아무것도 바뀌지 않았는지 확인하는 데 쓴다. 팀은 지문 대신 commit 해시로 같은 것을 확인한다.
  • 수용: 작업이 끝났다고 인정되는 상태. 이슈가 닫혔다는 것만으로는 수용이 아니다. 마지막 판정이 APPROVE이고, main에 들어간 것이 리뷰한 변경 그대로이고, 리뷰할 때의 기준 commit(base) 위에 들어갔다는 것이 확인돼야 한다. 조건은 수용 조건에 있다. nexi-merge가 확인한 뒤 이슈에 NEXI 수용 댓글을 남긴다.

예: 요청 하나가 수용되기까지

아래는 할 일 목록에 완료 표시를 더하는 설명용 예다. 작업 번호와 파일 경로의 <N>은 실제 이슈 번호로 바꾼다.

단계 예에서 남는 것 그 결과가 뜻하는 것
요구사항 결정 REQ-CONTEXT에 완료 표시와 미완료 목록의 동작을 결정한다. 사람이 승인한 범위와 확인 방법이 작업의 기준이 된다.
작업 계약서 T#<N>의 수용 기준에 완료 표시 뒤 미완료 목록에서 빠지는 동작과 검사를 적는다. 구현할 변경 하나와 끝났다고 볼 조건이 승인된다.
구현 증거 새 검사의 red, 마지막 변경 뒤 모든 검사 결과와 필요한 화면 PNG를 남긴다. 검사한 코드와 결과를 연결한다. 구현 전부터 있던 동작은 회귀 검사로 적는다.
리뷰 판정 다른 agent가 기준별 코드·증거를 읽고 APPROVE를 기록한다. 리뷰한 변경에 대한 판정이다. 아직 main 수용은 아니다.
작업 수용 리뷰한 base 위에 같은 변경을 넣고 원격 main과 NEXI 수용을 확인한다. 다음 작업이 그 결과를 선행 작업으로 쓸 수 있다.
최종 확인 모든 작업 뒤 새 사본 검증과 사람이 써 본 결과를 FINAL에 담아 승인받는다. 시험한 main에 대한 최종 보고다. 운영 반영은 별도 절차로 한다.

계약서는 승인된 REQ-CONTEXT의 해시를 가리킨다. 요구사항이 바뀌면 계약서를 다시 쓰고 승인받는다. 증거와 판정은 검사하고 리뷰한 변경을 가리킨다. 변경이나 base가 달라지면 그대로 통과한 것으로 쓰지 않고 다시 검증·리뷰한다.

APPROVE는 리뷰, NEXI 수용은 병합, FINAL의 승인은 끝내기가 맡는다. 같은 agent 리뷰의 사람 선택과 위험 범주 제한은 리뷰 참조에 있다.

결정의 승인 상태

REQ-CONTEXT를 승인할 때 결정마다 승인 상태가 붙는다. 상태는 ## 승인 상태 표에 결정마다 하나 적힌다. 작업 계약서는 받아들임인 결정만 쓴다.

승인 상태 뜻
받아들임 이 결정대로 한다
받아들이지 않음 수행사가 정한 결정을 사람이 받아들이지 않았다. 이 결정에서만 나온 규칙은 문서에서 빠진다
고객 확인 필요 구현을 막지 않지만 고객이 확인해야 한다. 최종 보고까지 "고객 확인이 남은 결정"으로 따라간다
보류 고객이 나중에 정하기로 한 패턴 값이다. 결정의 제목이 보류:로 시작하고 필요한 때, 정할 사람, 미룬 이유가 있다. 어떤 작업 계약서도 이 결정을 쓰지 않는다. 값을 정해 다시 승인하면 받아들임이 된다

nexi-req-check.sh(키트의 nexi-init/assets)가 패턴 결정 표와 결정의 적용 범위, 보류 결정의 필드, 승인 상태를 글자로 검사한다. 결정이 그 작업을 덮는지는 AI가 판단한다.

상태 줄

문서 맨 위의 한 줄이 그 문서가 어디까지 왔는지 나타낸다.

줄 붙는 문서 뜻
상태: 초안 REQ-CONTEXT, 작업 계약서, BRIEF, FINAL 사람이 아직 승인하지 않았다. 승인한 문서를 고치면 초안으로 돌아간다
상태: 승인 같음 사람이 승인했다. 승인은 skill의 approve가 사람의 분명한 답을 받아 기록한다. AI가 대신 승인하지 않는다
상태: 작성 중 증거 구현이 아직 끝나지 않았다. 이 줄이 있으면 리뷰는 REVISE다. nexi-implement가 증거를 다 쓰면 이 줄을 지운다
요구사항: <해시> 작업 계약서 이 작업 계약서가 기준으로 삼은 REQ-CONTEXT. 지금 것과 다르면 요구사항이 바뀐 것이므로 작업 계약서를 다시 쓰고 승인한다

다음 프롬프트와 재개

  • 다음: 줄: 모든 skill은 답 끝에 다음에 넣을 프롬프트를 보여 준다. 그 줄을 넣거나, 다른 사람이나 다른 도구의 차례면 그쪽에 알린다.
  • 재개: 끊기거나 멈춘 뒤 같은 프롬프트를 다시 넣으면 skill이 이미 한 일을 알아보고 이어 간다. 상태는 git, 이슈, 산출물 파일에 남아 있으므로 따로 적어 둘 것이 없다. 이미 끝난 일은 다시 하지 않고 상태를 알려 준다.
