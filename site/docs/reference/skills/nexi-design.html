nexi-design — 화면의 디자인 기준

읽기 안내 — 누가: 이 skill을 실행하거나 결과를 넘겨받는 사람 · 언제: 입력, 산출물과 멈춘 이유를 확인할 때 · 읽은 뒤: 알맞은 프롬프트를 넣고 다음 차례에 결과를 넘긴다.

시작 전에

  • 입력: 디자인 시스템 작업 또는 디자인 변경 작업의 이슈 번호. 승인된 요구사항과, 변경이면 기존 BRIEF가 필요하다. 원하는 분위기는 선택 입력이다.
  • 실행하는 사람: 담당 FDE가 쓰고, PM이 nexi-contract approve에서 작업 계약서와 함께 승인한다.
  • 공통 확인: 원문과 버전, 환경과 재개. 공개 키트 상태는 배포 안내에서 본다.

명령과 동작

화면의 디자인 기준 docs/design/BRIEF.md를 쓴다. 디자인 시스템 작업과 디자인 변경 작업에서 쓰고, 코드는 쓰지 않는다.

프롬프트 누가(팀) 하는 일
/nexi-design <N> [원하는 분위기] FDE REQ-CONTEXT의 화면 결정과 사람이 말한 선호로 BRIEF 초안을 쓴다. 색, 글자, 간격, 구성 요소, 화면 폭별 배치, 화면별 상태를 담고, 근거 없는 값은 (제안)으로 적는다. 디자인 변경 작업이면 이슈가 요청한 값만 바꾼다

멈추는 경우

  • 팀에서 커밋되지 않은 다른 변경이 있다(쓰다 만 BRIEF는 이어 쓴다).
  • 팀에서 담당 FDE가 없거나 여러 명이거나, 다른 사람에게 지정된 작업이다. PM이 담당을 정한 뒤 다시 넣는다.
  • 팀의 작업 branch에 허용되지 않은 commit이 있거나 원격과 갈라졌다. 기록을 보존하고 사람이 확인한다.

이 작업에서 승인된 BRIEF가 그대로이고 새 요청도 없으면 파일을 바꾸지 않고 승인 상태를 보여 준다.

다음 차례

다음: /nexi-contract <N> approve. 이것이 BRIEF도 승인한다. 승인 뒤 BRIEF를 고치면 다시 초안이 된다.

남는 것

산출물 확인할 것
디자인 기준 docs/design/BRIEF.md 초안. 수정하면 다시 초안으로 돌아간다.
리뷰 기준 화면마다 비교할 항목과 캡처 전에 보여야 할 제목·상태를 Checks에 적는다.

BRIEF에는 방향, 토큰, 구성 요소, 배치, 표시 형식, 화면별 상태와 Checks를 담는다. 글자와 배경의 대비는 4.5:1 이상인지 확인한다. 요구사항이나 사람의 선호에 근거가 없는 값은 (제안)으로 보인다.
