NEXI 산출물 참조

읽기 안내 — 누가: NEXI 키트로 프로젝트를 하는 사람 · 언제: skill이 만든 파일이나 이슈 줄을 읽거나 검토할 때 · 읽은 뒤: 각 파일이 무엇을 담아야 하는지 알고, 빠지거나 틀린 곳을 AI에게 고치라고 한다.

NEXI 프로젝트에서 남는 것은 저장소의 파일, GitHub 이슈 본문의 줄, 이슈 댓글이다. 파일은 nexi-init이 만든 폴더에 각 skill이 쓴다. 정확한 형식은 각 skill의 원문(skill 참조)이 정한다.

저장소의 파일

파일 쓰는 skill 담는 것
AGENTS.md(CLAUDE.md는 링크) nexi-init 프로젝트 한 줄 설명, Mode: solo 또는 Mode: team, 팀이면 PM: <GitHub 아이디>, 명령(make build, make test, make lint, make screenshots T=<N>), 문서 위치, 작업 규칙 여섯 개, 팀이면 팀 규칙 세 개. Codex는 AGENTS.md를, Claude Code는 CLAUDE.md를 읽는다
docs/requirements/REQUEST.md nexi-init 고객의 요구사항 원문 그대로. 다시 쓰지 않는다
docs/requirements/REQ-ANALYSIS.md nexi-requirements analyze 모듈과 기능, 데이터와 관계, 업무 규칙, 화면과 사용자의 일, 품질 요구(원문에 없으면 "원문에 품질 요구 없음" 한 줄), 스택과 제약, 모호한 점. 항목마다 원문의 문장을 인용한다
docs/requirements/QUESTIONS.md nexi-requirements analyze 한 줄에 질문 하나와 원문 위치. 구현이나 검증을 막는 것만
docs/requirements/CLIENT_ANSWERS.md nexi-requirements answers 질문, 답, 근거 표. 근거는 고객, 원문, 수행사 결정 중 하나
docs/requirements/REQ-CONTEXT.md nexi-requirements decide, approve 맨 위 상태: 초안 또는 상태: 승인. 결정마다 번호(D1…), 원문 → 질문과 답 → 결정의 흐름, 출처(원문, 고객, 수행사). 품질 요구마다 요구 수준과 확인 방법. 스택 결정에 런타임과 패키지 관리자. 끝에 수행사가 고객 없이 정한 결정과 아직 답이 없는 질문. 승인할 때 결정마다 승인 상태(받아들임, 받아들이지 않음, 고객 확인 필요, 보류)와 "고객 확인이 남은 결정" 목록이 더해지고, 받아들이지 않은 결정에서만 나온 규칙은 빠진다. 구현 패턴의 적용 전 결정은 적용 범위와 함께 결정이 된다. 패턴 예외 결정은 패턴 예외: <패턴> · 조건 <번호>로 시작하고 패턴 판, 조건 문장, 고객 요구, 위험, 대신 하는 동작, 적용 범위, 고객 결정(이름, 날짜)을 가진다. [보안] 조건이면 보안·데이터 담당자(이름, 날짜)도 가진다. ## 패턴 결정 표에 해당할 수 있는 패턴의 적용 전 결정 항목마다 한 줄(패턴, 판, 항목, 결정, 세부)이 있다. 고객이 미룬 값은 제목이 보류:로 시작하는 결정(필요한 때, 정할 사람, 미룬 이유)이고 승인 상태가 보류다. 표와 결정의 형식은 키트의 nexi-req-check.sh가 검사한다(결정의 승인 상태)
docs/engineering/STANDARDS.md 코드 표준 작업(nexi-contract, nexi-implement) 코드 표준. 절은 적용 범위, 패키지와 가시성, 의존 방향, 공용 코드, 로깅, 문서 주석, 예외 목록. 규칙마다 지키는 예 하나와, make lint의 검사 이름이나 "리뷰가 본다"
docs/contracts/T<N>.md nexi-contract 작업 계약서. 맨 위 상태: 초안 또는 상태: 승인과 요구사항: <REQ-CONTEXT의 git hash-object>. 산출물 하나, 수용 기준(기준마다 확인 방법), 검증 명령(새 검사마다 실행 명령과 구현 전에 실패해야 할 구체적인 확인 조건, 회귀 검사, 준비 명령), 정해진 요구 네 가지의 해당 여부, 하지 않을 일, ## 적용 패턴(패턴마다 판, 적용 또는 해당 없음, 근거. 적용이면 조건마다 수용 기준, 해당 없음과 이유, 예외 가운데 하나와 적용 전 결정의 값과 결정 번호. 패턴 전체가 해당 없음이면 판, 이유, 근거만), 화면 작업이면 화면. 변경 작업과 나눈 작업, 골격 작업은 skill 참조의 추가 항목을 담는다. ## 표준 예외(표준과 다르게 하는 곳: 규칙, 이유, 대신 하는 동작, 범위, 정한 사람)와 ## 넘기는 일(받는 이슈와 한 줄)을 가진다.
docs/design/BRIEF.md nexi-design 디자인 기준. 맨 위 상태: 초안 또는 상태: 승인. 방향, 토큰(색 역할, 글자, 간격, 모서리, 그림자, 대비 4.5:1 이상), 구성 요소와 상태, 배치와 중단점, 날짜·금액 형식, 화면별 상태, 스크린샷에서 대조할 항목. 근거 없는 값은 (제안)
docs/evidence/T<N>.md nexi-implement 증거. 구현 중에는 맨 위에 상태: 작성 중이 있고, 증거를 완성하면 이 줄을 지운다. 검사한 상태(혼자 하면 코드 지문, 팀이면 검사한 commit), 기준 commit(혼자 하면 HEAD, 팀이면 origin/main), implemented by:(구현한 CLI와 모델), 환경(OS, 런타임과 패키지 관리자 버전), 수용 기준마다 검사와 종류(new면 실패한 명령, 종료코드, 실패한 확인 내용, regression이면 기준 실행과 이유), 마지막 수정 뒤 통과 결과, 찍은 PNG와 그때의 상태. 이슈의 넘겨받는 일: 댓글을 그대로 옮기고 그 일을 덮는 수용 기준을 함께 적은 ## 넘겨받는 일도 있다. 댓글이 없으면 없음이다.
docs/screens/T<N>/ nexi-implement(make screenshots) 화면 작업의 스크린샷 PNG
docs/reviews/T<N>.md nexi-review record, nexi-merge 판정 기록. 판정을 받은 그대로 날짜와 함께 차례로 덧붙인다. 이전 판정은 고치지 않는다. 판정 하나의 형식은 nexi-review 참조: 첫 줄 APPROVE·REVISE·BLOCK, 작업 번호, 혼자인지 팀인지, 리뷰한 commit과 기준 commit(base), 혼자 하면 두 지문, reviewer:, 기준별 판단, PNG별 대조, 사유
docs/FINAL.md nexi-finish 최종 보고. 맨 위 상태: 초안 또는 상태: 승인. 날짜와 시험한 main commit, 새 사본과 이 폴더의 결과표(사용한 버전 포함), ## 앱(주소, 띄운 프로세스, 명령 또는 띄우지 않은 이유), 수용된 작업과 수용되지 않고 닫힌 작업, 고객 확인이 남은 결정, ## 패턴 예외(수용된 작업이 쓴 예외와 그 계약서가 따른 판의 결정, 지금의 패턴 예외 결정과 쓰는 작업, 쓰이지 않은 예외), 역할별 seed 계정, 사람이 채울 확인 목록. ## 표준 점검(코드 표준과 어긋난 곳, 예외, 없음이나 점검할 표준 없음)과 ## 넘긴 일(넘긴 일마다 받음, 남음, 확인할 수 없음, 또는 없음)도 있다.
scripts/nexi-fingerprint.sh nexi-init, nexi-implement 지문 스크립트. 키트의 원본과 같아야 한다
scripts/nexi-isolated.sh nexi-init, nexi-implement 빈 환경 실행기. 명령 하나를 호출한 셸의 설정 없이 돌린다. 데이터베이스를 준비하는 검사와 깨끗한 사본의 단계가 쓴다. 키트의 원본과 같아야 한다
scripts/nexi-clean-copy.sh nexi-init, nexi-implement 깨끗한 사본 검사. 이 저장소의 사본을 임시 폴더에 만들고 scripts/nexi-clean-copy.steps의 단계를 하나씩 실행기로 돌린 뒤 사본이 그대로인지 본다. 키트의 원본과 같아야 한다
scripts/nexi-clean-copy.steps nexi-init, 골격 작업 README의 단계를 README의 순서대로 한 줄에 명령 하나씩. #로 시작하는 줄과 빈 줄은 건너뛴다. 줄 사이에 cd나 export는 이어지지 않는다

"상태" 줄의 뜻은 개념 참조에 있다.

GitHub 이슈의 줄

작업 이슈(라벨 task) 본문에서 skill이 읽는 줄이다. 한 줄에 하나씩, 정해진 글자 그대로 쓴다. 선행 작업: 줄은 나중에 단 댓글로 바꿀 수 있다. 본문과 댓글이 다르면 가장 나중의 줄을 따른다.

줄 쓰는 skill 뜻
선행 작업: #<a>, #<b> 또는 선행 작업: 없음 nexi-backlog, split, change 이 작업을 시작하기 전에 main에 수용돼야 하는 이슈. next는 이 줄이 없는 이슈를 고르지 않는다
나눔 출처: #<N> nexi-backlog split 이 이슈가 #<N>을 나눠 생겼다. 이어받는 것은 없고 main에서 새로 구현한다
변경 대상: T#<N> nexi-backlog change 이 이슈가 끝난 작업 T#<N>을 바꾸는 변경 작업이다
배포됨: 계약서에 배포 후 확인과 되돌리기 방법을 넣는다 nexi-backlog change 바꿀 작업이 이미 배포됐다
결함 출처: nexi-finish <commit> nexi-finish reject 최종 확인에서 찾은 결함으로 만든 이슈

skill이 남기는 이슈 댓글

댓글 남기는 skill 뜻
NEXI 수용: <commit> · reviewed files <지문>(혼자) nexi-merge 이 작업이 수용됐다. 수용 조건은 이 commit으로 검사한다
NEXI 수용: merge commit <M> · reviewed commit <R> · base <B>(팀) nexi-merge 같다
나눔: #<새 번호> · 저장 <위치> · … nexi-backlog split 이 이슈를 나눴다. 수용된 것이 아니다
차례 댓글(예: 계약서 초안 — PM 승인 차례 <해시>) 팀일 때 각 skill 다음 차례와 그때의 commit. 같은 해시의 댓글이 있으면 다시 달지 않는다
