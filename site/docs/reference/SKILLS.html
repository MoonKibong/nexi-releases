NEXI 키트 skill 참조

NEXI 키트 skill 참조

읽기 안내 — 누가: NEXI 키트로 프로젝트를 하는 사람 · 언제: skill 하나가 무엇을 하고 언제 멈추는지 알아야 할 때 · 읽은 뒤: 알맞은 프롬프트로 skill을 부르고, 멈췄으면 그 이유를 보고 다음 일을 정한다.

NEXI 키트에는 skill 열 개가 있다. skill마다 하는 일, 부르는 프롬프트, 멈추는 경우, 다음 프롬프트를 적었다. 자세한 절차는 각 skill의 원문(링크)에 있고, 둘이 다르면 원문을 따른다.

한눈에 보기

skill 하는 일 누가(팀)
nexi-init 저장소와 작업 규칙을 만든다 PM
nexi-requirements 요구사항을 분석하고 결정 문서를 만들어 승인받는다 FDE, 승인은 PM
nexi-backlog 작업 이슈를 만들고 다음에 할 작업을 고른다 PM, next는 FDE
nexi-contract 작업 하나의 계약서를 쓰고 승인받는다 FDE, 승인은 PM
nexi-design 화면의 디자인 기준(BRIEF)을 쓴다 FDE
nexi-implement 계약서대로 구현하고 검사 결과를 증거로 남긴다 개발자
nexi-review 구현하지 않은 agent가 리뷰하고 판정을 기록한다 검토자
nexi-merge APPROVE된 작업을 main에 넣고 이슈를 닫는다 PM
nexi-finish 새 사본에서 전체를 검증하고 최종 보고서를 승인받는다 PM
nexi-run(선택 기능) 구현, 리뷰, 판정 기록을 한 번에 돌린다 개발자

보통 순서는 nexi-init → nexi-requirements → nexi-backlog → 작업마다 nexi-contract(화면 기준 작업은 nexi-design도) → nexi-implement → nexi-review → nexi-merge → nexi-finish다.

모든 skill에 공통인 규칙

공통 규칙 원문

  • 입력이 빠졌거나 쓸 수 없으면(없는 이슈 번호, 읽을 수 없는 파일) 아무것도 하지 않고 무엇을 넣을지 알려 준다.
  • 답은 늘 다음: 줄로 끝난다. 다음에 넣을 프롬프트다. 다른 사람이나 다른 도구의 차례면 다음 (PM): …, 다음 (Codex, 읽기 전용): …처럼 밝힌다.
  • 같은 프롬프트를 다시 넣으면 끊긴 곳부터 이어 간다. 이미 만든 이슈나 commit을 또 만들지 않는다. 이미 끝난 일은 다시 하지 않고 상태를 알려 준다. 사람이 다시 할 것을 프롬프트에 적으면 한다.
  • stash, reset, clean, rebase, force push는 어느 skill도 하지 않는다.
  • GitHub나 git 원격이 실패하면 nexi-init/assets/nexi-gh-check.sh로 원인을 가린다. NOT_LOGGED_IN이면 사람이 로그인한다. BLOCKED(샌드박스가 네트워크나 키체인을 막음)면 다시 로그인하지 않고 샌드박스 밖 실행을 승인받거나, 사람이 자기 터미널에서 돌릴 명령을 준다. OK면 명령 자체의 문제다.
  • 팀 모드(AGENTS.md의 Mode: team)에서는 작업을 branch t<N>, 요구사항을 branch req에서 한다. 파일을 쓰는 skill은 끝에 commit과 push를 하고 이슈에 다음 차례를 댓글로 단다. nexi-finish 초안은 예외로 commit하지 않는다. PM만 할 수 있는 일은 PM: 줄의 사람인지 먼저 확인한다.

nexi-init

저장소를 만들고 작업 규칙을 세운다. 원문

프롬프트 누가(팀) 하는 일
/nexi-init <이름> + 요구사항 본인 비공개 GitHub 저장소, AGENTS.md(작업 규칙), docs/ 폴더, Makefile, README.md를 만들고 요구사항을 docs/requirements/REQUEST.md에 저장한다. 첫 commit을 push한다. 키트가 만들지 않은 이력이 있으면 그것을 검토할 작업을 안내한다
/nexi-init <이름> team + 요구사항 PM 위와 같고, AGENTS.md에 팀 규칙과 PM: 줄을 더하고 팀원을 초대한다
/nexi-init clone 누구나 지금 폴더 옆에 저장소를 새로 받는다(<이름>-2). 작업을 나눈 뒤나 nexi-finish reject 뒤에 쓴다

착수 합의에서 정한 forge=, agents=, data=를 함께 넣을 수 있다(환경 프로필).

멈추는 경우:

  • git이나 gh가 없다.
  • GitHub의 main에 이 skill이 만들지 않은 이력이 있고 로컬과 다르다.

이미 있는 파일은 덮어쓰지 않고 알린다.

다음: /nexi-requirements analyze. 팀이면 팀원이 초대를 받고 git clone한다. clone 뒤에는 새 폴더에서 하려던 프롬프트를 넣는다.

nexi-requirements

요구사항을 분석하고 결정 문서(REQ-CONTEXT.md)를 만들어 승인받는다. docs/requirements/만 쓰고 코드는 쓰지 않는다. 원문

프롬프트 누가(팀) 하는 일
/nexi-requirements analyze FDE 원문을 모듈, 데이터, 업무 규칙, 화면, 품질 요구, 스택으로 나눠 REQ-ANALYSIS.md에 적고, 모호한 점을 QUESTIONS.md의 질문으로 만든다
/nexi-requirements answers FDE 고객 답을 질문에 맞춰 CLIENT_ANSWERS.md에 정리한다. 답이 없으면 질문마다 답을 제안하고, 사람이 고친 뒤 저장한다
/nexi-requirements decide FDE 결정마다 번호(D1…)와 출처(원문, 고객, 수행사)를 단 REQ-CONTEXT.md 초안을 쓴다. 해당할 수 있는 구현 패턴의 적용 전 결정을 범위와 함께 결정이나 질문으로 올리고, 사람이 말한 패턴 예외를 조건 하나씩 적는다
/nexi-requirements approve PM 승인할 내용과 고객 확인이 남은 결정을 보여 주고, 사람이 승인한다고 답하면 REQ-CONTEXT.md를 승인으로 바꿔 commit한다. 팀은 req의 PR을 병합한다

approve는 다음 줄에 받아들이지 않는 수행사 결정: <번호 | 없음>을 함께 넣는다. 작업이 진행 중일 때 승인하면 다시 리뷰받을 작업을 먼저 보여 주고, 병합 뒤 리뷰를 기다리는 작업과 승인된 작업에 새 main을 반영한다. 결정 문서(REQ-CONTEXT.md)가 바뀐 병합이면 반영하지 않고, 그 작업들은 계약서부터 다시 쓰고 승인받는다.

멈추는 경우:

  • 받아들이지 않은 결정이나 미정 항목이 구현을 막는다(approve).
  • 패턴 예외에 조건 번호, 패턴 판, 조건 문장, 고객 요구, 위험, 대신 하는 동작, 적용 범위, 고객 결정자의 이름이나 날짜가 빠졌다. [보안] 조건인데 보안·데이터 담당자의 이름이나 날짜가 없다. 판이나 조건 문장이 키트와 다르다(approve).
  • 보여 준 뒤 승인 전에 파일이 바뀌었다.
  • main의 요구사항이 이미 바뀌었다.
  • 팀에서 커밋되지 않은 다른 변경이 있다(같은 단계의 쓰다 만 초안은 이어 쓴다).

다음: analyze → answers → decide → 사람이 검토 → approve → /nexi-backlog.

nexi-backlog

작업 이슈를 만들고, 다음에 할 작업을 고르고, 작업을 나누거나 바꾼다. 원문 · 작업 상태

프롬프트 누가(팀) 하는 일
/nexi-backlog [우선순위 메모] PM 승인된 REQ-CONTEXT로 하루 이하의 작업 이슈를 만든다. 골격, 코드 표준, 디자인 시스템(화면이 있으면), 기능 순서이고, 이슈마다 선행 작업: 줄을 단다. 최종 보고가 승인된 뒤에는 만들지 않고 change나 요구사항으로 안내하며, 그 뒤에 승인된 새 결정의 이슈만 만들 수 있다
/nexi-backlog next FDE 선행 작업이 모두 끝난 이슈 가운데 번호가 가장 작은 것을 고른다. 팀이면 나에게 지정됐거나 아무도 맡지 않은 이슈만 본다. 고른 작업에 필요할 수 있는 보류 결정과, 기록된 반복 지적을 모두 보여 준다
/nexi-backlog status 누구나(팀) 열린 작업마다 상태, 담당자, 다음에 할 사람과 넣을 프롬프트를 표로 보여 준다. 보류 결정의 수와 반복 지적도 보인다. 아무것도 바꾸지 않는다
/nexi-backlog assign <N> <아이디> PM(팀) 그 사람을 이슈의 담당자로 지정한다
/nexi-backlog split <N> PM 다음 줄에 적은 방법대로 작업을 작은 이슈로 나누고, 원래 이슈는 "나눔"으로 닫는다
/nexi-backlog change PM 다음 줄에 적은 바꿀 내용으로 끝난 작업을 바꿀 변경 이슈를 만든다. 이슈마다 결함과 개선의 구분, 예상 시간, 선행 작업을 보이고 고른 것만 만든다. 요구사항을 바꾸는 변경이면 결정 문서부터 바꾸라고 멈춘다

next는 선행 작업: 줄이 없거나, 없는 이슈를 가리키거나, 서로 순환하는 이슈를 고르지 않고 목록으로 보여 준다. 열린 이슈는 있는데 고를 것이 없으면 그 문제를 먼저 푼다.

멈추는 경우:

  • 요구사항이 승인되지 않았다.
  • 작업 이슈를 만들 때 커밋되지 않은 변경이 있다.
  • 나누는 방법이나 변경 종류가 분명하지 않다(묻는다).

다음: next → /nexi-contract <N>. 열린 작업이 없으면 /nexi-finish.

nexi-contract

작업 하나의 계약서(docs/contracts/T<N>.md)를 쓰고 승인받는다. 코드는 쓰지 않는다. 원문

프롬프트 누가(팀) 하는 일
/nexi-contract <N> 담당 FDE 해당할 수 있는 구현 패턴을 보이고, 수용된 계약서에 같은 판의 적용이 없는 패턴마다 적용, 해당 없음, 예외를 묻는다. 산출물 하나, 수용 기준과 확인 방법, 검증 명령, 하지 않을 일, ## 적용 패턴, 화면 작업이면 화면을 적은 계약서 초안을 쓴다. 요구사항과 맞는지, 검증 명령이 부르는 것이 저장소에 있거나 이 작업이 만들고 바깥 도구는 README가 준비하라고 한 것인지 스스로 검사한 결과를 맞음, 고침, 질문 표로 함께 보여 준다
/nexi-contract <N> approve PM ## 적용 패턴을 검사한 뒤, 보여 준 계약서를 사람이 승인하면 상태: 승인으로 바꾼다. 화면 작업이면 BRIEF도 함께 승인한다

승인한 계약서를 구현을 시작한 뒤에 고칠 때(구현 중 고침)는 이슈 담당자가 /nexi-contract <N>으로 초안을 쓴다. 초안 맨 위의 ## 고친 이유에 이전 승인본, 막힌 사실, 바뀌는 기준, 고를 것을 적는다. approve는 이전 승인본과의 기준 차이 표와 보안 점검 결과를 보여 주고, (제안)을 고르면 그대로 승인한다.

작업 종류에 따라 계약서에 더 넣는 것:

  • 골격 작업: 런타임 버전과 깨끗한 사본 검사. make test, make lint, make build가 아직 없으므로 새 검사로 넣는다.
  • 코드 표준 작업: docs/engineering/STANDARDS.md의 절(적용 범위, 패키지와 가시성, 의존 방향, 공용 코드, 로깅, 문서 주석, 예외 목록)과, 기계로 확인할 규칙마다 make lint의 검사. 검사의 시험이 규칙을 어긴 예를 거부하는지 확인한다.
  • 모든 작업: 코드 표준을 따르고, 다르게 해야 하면 ## 표준 예외. 다른 작업에 넘기는 일은 ## 넘기는 일. 이슈의 넘겨받는 일: 댓글은 수용 기준.
  • 변경 작업(변경 대상:): 원래 작업의 기준 가운데 지킬 것을 회귀 검사로 넣는다. 배포된 작업이면 배포 후 확인과 되돌리기도 넣는다.
  • 나눈 작업(나눔 출처:): 원래 작업에서 이어받는 것 없이 새로 쓴다.

승인 질문에 "승인한다. nexi-run까지"라고 답하면 같은 대화에서 nexi-run <N>으로 이어 간다. Claude Code에서만 되고, 팀이면 승인한 PM이 그 작업을 직접 구현할 때만 된다.

멈추는 경우:

  • 요구사항이 승인되지 않았거나 main과 다르다.
  • 골격 작업인데 REQ-CONTEXT에 런타임이나 패키지 관리자가 없다.
  • 적용하는 패턴의 적용 전 결정이 REQ-CONTEXT에 없거나, 받아들임이 아니거나, 이 작업을 범위에 넣지 않는다. 예외로 답한 조건에 패턴, 판, 조건, 범위, 대신 하는 동작이 맞는 받아들임 패턴 예외 결정이 없다. 이때 작업 트리의 변경이 쓰다 만 이 계약서뿐이면 ~/nexi-drafts/에 복사하고 해시를 확인한 뒤 지운다(commit된 초안이면 마지막 commit으로 되돌린다). 다른 변경이 있으면 아무것도 바꾸지 않는다. 다시 넣으면 새로 쓰고 보관한 초안은 참고로만 보인다.
  • ## 적용 패턴 검사가 실패했다(approve): 조건 줄이 빠졌거나, 판이 다르거나, 인용한 결정이 받아들임이 아니거나 이 작업을 덮지 않거나, 값에 결정에 없는 부분이 있다.
  • 보여 준 뒤 승인 전에 계약서나 요구사항이 바뀌었다.
  • 팀에서 다른 사람에게 지정된 이슈다.

다음: /nexi-contract <N> approve. 디자인 시스템 작업과 디자인 변경 작업은 그 전에 /nexi-design <N>. 승인 뒤 /nexi-implement <N>.

nexi-design

화면의 디자인 기준 docs/design/BRIEF.md를 쓴다. 디자인 시스템 작업과 디자인 변경 작업에서 쓰고, 코드는 쓰지 않는다. 원문

프롬프트 누가(팀) 하는 일
/nexi-design <N> [원하는 분위기] FDE REQ-CONTEXT의 화면 결정과 사람이 말한 선호로 BRIEF 초안을 쓴다. 색, 글자, 간격, 구성 요소, 화면 폭별 배치, 화면별 상태를 담고, 근거 없는 값은 (제안)으로 적는다. 디자인 변경 작업이면 이슈가 요청한 값만 바꾼다

멈추는 경우:

  • 팀에서 커밋되지 않은 다른 변경이 있다(쓰다 만 BRIEF는 이어 쓴다).

다음: /nexi-contract <N> approve. 이것이 BRIEF도 승인한다. 승인 뒤 BRIEF를 고치면 다시 초안이 된다.

nexi-implement

승인된 계약서대로 구현하고, 검사 결과를 증거 파일에 남긴다. 리뷰 지적을 고칠 때도 같은 프롬프트를 쓴다. 원문

프롬프트 누가(팀) 하는 일
/nexi-implement <N> 개발자 새 검사가 실패하는 것을 먼저 보고, 구현한 뒤 모든 검사를 통과시킨다. 화면 작업이면 계약서가 정한 제목이나 상태 제목이 보이는지 확인한 뒤 스크린샷을 찍는다. 결과는 docs/evidence/T<N>.md에 적는다. 혼자면 commit하지 않고, 팀은 commit과 push를 하고 PR을 연다

구현 전부터 통과하는 검사는 그 동작이 이미 있다는 뜻이다. 일부러 실패하게 만들지 않고 regression으로 적는다.

멈추는 경우:

  • 계약서가 승인되지 않았거나, 계약서를 쓴 뒤 요구사항이 바뀌었다.
  • 화면 작업인데 BRIEF가 승인되지 않았다.
  • 승인한 계약서대로 끝낼 수 없다(리뷰 지적이든, 구현하거나 main을 병합하다 드러났든). 계약서를 다르게 읽고 진행하지 않는다. 작업을 남기고(팀은 commit과 push), 이슈 담당자면 nexi-contract로 고친 초안을 쓴다. 담당자가 아니면 FDE 차례 댓글을 단다.
  • 리뷰가 BLOCK이거나 REVISE가 세 번 이어졌다. 사람(팀은 PM)이 원인을 정할 때까지 멈춘다. 원인이 계약서이면 팀은 PM의 결정: 계약서 — 개발자 차례 댓글, 혼자면 프롬프트 다음 줄의 결정: 계약서가 있을 때만 이어 간다.
  • 이 작업과 관계없는 변경이 있거나, merge 충돌이 작업 범위 밖이다.

다음: 혼자면 Codex를 읽기 전용으로 열고 nexi-review skill로 T#<N>을 리뷰해라.를 넣는다(Codex가 구현했으면 Claude Code로). 팀이면 /nexi-review <N> prepare.

nexi-review

구현하지 않은 agent가 읽기 전용으로 리뷰하고, 그 판정을 기록한다. 원문 · 판정 형식

프롬프트 누가(팀) 하는 일
nexi-review skill로 T#<N>을 리뷰해라. 리뷰 agent 수용 기준마다 코드와 증거를 보고, 화면이면 스크린샷을 BRIEF와 대조한다. 코드 표준이 있으면 변경을 표준의 절마다 대조하고, 증거의 ## 넘겨받는 일이 수용 기준과 구현에 있는지 본다. APPROVE, REVISE, BLOCK 중 하나를 낸다. 파일을 바꾸지 않고 검사도 돌리지 않는다
/nexi-review <N> prepare 검토자(팀) 리뷰할 commit을 받고 리뷰할 agent를 고르게 한다. 리뷰를 백그라운드로 돌려 판정을 자동으로 기록하거나, 리뷰 프롬프트를 클립보드에 복사한다
/nexi-review <N> record 검토자 붙여 넣은 판정의 형식을 검사하고 docs/reviews/T<N>.md에 덧붙인다. 팀은 commit과 push를 하고 PR에 댓글을 단다
/nexi-review <N> confirm 검토자(팀) 개발자가 직접 기록한 APPROVE(nexi-run 등)를 검토자가 확인하고 이슈에 PM 병합 차례를 알린다

리뷰 agent는 구현한 agent와 달라야 한다. Claude Code가 구현했으면 Codex, Codex가 구현했으면 Claude Code가 리뷰한다. 같은 agent밖에 없으면 멈추고 묻는다.

판정 기준:

  • BLOCK: 사람이 정해야 할 것이 있다. 예: 계약서가 승인되지 않았거나 계약서를 쓴 뒤 요구사항이 바뀌었다. 판정은 사람이 정할 것(항목마다 원인 후보)과 결정 뒤 고칠 것을 나눠 적는다. 정할 것이 없으면 REVISE다.
  • REVISE: 기준이 충족되지 않았다. 증거나 스크린샷이 없거나 낡았다. 새 검사가 기준이 아닌 다른 이유로 실패했다.

멈추는 경우:

  • 리뷰하는 사이 파일이 바뀌었다.
  • 판정이 형식 검사를 통과하지 못했다(record).

다음: 리뷰 agent의 판정을 붙여 /nexi-review <N> record로 기록한다(prepare에서 백그라운드 리뷰를 골랐으면 자동으로 기록된다). 기록 뒤 APPROVE면 /nexi-merge <N>(팀에서 개발자가 기록했으면 먼저 confirm). REVISE면 /nexi-implement <N>. BLOCK이나 연속 세 번째 REVISE면 사람(팀은 PM)이 원인을 정한다. 원인별 다음 차례는 작업 순환에 있다.

nexi-merge

APPROVE된 작업을 main에 넣고 이슈를 닫는다. 원문 · 수용 조건

프롬프트 누가(팀) 하는 일
/nexi-merge <N> PM 혼자면 작업 파일만 commit해 push하고, 팀이면 PR을 squash 병합한다. 수용 조건을 모두 통과하면 이슈에 NEXI 수용 댓글을 달고 닫는다

혼자 작업하며 판정을 아직 기록하지 않았으면 APPROVE 판정을 함께 붙여 넣는다. 병합한 뒤 수용 조건이 깨지면 이슈를 다시 열고 PM이 정한다. 팀에서는 이 병합으로 뒤처진 리뷰 대기 작업과 승인된 작업에 /nexi-implement <M> refresh를 이어서 돌린다. 각 작업의 승인된 계약서 안에서 새 main을 합치고 검사와 증거를 다시 만든다.

멈추는 경우:

  • 마지막 판정이 APPROVE가 아니다.
  • 리뷰 뒤 코드나 계약서가 바뀌었다(새 리뷰가 필요하다).
  • 리뷰 뒤 main이 앞서 나갔다(개발자가 /nexi-implement <N>을 다시 하고 새 리뷰를 받는다).
  • 이 작업과 관계없는 파일이 있다.

다음: /nexi-backlog next. 열린 작업이 없으면 /nexi-finish.

nexi-finish

새로 받은 사본에서 전체를 검증하고, 사람이 앱을 써 본 뒤 최종 보고서를 승인한다. 원문

프롬프트 누가(팀) 하는 일
/nexi-finish PM 열린 작업이 없는지 확인하고, 새 사본에서 README 순서대로 설치부터 lint까지 돌린다. 이 폴더에서는 README가 정한 방법이 있으면 새 DB로 준비하고 앱을 이 컴퓨터에만 띄운다(포트가 쓰이고 있으면 바꿀지 묻는다). 결과, 패턴 예외, 둘러볼 목록을 docs/FINAL.md 초안에 적는다. commit하지 않는다
/nexi-finish reject <결함> PM 결함마다 작업 이슈를 만들고, 띄운 앱을 멈추고, 초안을 ~/nexi-final/에 저장한 뒤 작업 트리에서 지운다
/nexi-finish approve PM 둘러보기 목록의 모든 행에 사람이 적은 결과가 있어야 한다. 실패하거나 돌리지 않은 단계가 있으면 고객이 받아들였는지 묻는다. 승인한 docs/FINAL.md를 main에 넣는다

멈추는 경우:

  • 열린 작업이 있다.
  • 작업 트리에 FINAL.md 말고 다른 변경이 있다.
  • main에 리뷰받지 않은 외부 commit이 있다(이미 있는 저장소에 팀 모드 들이기 6).
  • 둘러보기 목록에 빈 행이나 이상 있음이 있다(approve). 빈 행을 채우거나 reject한다.
  • 시험한 뒤 main이 움직였다(approve).

다음: 초안 뒤 사람이 앱을 써 보고 둘러보기 목록의 행마다 확인함, 이상 있음: <무엇>, 확인 안 함 가운데 하나를 적은 뒤 approve 또는 reject <결함 내용>. reject 뒤 /nexi-backlog next. approve 뒤에는 할 일이 없다.

nexi-run (선택 기능)

구현, 리뷰, 판정 기록을 한 번에 돌린다. Claude Code에서만 쓴다. 원문

프롬프트 누가(팀) 하는 일
/nexi-run <N> 개발자 nexi-implement 규칙으로 구현하고, Codex(gpt-6-astra)가 읽기 전용으로 리뷰한 판정을 기록한다. 첫째와 둘째 REVISE면 고치고 다시 리뷰받는다. 병합은 하지 않는다

멈추는 경우:

  • APPROVE, BLOCK, 연속 세 번째 REVISE가 나왔다. 시작할 때 기록된 마지막 판정이 지금 파일에 그대로 해당하고 이 셋 가운데 하나여도 구현하지 않고 그 판정을 보여 준다.
  • Codex가 실패하거나 시간이 초과됐거나 판정이 아닌 답을 냈다.

다음: APPROVE면 판정과 증거를 읽은 뒤 /nexi-merge <N>(팀은 먼저 검토자가 /nexi-review <N> confirm).
