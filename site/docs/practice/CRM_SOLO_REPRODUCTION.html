혼자 CRM 만들어 보기

혼자 CRM 만들어 보기

읽기 안내 — 누가: 혼자서 NEXI 방식으로 CRM을 처음부터 만들어 볼 사람 · 언제: 빈 폴더 하나와 요구사항 문서 하나만 있을 때 · 읽은 뒤: 단계마다 프롬프트를 넣고, AI가 만든 결과를 읽고 승인해 검토를 마친 CRM까지 간다.

사람은 프롬프트를 쓰고, AI가 만든 문서와 결과를 읽고, 승인한다. git, GitHub, 빌드, 테스트 같은 명령은 모두 AI가 실행한다. 코드와 문서는 Claude Code가 쓰고, 리뷰는 Codex에서 다른 회사의 모델 gpt-6-astra가 한다. 단계마다 쓰는 절차는 NEXI 키트의 skill에 들어 있어, 프롬프트는 대부분 skill 이름으로 시작한다. 사람이 터미널에 직접 치는 것은 폴더를 만들고 claude와 codex를 여는 명령뿐이다. 작업은 검토가 끝난 뒤에만 main에 들어간다.

준비물. 로그인한 Claude Code 또는 cucu, Codex, GitHub 계정, Chrome. GitHub CLI는 Step 1에서 AI가 확인하고 설치나 로그인을 돕는다. Node.js와 패키지 관리자는 REQ-CONTEXT에서 스택을 정한 뒤, Step 4 골격 작업의 계약서(4-1)가 버전을 정하고, 구현(4-3)에서 AI가 그 버전을 설치한다.

Step 0. 키트를 설치한다

키트 설치·배포 안내에서 배포 상태를 확인한다. 공개 다운로드가 준비되지 않았으면 키트를 받은 뒤 진행한다. 사용할 agent를 열고 다음과 같이 요청한다.

Claude Code를 쓰면 이렇게 넣는다.

~/Downloads/nexi-kit.zip 안의 INSTALL.txt를 읽고 그대로 설치해라.

cucu를 쓰면 이렇게 넣는다.

~/Downloads/nexi-kit.zip을 ~/.cucu/skills/ 경로에 압축 해제하고, 앞으로 !nexi- 로 시작하는 명령어를 입력하면 이 경로의 파일을 읽고 지침에 따라 수행하도록 설정해라.

CuCu에서는 이 문서의 /nexi-… 프롬프트를 !nexi-…로 바꿔 넣는다. 지금 키트는 CuCu를 agent로 받지 않아 skill이 첫 환경 확인에서 멈춘다. 지원은 준비 중이다(P#275). CuCu TUI는 /로 시작하는 입력을 자기 명령으로 받는다. CuCu를 써도 리뷰하는 Codex에는 키트가 필요하다. 그래서 먼저 Claude Code나 Codex에 위의 INSTALL.txt 프롬프트를 넣어 스무 칸을 "같음"으로 맞추고, 그다음 CuCu 프롬프트로 ~/.cucu/skills에 푼다. CuCu 위치는 아직 비교 표에 없으므로(P#275) 그곳에는 skill 폴더 열 개가 있는지만 본다.

설치 절차는 zip의 INSTALL.txt에 있다. AI가 zip의 SHA-256과, skill마다 두 설치 위치(~/.claude/skills, ~/.codex/skills)의 비교 표를 보여 준다.

확인

표의 스무 칸이 모두 "같음"인지 본다. 모두 "같음"이면 Claude Code와 Codex를 닫았다가 다시 열고 Step 1로 간다. SHA-256은 적어 둔다. 키트를 새로 받으면 이 Step을 다시 한다.

  • "다름"이 있으면 예전에 설치한 같은 이름의 skill이다. AI가 예전 것을 백업하고 바꿀지 묻는다. "바꿔라"라고 답한다. 예전 skill을 계속 쓰려면 이 가이드로 진행하지 않는다.
  • "없음"이 남으면 AI가 보여 준 빠진 파일과 오류를 보고 원인을 해결한 뒤 같은 프롬프트를 다시 넣는다.

Step 1. 프로젝트를 시작한다

mkdir crm
cd crm
claude

Claude Code에 넣는다. 요구사항 원문 자리에는 부록의 한국어 글이나 영어 글을 그대로 붙여 넣는다.

/nexi-init crm
요구사항 원문:
<부록의 글을 붙여 넣는다>

AI가 GitHub 로그인을 요청하면 브라우저에서 마친다. 설치할 도구가 있다고 하면 "설치해라"라고 답한다.

확인

AI가 알려 준 GitHub 저장소 주소가 열리는지, AGENTS.md에 작업 규칙 여섯 개가 있는지 본다.

Step 2. 요구사항을 확정한다

네 프롬프트를 차례로 넣는다. 이 연습에서는 내가 고객이자 수행사다.

순서 넣는 프롬프트
2-1 /nexi-requirements analyze
2-2 /nexi-requirements answers
2-3 /nexi-requirements decide
2-4 /nexi-requirements approve

2-1. 요구사항 분석

/nexi-requirements analyze
확인

docs/requirements/REQ-ANALYSIS.md에 원문의 여섯 모듈, 대시보드, seed 데이터, 기술 스택, "깔끔하고 현대적인 UI"(clean modern UI) 같은 화면 요구가 모두 있는지 본다. 빠진 것은 AI에게 말한다.

2-2. 질문에 답하기

/nexi-requirements answers

AI가 질문마다 제안한 답을 표로 보여 준다. 바꿀 답을 말한 뒤 "이대로 저장해라"라고 한다. 실제 프로젝트라면 QUESTIONS.md를 고객에게 보내고, 받은 답을 /nexi-requirements answers 다음 줄에 붙여 넣는다.

확인

docs/requirements/CLIENT_ANSWERS.md에 질문마다 답과 근거가 있는지, AI가 보여 준 "아직 답이 없는 질문" 목록이 비었는지 본다.

2-3. 결정 문서

/nexi-requirements decide

검토한다. docs/requirements/REQ-CONTEXT.md가 뒤의 모든 작업의 근거다. 모듈, 화면, 품질 요구가 빠짐없이 결정으로 들어갔는지, 원문과 어긋나는 결정이 없는지 읽는다. 끝에 있는 "수행사가 고객 없이 정한 결정" 목록에서 받아들일 것과 받아들이지 않을 것을 정한다. 고칠 것은 AI에게 말한다.

2-4. 요구사항 승인

다 맞으면 넣는다.

/nexi-requirements approve
받아들이지 않는 수행사 결정: <번호, 없으면 "없음">

AI는 먼저 받아들이지 않은 결정과 아직 정하지 않은 결정마다 구현이나 검사를 막는지 표로 보여 준다.

  • 막는 결정이 있으면 AI는 아무것도 바꾸지 않고 멈춘다. 결정마다 고를 수 있는 것(결정을 고친다, 그 범위를 뺀다, 다른 결정과 맞춘다)을 보고 하나를 정한다. 정한 내용을 /nexi-requirements decide 다음 줄에 적어 넣고, 2-3부터 다시 한다.
  • 막는 결정이 없으면 AI가 본문에서 뺄 줄, 결정마다의 승인 상태, 고객 확인이 남은 결정 목록, 승인과 함께 commit할 요구사항 파일 목록을 보여 주고 승인할지 묻는다. 읽고 맞으면 "승인한다"라고 답한다. 목록에 없는 파일이 바뀌어 있으면 AI가 승인하지 않고 그 파일을 보여 준다.
확인

맨 위 줄이 상태: 승인인지, 받아들이지 않은 결정의 규칙이 본문에 남지 않았는지, 고객 확인이 남은 결정 목록이 있는지 본다.

승인을 기록하거나 push하다 끊겼으면 같은 프롬프트를 다시 넣는다. skill이 이미 만든 commit을 확인해 이어 간다. 파일만 바꾸고 commit 전에 끊겼으면 AI가 그 변경을 승인하는지 다시 묻는다.

Step 3. 작업 목록을 만든다

/nexi-backlog
확인

AI가 보여 준 이슈 표가 골격 → 코드 표준 → 디자인 시스템 → 기능 순서인지, 이슈마다 적힌 선행 작업이 맞는지, 하루를 넘을 것 같은 이슈가 없는지 본다. 크면 쪼개 달라고 한다.

Step 4. 작업 하나를 끝낸다 (작업마다 반복)

작업을 시작할 때마다 넣는다. AI가 선행 작업이 모두 원격 main에 수용된 열린 이슈 가운데 번호가 가장 작은 것을 고른다.

/nexi-backlog next

AI가 멈췄으면 앞 작업이 덜 끝난 것이다. AI가 알려 준 대로 한다. push하지 못한 반영이면 /nexi-merge <번호>를 다시 넣고, 그 밖이면 멈췄을 때처럼 하던 단계의 프롬프트를 다시 넣는다. 아래 <N>은 고른 이슈 번호다.

4-1. 계약서

/nexi-contract <N>

AI가 계약서를 쓰고 REQ-CONTEXT, 끝난 작업의 계약서, seed 데이터, 역할별 권한, 디자인 기준과 맞는지 스스로 점검한 표를 함께 보여 준다. 첫 작업(골격)이면 계약서에 실행 환경 버전과 테스트 준비 순서가 들어간다. REQ-CONTEXT에 런타임이나 패키지 관리자가 없다고 AI가 멈추면 2-3으로 돌아가 /nexi-requirements decide에 그 결정을 적어 넣고 /nexi-requirements approve로 승인한 뒤 /nexi-contract <N>을 다시 넣는다.

계약서를 쓰기 전에 AI가 해당할 수 있는 구현 패턴을 이유와 함께 보이고, 앞서 수용된 작업이 같은 판으로 적용하지 않은 패턴마다 적용, 해당 없음, 예외를 묻는다 (작업 순환). 고객 목록 같은 목록 작업이면 권한 부여와 데이터 격리, 페이지네이션과 조회, 입력 검증과 오류 응답, 테스트 데이터 격리가 나오는지 본다. 초간단 요구사항처럼 로그인과 역할이 없으면 인증과 권한 패턴이 해당 없음인지 본다. 패턴이 요구하는 값이 REQ-CONTEXT에 없다고 AI가 멈추면 2-3으로 돌아가 decide와 approve로 그 값을 정한 뒤 /nexi-contract <N>을 다시 넣는다.

docs/contracts/T<N>.md와 점검 표를 읽는다. 산출물이 하나인지, 수용 기준마다 확인 방법이 있는지, 새 검사가 그 기준을 실제로 검사하는지, 화면 작업이면 찍을 화면이 적혀 있는지 본다. 점검 표에 "질문"이 있으면 정해서 AI에게 말한다. 고칠 것은 AI에게 말한다.

디자인 시스템 작업(세 번째 작업)이면 이어서 디자인 기준을 쓰게 한다. 원하는 분위기가 있으면 같이 적는다.

/nexi-design <N>

docs/design/BRIEF.md의 분위기, 색, 글꼴, 간격, 구성 요소가 원하는 모습인지, (제안) 표시가 붙은 값이 괜찮은지 본다. 고칠 것은 AI에게 말한다.

4-2. 승인

다 맞으면 승인한다. 디자인 시스템 작업이면 "docs/design/BRIEF.md도 승인한다." 줄을 함께 넣는다. 이 줄이 없으면 AI가 BRIEF도 승인할지 묻는다. 승인하지 않은 BRIEF는 초안으로 남는다.

/nexi-contract <N> approve
docs/design/BRIEF.md도 승인한다.
확인

AI가 보여 준 계약서와 BRIEF의 첫 줄이, 디자인 시스템 작업이면 둘 다 상태: 승인인지 본다. 하나라도 상태: 초안이면 /nexi-implement가 멈춘다.

4-3. 구현

/nexi-implement <N>
확인

보고에 수용 기준마다의 증거, 새 검사마다 Red의 실패 이유, 마지막 수정 뒤의 Green 결과, 실제로 쓴 Node.js와 패키지 관리자 버전, 다시 찍은 PNG 목록이 있는지 본다. 이미 있던 동작을 확인하는 검사는 Red 대신 회귀 검사로 표시되고, 바꾸기 전의 통과 결과와 근거가 함께 적힌다. 검사 개수만 보지 말고, 각 검사가 수용 기준의 어떤 동작을 확인하는지 읽는다. 화면 작업이면 docs/screens/T<N>/의 PNG를 열어 직접 본다.

계약서를 승인한 뒤 REQ-CONTEXT가 바뀌었으면 AI가 구현하지 않고 멈춘다. /nexi-contract <N>으로 계약서를 다시 쓰게 하고 4-2처럼 승인한 뒤 /nexi-implement <N>을 다시 넣는다.

4-4. 리뷰

터미널을 하나 더 열어 지금 작업하는 폴더(Step 1에서 만든 crm, 작업을 나눈 뒤에는 새로 받은 폴더)로 가서 Codex를 모델 gpt-6-astra, 읽기 전용으로 연다.

cd crm   # 작업을 나눈 뒤에는 새로 받은 폴더
codex --model gpt-6-astra --sandbox read-only

Codex에서 /status로 모델이 gpt-6-astra인지 본다. 이 모델을 쓸 수 없다고 나오면 다른 모델로 리뷰하지 않고 멈춘다. 어느 모델로 바꿀지는 사람이 정한다. Claude Code가 "Astra"라는 이름을 붙여 돌린 검토는 이 리뷰가 아니다.

nexi-review skill로 T#<N>을 리뷰해라.

Codex가 쓰기 권한을 달라고 하면 거절한다. 리뷰하는 쪽은 파일을 바꾸지 않는다. 판정의 기준별 판단에 수용 기준마다 판단이 있는지, 화면 작업이면 PNG별 대조에 PNG마다 줄이 있는지 본다. 빠졌으면 Codex에 "근거가 빠졌다. 처음부터 다시 리뷰해라"라고 한다.

판정이 나오면 무엇이든(APPROVE, REVISE, BLOCK) 파일을 고치기 전에 Codex의 답을 복사해 Claude Code에 넣는다.

/nexi-review <N> record
<Codex의 답을 붙여 넣는다>

AI가 판정을 docs/reviews/T<N>.md에 그대로 덧붙여 남기고 다음 차례를 알려 준다. 이 파일은 commit하지 않고 4-6에서 작업과 함께 commit된다. 다음 리뷰는 이 파일의 앞선 판정을 읽는다. 형식이 빠진 판정이거나 리뷰 뒤에 파일이 바뀌었으면 AI가 남기지 않고 멈춘다. 그때는 Codex를 새로 열어 리뷰를 다시 받는다.

APPROVE를 받은 뒤에는 Claude Code에서 파일을 고치지 않는다. 코드, 계약서, 증거, 스크린샷 가운데 하나라도 바뀌면 /nexi-merge가 멈추고, 리뷰를 다시 받아야 한다.

Step 5. 끝낸다

/nexi-finish

AI가 원격 main을 새로 clone한 폴더에서 README 순서대로 설치, DB 준비와 seed, build, test, lint를 돌리고 README의 실행 명령으로 앱이 뜨는지 본 결과 표와, 앱을 띄울 지금 폴더의 결과 표를 따로 보여 준다. 그리고 이 컴퓨터에서만 열리는 주소, 역할마다 로그인할 seed 계정, 써 볼 목록을 알려 준다.

준비 단계(설치, DB 준비와 seed, build) 가운데 하나라도 실패하면 AI는 앱을 띄우지 않는다. 실패한 단계, 그 때문에 돌리지 않은 단계, 돌린 데까지의 결과를 적은 docs/FINAL.md 초안을 남기고 멈춘다. 이때는 써 보지 않고 아래의 /nexi-finish reject로 실패를 작업으로 돌려보낸다.

README의 포트를 이미 다른 프로그램이 쓰고 있으면 AI는 앱을 띄우지 않고 그 프로그램도 멈추지 않는다. 어느 프로그램인지 적은 초안을 남긴다. 그 프로그램을 끝낼지는 사람이 정하고, 끝낸 뒤 /nexi-finish를 다시 넣는다.

앱이 떴으면 주소를 브라우저로 열어 직접 써 본다. 이 앱은 clone 폴더가 아니라 지금 작업하는 폴더에서 seed 데이터로 띄운 것이다. 다음을 본다.

  • 대시보드의 KPI 카드와 차트, 고객·거래·활동·작업·예측·직원 화면이 원문대로 동작한다.
  • 화면마다 seed 데이터가 보인다.
  • admin, manager, rep으로 각각 로그인하면 볼 수 있는 데이터와 할 수 있는 일이 결정대로 다르다.
  • 휴대폰 너비와 데스크톱 너비에서 화면이 디자인 기준과 맞는다.

본 결과를 docs/FINAL.md의 둘러보기 목록에 줄마다 확인함, 이상 있음: <무엇>, 확인 안 함 가운데 하나로 적는다. 파일을 직접 고치거나 AI에게 줄마다 말한다. 빈 줄이 남아 있으면 /nexi-finish approve가 멈춘다.

clone 폴더의 검사가 실패했거나 써 보다 이상한 곳이 있으면 승인하지 않고 결함을 작업으로 돌려보낸다.

/nexi-finish reject <결함 내용>

AI가 결함마다 task 이슈를 만들고, 앱을 멈추고, commit하지 않은 docs/FINAL.md 초안을 ~/nexi-final/ 아래에 저장한 뒤 지운다. 초안에 적힌 실패 가운데 결함 내용에 없는 것이 있으면 AI가 결함으로 더할지 묻는다. 중간에 끊겨 같은 프롬프트를 다시 넣어도 이미 만든 이슈는 다시 만들지 않는다. 초안이 없거나 앱을 띄우지 않았으면 그 단계는 건너뛴다고 알려 준다. 다른 변경이 있어 AI가 멈췄으면 /nexi-init clone으로 옆 폴더에 저장소를 새로 받아, 결함 작업은 그 폴더에서 한다. 지금 폴더는 그대로 둔다. 결함 작업이 Step 4로 수용되면 수용된 main에서 /nexi-finish를 다시 한다. 저장해 둔 초안은 비교용이며 승인하지 않는다.

docs/FINAL.md를 읽는다. 결과 표가 실제로 돌린 명령의 결과와 같은지, 실패했거나 돌리지 않은 검사, 아직 고객 확인이 필요한 결정, 써 보며 만든 이슈가 빠짐없이 적혀 있는지 본다. 맞으면 승인한다.

/nexi-finish approve

승인을 push하다 끊겼으면 같은 프롬프트를 다시 넣는다. skill이 이미 만든 commit이 승인한 docs/FINAL.md만 더한 것인지, 시험한 main 위에 있는지 확인한 뒤 이어 간다. docs/FINAL.md를 상태: 승인으로 바꾼 뒤 commit 전에 끊겼으면 AI가 그 파일을 승인하는지 다시 묻는다.

끝낸 뒤 바꾸기

최종 보고를 승인한 뒤에 결함을 찾았거나, 만든 것을 바꾸거나, 새 요구사항이 생기면 reject가 아니라 아래 길로 간다. 어느 길로 갈지는 끝내기와 넘기기의 표에 있다.

결함이나 바꿀 동작이면 이렇게 넣는다. 둘째 줄에 무엇을 어떻게 바꾸는지 적는다.

/nexi-backlog change
고객 목록 검색이 회사명의 대소문자를 구분한다. 구분하지 않게 고친다.

AI가 바뀌는 종류(요구사항, 디자인, 구현만)와 영향받는 끝난 작업을 표로 보이고, 맞다고 답하면 변경 이슈를 만든다. 요구사항 결정이 바뀌는 변경이면 AI가 멈춘다. 2-3과 2-4로 결정을 고쳐 승인한 뒤 같은 change를 다시 넣는다.

새 기능이면 요구사항부터 넣는다.

/nexi-requirements decide
새 요구: 고객 목록을 CSV로 내려받는다.

2-4처럼 승인한 뒤 /nexi-backlog를 넣는다. 이미 있는 작업은 다시 만들지 않고 새 결정의 작업만 만든다.

새로 생긴 작업은 Step 4대로 끝낸다. 모두 수용되면 Step 5를 처음부터 다시 한다.

멈췄을 때

  • 같은 작업에서 REVISE가 세 번 이어졌거나 BLOCK이 나왔다: docs/reviews/T<N>.md의 판정에서 사람이 정할 것과 원인 후보를 읽고 원인을 정한다. 세 번째 REVISE나 예전 형식의 BLOCK에는 원인 후보가 없으므로 원인을 모두 따져 본다. 계약서가 원인이면 /nexi-implement <N> 다음 줄에 결정: 계약서를 넣는다. AI가 고친 계약서 초안을 쓰고, 4-2처럼 승인한 뒤 4-3부터 이어 간다. 다른 원인은 작업 순환의 표대로 한다. 작업이 너무 크면 나눈다. 둘째 줄에 어떻게 나눌지 쓴다.
/nexi-backlog split <N>

AI가 지금까지 바꾼 것을 저장소 밖에 참고용으로 저장하고, 작은 이슈들을 만들어 순서(선행 작업)를 적는다. 어떤 순서로 할지 분명하지 않으면 묻는다. #<N>이 끝나야 시작할 수 있던 다른 이슈에는 새로 나눈 작업의 번호를 선행 작업으로 적는다. 그리고 옆 폴더에 저장소를 새로 받고 #<N>을 닫는다. 중간에 끊기면 같은 프롬프트를 다시 넣는다. 이미 만든 이슈는 다시 만들지 않는다.

  • 사용량 한도나 퇴근으로 멈춰야 한다: Claude Code와 Codex를 그냥 닫는다. 돌아와서 같은 폴더에서 다시 열고, 하던 단계의 프롬프트를 그대로 다시 넣는다. AI가 쓰다 만 초안과 이미 기록한 결과를 알아보고 이어 간다. 끝난 단계는 다시 하지 않는다. AI의 답이 끝났더라도 /nexi-implement의 보고에 마지막으로 고친 뒤 모든 검사가 통과한 결과(green)가 없으면 구현은 끝나지 않았다. /nexi-implement <N>을 다시 넣는다. Codex 리뷰가 중간에 끊겼으면 Codex를 다시 열어 4-4를 처음부터 한다.
  • push가 실패했다: 이슈가 열린 채로 남는다. 원인을 해결한 뒤 /nexi-merge <N>만 다시 넣는다. skill이 이미 만든 commit이 리뷰한 내용 그대로인지 확인한 뒤 그 commit만 push하고 이슈를 닫는다. 같은 변경을 다시 commit하지 않는다. 그 commit 말고 push하지 않은 commit이 더 있으면 AI가 아무것도 push하지 않고 목록을 보여 준다. 무엇인지 확인하고 어떻게 할지 정한다.

부록: 요구사항 원문

Step 1의 프롬프트에 아래 한국어 글과 영어 글 가운데 하나를 그대로 붙여 넣는다. 두 글은 같은 요구사항이고 언어만 다르다. 한국어 글에서도 역할(admin, manager, rep), 단계와 상태 값, 기술 이름은 영어로 둔다.

한국어

다음 모듈을 갖춘 풀스택 CRM(고객 관계 관리) 시스템을 구현한다.

1. 고객 관리 - 회사 정보, 연락처, 커뮤니케이션 이력, 세분화/태그를 갖춘 고객 CRUD
2. 영업 기회/거래 파이프라인 - 영업 파이프라인 단계(lead, qualified, proposal, negotiation, closed-won/lost), 거래 금액, 성사 확률, 예상 마감일
3. 영업 활동 추적 - 영업 활동(전화, 이메일, 미팅) 기록, 고객/영업 기회와 연결, 활동 로그와 이력
4. 매출 예측 - 기간별(월/분기) 매출 예측, 거래 확률로 가중한 파이프라인, 실적 대비 예측 비교, 대시보드 차트
5. 작업 배정 - 영업 사원에게 작업 생성/배정, 마감일, 우선순위, 상태 추적(todo/in-progress/done), 작업 알림
6. 영업 사원 관리 - 사원 프로필, 역할(admin/manager/rep), 팀 계층, 성과 지표, 할당량(quota) 추적

기술 스택: 프런트엔드는 Next.js 15 (App Router) + TypeScript + Tailwind CSS + shadcn/ui로, 깔끔하고 현대적인 UI로 만든다. 데이터베이스는 Drizzle ORM으로 SQLite를 쓴다. 데모용 seed 데이터를 넣는다. 첫 화면은 KPI 카드, 파이프라인 차트, 최근 활동, 다가오는 작업을 보여 주는 반응형 대시보드다.

English

Implement a full-stack CRM (Customer Relationship Management) system with the following modules:

1. Customer Management - CRUD for customers with company info, contacts, communication history, segmentation/tags
2. Opportunity/Deal Pipeline - Sales pipeline stages (lead, qualified, proposal, negotiation, closed-won/lost), deal values, probability, expected close dates
3. Sales Tracking - Track sales activities (calls, emails, meetings), link to customers/opportunities, activity logs and history
4. Revenue Forecast - Forecast revenue by period (monthly/quarterly), weighted pipeline based on deal probability, actual vs forecast comparison, dashboard charts
5. Task Assignment - Create/assign tasks to sales staff, due dates, priorities, status tracking (todo/in-progress/done), task notifications
6. Sales Staff Management - Staff profiles, roles (admin/manager/rep), team hierarchy, performance metrics, quota tracking

Tech stack: Next.js 15 (App Router) + TypeScript + Tailwind CSS + shadcn/ui for frontend, with a clean modern UI. Use SQLite via Drizzle ORM for the database. Include seed data for demo purposes. The app should have a responsive dashboard landing page with KPI cards, pipeline chart, recent activities, and upcoming tasks.
