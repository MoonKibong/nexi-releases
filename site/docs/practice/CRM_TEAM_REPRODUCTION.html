다섯 명이 CRM 만들어 보기

읽기 안내 — 누가: 역할 다섯을 나눠 CRM을 처음부터 만들어 볼 팀 · 언제: 저장소가 아직 없고 요구사항 문서 하나만 있을 때 · 읽은 뒤: 각자 자기 차례에 프롬프트를 넣고 결과를 확인해, 일을 다음 사람에게 넘긴다.

다섯 사람이 각자 자기 컴퓨터의 Claude Code 또는 cucu로 일하고, GitHub 저장소 하나로 일을 주고받는다. 사람은 프롬프트를 쓰고 결과를 읽고 결정한다. 프롬프트는 대부분 NEXI 키트의 skill 이름으로 시작한다. 팀으로 시작한 저장소에서는 skill이 작업마다 branch를 만들고, 단계가 끝나면 commit, push, 이슈 댓글까지 한다. 사람이 터미널에 직접 치는 것은 폴더를 만들고 들어가는 명령(mkdir, cd), claude 또는 cucu를 여는 명령, 팀원이 저장소를 처음 받을 때의 git clone뿐이다. 그 밖의 git, GitHub, 빌드, 테스트 명령은 모두 AI가 실행한다.

각자의 컴퓨터는 다른 사람의 로컬 파일을 보지 못한다. 넘겨받는 사람은 push된 branch와 이슈 댓글만 보고 일한다. 각 단계의 skill을 실행하면 AI가 GitHub의 최신 commit을 가져오고 해시를 보여 준다. 넘겨받는 사람은 그 해시가 앞사람이 알려 준 것과 같은지 보고 내용을 읽는다.

준비물(모두). 로그인한 Claude Code와 Codex, GitHub 계정, Chrome. GitHub CLI는 Step 1에서 AI가 확인하고 설치나 로그인을 돕는다. Node.js와 패키지 관리자는 REQ-CONTEXT에서 스택을 정한 뒤, Step 4 골격 작업의 계약서(4-1)가 버전을 정하고, 구현(4-3)에서 개발자의 AI가 그 버전을 설치한다.

역할 하는 일
PM 저장소 만들기, 질문의 답, 요구사항·계약서·디자인 기준 승인, 작업 목록, 병합, 끝내기

Step 0. 키트를 설치한다

다섯 사람 모두 각자의 컴퓨터에서 한다. 키트 설치·배포 안내에서 배포 상태를 확인한다. 공개 다운로드가 준비되지 않았으면 키트를 받은 뒤 진행한다. 사용할 agent(Claude Code 또는 cucu)를 열고 다음과 같이 요청한다.

Claude Code를 쓰면 이렇게 넣는다.

~/Downloads/nexi-kit.zip 안의 INSTALL.txt를 읽고 그대로 설치해라.

cucu를 쓰면 이렇게 넣는다.

~/Downloads/nexi-kit.zip을 ~/.cucu/skills/ 경로에 압축 해제하고, 앞으로 !nexi- 로 시작하는 명령어를 입력하면 이 경로의 파일을 읽고 지침에 따라 수행하도록 설정해라.

CuCu에서는 이 문서의 /nexi-… 프롬프트를 !nexi-…로 바꿔 넣는다. 지금 키트는 CuCu를 agent로 받지 않아 skill이 첫 환경 확인에서 멈춘다. 지원은 준비 중이다(P#275). CuCu TUI는 /로 시작하는 입력을 자기 명령으로 받는다. CuCu를 써도 리뷰하는 Codex에는 키트가 필요하다. 그래서 먼저 Claude Code나 Codex에 위의 INSTALL.txt 프롬프트를 넣어 스무 칸을 "같음"으로 맞추고, 그다음 CuCu 프롬프트로 ~/.cucu/skills에 푼다. CuCu 위치는 아직 비교 표에 없으므로(P#275) 그곳에는 skill 폴더 열 개가 있는지만 본다.

설치 절차는 zip의 INSTALL.txt에 있다. AI가 zip의 SHA-256과, skill마다 두 설치 위치(~/.claude/skills, ~/.codex/skills)의 비교 표를 보여 준다.

  • "다름"이 있으면 예전에 설치한 같은 이름의 skill이다. 팀 전체가 같은 zip의 파일로 일해야 한다. AI가 예전 것을 백업하고 바꿀지 물으면 "바꿔라"라고 답한다.
  • "없음"이 남으면 AI가 보여 준 빠진 파일과 오류를 AI·하네스 운영자와 보고 원인을 해결한 뒤 같은 프롬프트를 다시 넣는다.

누군가 예전 skill을 계속 쓰려고 하면 그 사람 혼자 예외로 두지 않는다. 팀이 다른 키트를 쓰게 되므로 Step 1을 시작하지 않고 AI·하네스 운영자에게 알린다. AI·하네스 운영자는 팀 전체가 쓸 zip 하나를 정해 메신저에 SHA-256과 함께 올리고, 다섯 사람 모두 그 zip으로 이 Step을 다시 한다.

설치나 교체가 끝나면 Claude Code와 Codex를 닫았다가 다시 연다. 각자 zip의 SHA-256, 키트 버전(nexi-init/KIT_VERSION), 비교 표를 메신저에 올린다.

확인

AI·하네스 운영자가 메신저에 올라온 것을 본다. 다섯 사람의 SHA-256과 키트 버전이 모두 같고, 다섯 사람의 표에서 스무 칸이 모두 "같음"이어야 한다. SHA-256이 다른 사람이 있거나 "같음"이 아닌 칸이 하나라도 있으면 Step 1을 시작하지 않는다. 키트를 새로 받으면 다섯 사람 모두 이 Step을 다시 한다.

Step 1. 프로젝트를 시작한다

PM. 폴더를 만들고 Claude Code를 연다.

mkdir crm
cd crm
claude

/nexi-init crm team
요구사항 원문:
<부록의 글을 붙여 넣는다>

요구사항 원문 자리에는 부록의 요구사항 가운데 하나를 그대로 붙여 넣는다. AI가 GitHub 로그인을 요청하면 브라우저에서 마친다. 설치할 도구가 있다고 하면 "설치해라"라고 답한다. AI가 팀원의 GitHub 아이디를 물으면 넷의 아이디를 알려 준다.

확인

AI가 알려 준 GitHub 저장소 주소가 열리는지, AGENTS.md에 작업 규칙 여섯 개와 팀 규칙, PM의 GitHub 아이디(PM: 줄)가 있는지 본다. PM만 할 수 있는 승인, 작업 목록, 병합, 끝내기는 skill이 이 줄과 실행한 사람의 GitHub 아이디를 비교해 막는다. 이 확인은 skill 안에서만 한다. 다른 사람이 main에 바로 push하는 것은 막지 못한다. GitHub 요금제가 허용하면 PM이 저장소 설정에서 main을 보호해 PR로만 바뀌게 하고, 어떤 설정을 썼는지 적는다. 설정은 PR 필수, 필요한 승인 수 0(키트는 GitHub 리뷰 승인을 남기지 않는다), squash 병합 허용, force push와 삭제 금지다. 승인 수를 1 이상으로 두면 모든 병합이 실패한다. 보호하지 못하면 그 사실을 적는다. 끝내기는 main의 commit이 모두 키트가 만든 것인지 확인하고, 아닌 commit이 있으면 멈춘다.

나머지 넷. GitHub에서 초대를 수락한 뒤 터미널에서 저장소를 받고, 받은 폴더에서 Claude Code를 연다.

mkdir work
cd work
git clone https://github.com/<PM 아이디>/crm.git
cd crm
claude

비공개 저장소라서 git clone이 로그인 문제로 실패할 수 있다. 그러면 work 폴더에서 claude를 열어 "GitHub CLI를 설치하고 로그인해 git도 이 로그인을 쓰게 해라"라고 요청한다. 브라우저에서 로그인을 마치고, AI가 git 설정까지 끝났다고 알리면 Claude Code를 닫고 git clone부터 다시 한다. 이후 프롬프트는 모두 이 crm 폴더에서 넣는다.

Step 2. 요구사항을 확정한다

FDE와 PM이 번갈아 네 번 넣는다. 아직 이슈가 없으므로 자기 차례가 끝나면 다음 사람에게 메신저로 알린다. FDE가 둘이면 PM이 한 사람(보통 골격 작업을 맡을 FDE)을 정해 이 Step의 FDE 차례를 모두 맡긴다.

순서 누가 넣는 프롬프트 끝나면 알릴 사람
2-1 FDE /nexi-requirements analyze PM
2-2 PM /nexi-requirements answers FDE
2-3 FDE /nexi-requirements decide PM(req branch의 commit 해시를 함께)
2-4 PM /nexi-requirements approve 모두(고칠 것이 있으면 FDE에게, 2-3으로)

2-1. 요구사항 분석 (FDE)

/nexi-requirements analyze
확인

docs/requirements/REQ-ANALYSIS.md에 붙여 넣은 요구사항의 모듈, 대시보드, seed 데이터, 기술 스택, "깔끔하고 현대적인 UI"(clean modern UI) 같은 화면 요구가 모두 있는지 본다. 빠진 것은 AI에게 말한다.

끝나면 PM에게 알린다.

2-2. 질문에 답하기 (PM)

/nexi-requirements answers

실제 고객이면 QUESTIONS.md를 보내고, 받은 답을 프롬프트 다음 줄에 붙여 넣는다. 연습이면 AI의 제안을 고친 뒤 "이대로 저장해라"라고 한다.

확인

docs/requirements/CLIENT_ANSWERS.md에 질문마다 답과 근거가 있는지, AI가 보여 준 "아직 답이 없는 질문" 목록이 비었는지 본다. 남은 질문은 고객에게 다시 묻거나 PM이 정해 답한다.

끝나면 FDE에게 알린다.

2-3. 결정 문서 (FDE)

/nexi-requirements decide
확인

docs/requirements/REQ-CONTEXT.md를 읽고 본다.

  • 원문과 어긋나는 결정이 없는가
  • 품질 요구마다 어느 수준인지, 무엇으로 확인하는지 적혀 있는가
  • 기술 스택에 런타임과 패키지 관리자가 정해져 있는가
  • 구성 요소마다 이 프로젝트가 만드는지, 이미 있는 외부 시스템인지 적혀 있는가

끝나면 AI가 알려 준 req branch의 commit 해시를 PM에게 알린다.

2-4. 요구사항 승인 (PM)

/nexi-requirements approve

AI가 req branch를 원격의 최신 commit으로 바꾸고 그 해시를 보여 준 뒤, 받아들이지 않는 수행사 결정을 묻는다. 해시가 FDE가 알린 것과 같은지 보고 docs/requirements/REQ-CONTEXT.md를 읽는다. 이 문서가 뒤의 모든 작업의 근거다. 모듈, 화면, 품질 요구가 빠짐없이 결정으로 들어갔는지, 원문과 어긋나는 결정이 없는지 본다. 고칠 것이 있으면 승인하지 않고 FDE에게 알려 2-3을 다시 하게 한다. 다 맞으면 끝의 "수행사가 고객 없이 정한 결정" 목록을 보고 답한다.

받아들이지 않는 수행사 결정: <번호, 없으면 "없음">

AI가 받아들이지 않은 결정과 아직 정하지 않은 결정마다 구현이나 검사를 막는지 표로 보여 준다.

  • 막는 결정이 있으면 AI는 아무것도 바꾸지 않고 멈춘다. 결정마다 고를 수 있는 것(결정을 고친다, 그 범위를 뺀다, 다른 결정과 맞춘다)을 보고 하나를 정해 FDE에게 알린다. FDE가 2-3을 다시 하고, PM이 2-4를 다시 한다.
  • 막는 결정이 없으면 AI가 본문에서 뺄 줄, 결정마다의 승인 상태, 고객 확인이 남은 결정 목록을 보여 주고 승인할지 묻는다. 읽고 맞으면 "승인한다"라고 답한다. 그사이 원격의 req가 바뀌었으면 AI가 승인하지 않고 diff를 보여 준다. 바뀐 곳을 읽고 2-4를 다시 한다.
확인

승인되면 맨 위 줄이 상태: 승인인지, 받아들이지 않은 결정의 규칙이 본문에 남지 않았는지, 고객 확인이 남은 결정 목록이 있는지 본다. 병합한 뒤에는 main에 들어간 내용이 승인한 req의 commit과 같은지 본다.

승인을 기록하거나 push, 병합하다 끊겼으면 PM이 같은 프롬프트를 다시 넣는다. skill이 이미 만든 commit과 PR을 확인해 이어 간다. 끝나면 모두에게 알린다.

Step 3. 작업 목록을 만든다

PM이 넣는다.

/nexi-backlog

AI가 묻는 대로 작업마다 담당 FDE를 정한다(FDE가 한 명이어도 정한다). 나중에 나누거나 바꾸면서 생긴 작업도 PM이 담당을 정한다.

팀을 나눠 일하면 여기서 나눈다. 백엔드와 프런트엔드처럼 계층으로 나누든, 고객 관리와 작업 배정처럼 모듈로 나누든 같다. 팀은 요구사항까지 하나로 일하고, 이 백로그에서 작업마다 담당과 선행 작업을 정해 나뉜다. /nexi-backlog 다음 줄에 팀 구성에 맞는 글을 붙인다. 계층 팀이면:

백엔드 팀(FDE: <아이디>)과 프런트엔드 팀(FDE: <아이디>, <아이디>)으로 나눠 일한다. API와 화면을 모두 새로 만드는 기능은 API
작업과 화면 작업으로 나누고, 화면 작업의 선행 작업에 그 API 작업을 적어라. 이미 있는 API를 쓰는 화면은 나누지 않는다. 작업마다
담당은 한 사람이다. 골격과 코드 표준은 백엔드 팀, 디자인 시스템은 프런트엔드 팀이 맡는다.

모듈 팀이면:

<모듈 이름> 팀(FDE: <아이디>), <모듈 이름> 팀(FDE: <아이디>)으로 모듈마다 나눠 일한다. 기능은 API와 화면을 나누지 않고 그 모듈
팀의 작업 하나로 만든다. 다른 모듈의 API나 데이터를 쓰는 작업은 그것을 만드는 작업을 선행 작업에 적어라. 골격, 코드 표준, 디자인 시스템, 그리고 승인된 요구사항에 있으면 로그인과 권한, 여러 모듈이 쓰는 데이터 모델을 이 순서로 공통 기반 작업으로 먼저 두고, 담당은 <아이디>다. 각 작업은 실제로 쓰는 공통 기반 작업만 선행 작업에 적어라. 작업마다 담당은 한 사람이다.
확인

이슈 표가 골격 → 코드 표준 → 디자인 시스템 → 기능 순서인지, 이슈마다 적힌 선행 작업이 맞는지, 하루를 넘을 것 같은 이슈가 없는지 본다. 크면 쪼개 달라고 한다. 담당이 두 사람이거나 모두가 맡는 작업, 끝에 몰아서 하는 테스트 작업이 없는지 본다. 다른 팀의 것을 쓰는 작업마다 선행 작업에 그것을 만드는 작업이 있는지, 공통 기반 작업이 백로그의 앞에 있고 기능 작업이 실제로 쓰는 것만 선행 작업으로 기다리는지 본다.

끝나면 모두에게 알린다. 그다음 Step 4는 팀마다 자기 작업으로 동시에 돈다. 리뷰와 병합은 모든 팀의 작업을 같은 검토자와 PM이 한다.

Step 4. 작업 하나를 끝낸다 (작업마다 반복)

자기 작업의 선행 작업이 병합된 뒤에 시작한다. 두 FDE는 서로 다른 작업을 동시에 할 수 있다. FDE가 4-1을 시작하기 전에 넣는다. AI가 선행 작업이 모두 원격 main에 수용된 열린 이슈 가운데, 자기에게 배정된 작업, 그다음 담당이 없는 작업에서 번호가 가장 작은 것을 고른다. 담당이 없는 작업은 이미 작업을 맡은 적이 있는 FDE만 가져가고, 그 밖의 사람이 넣으면 PM에게 넘긴다. 고를 작업이 없으면 무엇을 기다리는지 알려 준다. 선행 작업이 병합되면 skill이 기다리던 이슈에 "선행 작업 수용" 댓글을 단다.

/nexi-backlog next

<N>은 고른 이슈 번호다.

4-1. 계약서 (FDE)

/nexi-contract <N>

AI가 branch t<N>을 원격의 최신 main에 맞춘 뒤 계약서를 쓰고, REQ-CONTEXT, 끝난 작업의 계약서, seed 데이터, 역할별 권한, 디자인 기준과 맞는지 스스로 점검한 표를 함께 보여 준다. 첫 작업(골격)이면 계약서에 실행 환경 버전과 테스트 준비 순서가 들어간다.

골격 작업에서 REQ-CONTEXT에 런타임이나 패키지 관리자가 없다고 AI가 멈추면 PM에게 알린다. FDE가 Step 2의 2-3(decide)에 그 결정을 적어 넣고, PM이 2-4(approve)로 승인한 뒤, FDE가 /nexi-contract <N>을 다시 넣는다. 이때 skill이 승인된 REQ-CONTEXT를 t<N>에 merge하고 계약서를 "상태: 초안"부터 새로 쓴다. 옛 계약서나 그 승인은 이어지지 않는다.

계약서를 쓰기 전에 AI가 해당할 수 있는 구현 패턴을 이유와 함께 보이고, 앞서 수용된 작업이 같은 판으로 적용하지 않은 패턴마다 적용, 해당 없음, 예외를 묻는다 (작업 순환). 고객 목록 같은 목록 작업이면 권한 부여와 데이터 격리, 페이지네이션과 조회, 입력 검증과 오류 응답, 테스트 데이터 격리가 나오는지 본다. 초간단 요구사항처럼 로그인과 역할이 없으면 인증과 권한 패턴이 해당 없음인지 본다. 패턴이 요구하는 값이 REQ-CONTEXT에 없다고 AI가 멈추면 PM에게 알린다. FDE가 2-3(decide)에 그 값을 적고 PM이 2-4(approve)로 승인한 뒤 FDE가 /nexi-contract <N>을 다시 넣는다.

docs/contracts/T<N>.md와 점검 표를 읽는다. 산출물이 하나인지, 수용 기준마다 확인 방법이 있는지, 새 검사가 그 기준을 실제로 검사하는지, 화면 작업이면 찍을 화면이 적혀 있는지 본다. 점검 표에 "질문"이 있으면 정하거나 PM에게 묻고, 고칠 것은 AI에게 말한다. 다 읽고 맞으면 AI에게 "PM에게 넘겨라"라고 답한다. 그때 AI가 commit, push하고 이슈에 차례 댓글을 단다. 그 전에는 PM 차례가 아니다.

디자인 시스템 작업(세 번째 작업)이면 이어서 디자인 기준을 쓰게 한다. 원하는 분위기가 있으면 같이 적는다.

/nexi-design <N>

docs/design/BRIEF.md의 분위기, 색, 글꼴, 간격, 구성 요소가 원하는 모습인지, (제안) 표시가 붙은 값이 괜찮은지 본다. 고칠 것은 AI에게 말한다. 끝나면 AI가 알려 준 branch t<N>의 commit 해시를 PM에게 알린다. 디자인 시스템 작업은 계약서만 쓴 상태에서 PM 차례가 되지 않는다. 계약서 댓글이 "FDE 디자인 기준 차례"이면 /nexi-design <N>까지 끝내야 PM이 승인할 수 있다.

4-2. 승인 (PM)

/nexi-contract <N> approve

AI가 branch t<N>을 원격의 최신 commit으로 바꾸고 그 전체 해시와 계약서, BRIEF를 보여 준 뒤 승인할지 묻는다. 해시가 FDE가 알린 것과 같은지 보고 4-1과 같은 기준으로 읽는다.

  • 고칠 것이 있으면 고칠 내용을 답한다. AI가 이슈에 계약서 수정 요청 댓글을 단다. FDE가 4-1을 다시 하면 skill이 이 댓글을 읽고 고친다.
  • 맞으면 "승인한다"라고 답한다. 디자인 시스템 작업이면 "docs/design/BRIEF.md도 승인한다."를 함께 답한다. 이 말이 없으면 BRIEF는 초안으로 남는다. 계약서만 먼저 승인했으면, FDE가 BRIEF 초안을 올린 뒤 같은 프롬프트로 BRIEF만 승인한다.

그사이 원격의 t<N>이 바뀌었거나 REQ-CONTEXT가 다시 승인됐으면 AI가 승인하지 않고 알려 준다. 바뀐 곳을 읽고 4-2를 다시 하거나, FDE에게 4-1을 다시 하게 한다.

확인

AI가 보여 준 계약서와 BRIEF의 첫 줄, push한 commit 해시를 보고, 디자인 시스템 작업이면 둘 다 상태: 승인인지 본다. 하나라도 상태: 초안이면 개발자의 /nexi-implement가 멈춘다.

4-3. 구현 (개발자)

/nexi-implement <N>

보고에 수용 기준마다의 증거, 새 검사마다 Red의 실패 이유, 마지막 수정 뒤의 Green 결과, 실제로 쓴 Node.js와 패키지 관리자 버전(README의 버전), 다시 찍은 PNG 목록이 있는지 본다. 이미 있던 동작을 확인하는 검사는 Red 대신 회귀 검사로 표시되고, 바꾸기 전의 통과 결과와 근거가 함께 적힌다. 검사 개수만 보지 말고, 각 검사가 수용 기준의 어떤 동작을 확인하는지 읽는다. 화면 작업이면 PNG를 열어 직접 본다. skill이 commit, push하고 PR을 만든 뒤 이슈에 "리뷰 차례"라고 남긴다. 이슈는 PR이 병합될 때 닫히지 않고, 4-6의 확인이 끝난 뒤에 닫힌다.

계약서를 승인한 뒤 REQ-CONTEXT가 다시 승인됐으면 skill이 구현하지 않고 멈춘다. FDE에게 알린다. FDE가 4-1을 다시 하고 PM이 4-2로 승인한 뒤 구현을 이어 간다.

4-4. 리뷰 (검토자)

먼저 Claude Code에 넣는다. AI가 다른 변경이 섞이지 않은 폴더를 t<N>의 원격 최신 commit에 맞추고, Codex를 열 폴더와 Codex에 넣을 줄을 알려 준다. 작업 트리가 깨끗하지 않으면 그 변경을 건드리지 않고 crm-review 같은 옆 폴더에 저장소를 새로 받아 준비한다.

/nexi-review <N> prepare

터미널을 하나 더 열어 AI가 알려 준 폴더(예: work/crm, 옆 폴더에 준비했으면 work/crm-review)로 가서 Codex를 모델 gpt-6-astra, 읽기 전용으로 연다.

cd work/crm
codex --model gpt-6-astra --sandbox read-only

Codex에서 /status로 모델이 gpt-6-astra인지 본다. 이 모델을 쓸 수 없다고 나오면 다른 모델로 리뷰하지 않고 멈춰 PM에게 알린다. 창이나 세션의 이름은 모델을 정하지 않는다. Claude Code가 "Astra"라는 이름을 붙여 돌린 검토도 이 리뷰가 아니다. Codex에는 AI가 알려 준 줄을 그대로 넣는다.

nexi-review skill로 T#<N>을 리뷰해라. 리뷰할 commit은 <prepare가 보여 준 해시>다.

Codex가 쓰기 권한을 달라고 하면 거절한다. 리뷰하는 폴더에서 파일을 바꾸지 않는다. 리뷰 중에 파일이나 commit이 바뀌면 Codex가 판정을 내지 않는다. 판정의 기준별 판단에 수용 기준마다 판단이 있는지 본다. 화면 작업이면 PNG별 대조에 PNG마다 줄이 있는지도 본다. 빠졌으면 Codex에 "근거가 빠졌다. 처음부터 다시 리뷰해라"라고 한다. 그다음 Codex의 답을 복사해, prepare가 준비한 그 폴더에서 연 Claude Code에 넣는다. 옆 폴더에 준비했으면 그 폴더에서 claude를 새로 연다.

/nexi-review <N> record
<Codex의 답을 붙여 넣는다>

AI는 판정의 형식과 GitHub의 t<N>을 확인한다. t<N>이 리뷰한 commit 그대로이거나 그 뒤에 판정 기록만 더해졌으면, 판정을 그대로 기록하고 PR에 댓글을 단 뒤 다음 차례를 알려 준다. 기록이나 댓글 중에 끊겼으면 같은 프롬프트를 다시 넣는다. 이미 한 기록과 댓글은 다시 하지 않는다.

  • APPROVE → PM (4-6)
  • REVISE → 개발자 (4-5)
  • REVISE가 세 번 이어졌거나 BLOCK → PM과 AI·하네스 운영자 (멈췄을 때)

4-5. 리뷰 지적 반영 (개발자)

/nexi-implement <N>

skill이 마지막 판정을 읽고 고친 뒤 다시 push하고 "리뷰 차례"를 남긴다. 검토자는 4-4를 다시 한다. 리뷰 skill은 지난 판정의 지적과 그 뒤에 바뀐 곳을 모두 다시 보고, PNG도 다시 연다. APPROVE가 나올 때까지 되풀이한다.

지적을 고치는 데 수용 기준이나 디자인 기준을 바꿔야 하면, skill이 고치지 않고 멈춰 이슈에 그 사정을 댓글로 남긴다. FDE에게 넘긴다. FDE가 4-1을 다시 하면 계약서나 디자인 기준은 초안으로 돌아간다. PM이 4-2로 다시 승인한 뒤 구현을 이어 가고, 리뷰도 다시 받는다.

4-6. 병합 (PM)

/nexi-merge <N>

skill은 다음 셋이 모두 맞을 때만 병합한다.

  • 마지막 판정이 형식을 갖춘 APPROVE다.
  • 리뷰 뒤에 바뀐 것은 판정 기록(docs/reviews/T<N>.md)뿐이다. 코드, 계약서, 증거, 스크린샷이 바뀌었거나 리뷰 뒤에 merge commit이 생겼으면 다시 리뷰받는다.
  • 리뷰 뒤에 main이 앞서 나가지 않았다.

병합한 뒤 AI는 squash commit이 리뷰할 때의 기준 commit(base) 바로 위에 들어갔는지, 파일 내용이 병합 직전 PR의 마지막 commit(리뷰한 commit에 판정 기록만 더한 것)과 같은지 확인한다. 둘 다 맞아야 이슈를 닫는다.

하나라도 아니면 멈추고 누구 차례인지 알려 준다. 예를 들어 그사이 다른 작업이 병합됐으면, 개발자가 /nexi-implement <N>을 다시 해서 main을 merge하고 검사와 스크린샷을 다시 만든다. rebase나 force push는 하지 않는다. 그다음 검토자가 다시 리뷰한다.

확인

AI가 보여 준 PR이 MERGED인지, merge commit의 전체 해시가 origin/main에 있는지, 이슈 #<N>이 닫혔는지 본다. 병합되면 모두에게 알리고, FDE가 /nexi-backlog next로 다음 작업을 고른다.

병합이 중간에 끊겼으면 /nexi-merge <N>을 다시 넣는다. skill이 먼저 PR이 이미 병합됐는지 본다. 병합됐으면 다시 병합하지 않고, 위의 확인을 한 뒤 남은 일(이슈 닫기, 기록)만 한다. 확인에 실패하면(예: 병합 직전에 다른 작업이 main에 들어가 squash가 리뷰한 base 위에 들어가지 않았다) 이슈를 닫지 않고 멈춘다. 이미 main에 들어간 변경을 어떻게 할지 PM이 AI·하네스 운영자와 멈췄을 때처럼 정한다.

Step 5. 끝낸다

PM이 넣고, FDE는 PM과 함께 결과를 본다.

/nexi-finish

AI가 원격 main을 새로 clone한 폴더에서 README 순서대로 설치, DB 준비와 seed, build, test, lint를 돌리고 README의 실행 명령으로 앱이 뜨는지 본 결과 표와, 앱을 띄울 PM의 crm 폴더의 결과 표를 따로 보여 준다. 그리고 이 컴퓨터에서만 열리는 주소, 역할마다 로그인할 seed 계정, 써 볼 목록을 알려 준다.

PM의 폴더에서 준비 단계(설치, DB 준비와 seed, build) 가운데 하나라도 실패하면 AI는 앱을 띄우지 않는다. 실패한 단계, 그 때문에 돌리지 않은 단계, 돌린 데까지의 결과를 적은 docs/FINAL.md 초안을 남기고 멈춘다. 이때는 써 보지 않고 아래의 /nexi-finish reject로 실패를 작업으로 돌려보낸다.

README의 포트를 이미 다른 프로그램이 쓰고 있으면 AI는 앱을 띄우지 않고 그 프로그램도 멈추지 않는다. 어느 프로그램인지 적은 초안을 남긴다. 그 프로그램을 끝낼지는 사람이 정하고, 끝낸 뒤 /nexi-finish를 다시 넣는다.

앱이 떴으면 PM이 그 주소로 앱을 써 보고, FDE는 PM의 화면 공유로 같이 본다. 앱과 docs/FINAL.md는 PM의 컴퓨터에만 있다. 이 앱은 clone 폴더가 아니라 PM의 crm 폴더에서 seed 데이터로 띄운 것이다. 다음을 본다.

  • 대시보드와 고객·거래·활동·작업·예측·직원 화면이 원문대로 동작한다.
  • 화면마다 seed 데이터가 보인다.
  • admin, manager, rep으로 각각 로그인하면 볼 수 있는 데이터와 할 수 있는 일이 결정대로 다르다.
  • 휴대폰 너비와 데스크톱 너비에서 화면이 디자인 기준과 맞는다.

본 결과를 docs/FINAL.md의 둘러보기 목록에 줄마다 확인함, 이상 있음: <무엇>, 확인 안 함 가운데 하나로 적는다. 파일을 직접 고치거나 AI에게 줄마다 말한다. 빈 줄이 남아 있으면 /nexi-finish approve가 멈춘다.

clone 폴더의 검사가 실패했거나 써 보다 고칠 것이 있으면 승인하지 않고 결함을 작업으로 돌려보낸다. PM이 넣는다.

/nexi-finish reject <결함 내용>

AI가 결함마다 task 이슈를 만들고, 앱을 멈추고, commit하지 않은 docs/FINAL.md 초안을 ~/nexi-final/ 아래에 저장한 뒤 지운다. 초안에 적힌 실패 가운데 결함 내용에 없는 것이 있으면 AI가 결함으로 더할지 묻는다. 중간에 끊겨 같은 프롬프트를 다시 넣어도 이미 만든 이슈는 다시 만들지 않는다. 초안이 없거나 앱을 띄우지 않았으면 그 단계는 건너뛴다고 알려 준다. 다른 변경이 있어 AI가 멈췄으면 PM은 그 폴더를 그대로 두고, /nexi-init clone으로 옆 폴더에 저장소를 새로 받아 그 폴더에서 PM의 차례를 이어 간다. 결함 작업은 Step 4로 처리한다. 결함 작업이 병합되면 PM이 최신 main에서 /nexi-finish를 다시 한다. 저장해 둔 초안은 비교용이며 승인하지 않는다.

PM이 docs/FINAL.md의 내용을 메신저로 보내고, PM과 FDE가 읽는다. 결과 표가 실제로 돌린 명령의 결과와 같은지, 실패했거나 돌리지 않은 검사, 아직 고객 확인이 필요한 결정, 써 보며 만든 이슈가 빠짐없이 적혀 있는지 본다. 맞으면 PM이 /nexi-finish approve를 넣는다.

승인을 push하거나 병합하다 끊겼으면 PM이 같은 프롬프트를 다시 넣는다. skill이 이미 만든 commit과 PR이 승인한 docs/FINAL.md만 더한 것인지, 시험한 main 위에 있는지 확인한 뒤 이어 간다. docs/FINAL.md를 상태: 승인으로 바꾼 뒤 commit 전에 끊겼으면 AI가 그 파일을 승인하는지 다시 묻는다.

끝낸 뒤 바꾸기

최종 보고를 승인한 뒤에 결함을 찾았거나, 만든 것을 바꾸거나, 새 요구사항이 생기면 reject가 아니라 아래 길로 간다. 어느 길로 갈지는 끝내기와 넘기기의 표에 있다.

결함이나 바꿀 동작이면 PM이 이렇게 넣는다. 둘째 줄에 무엇을 어떻게 바꾸는지 적는다.

/nexi-backlog change
고객 목록 검색이 회사명의 대소문자를 구분한다. 구분하지 않게 고친다.

AI가 바뀌는 종류(요구사항, 디자인, 구현만)와 영향받는 끝난 작업을 표로 보이고, 맞다고 답하면 변경 이슈를 만든다. 요구사항 결정이 바뀌는 변경이면 AI가 멈춘다. FDE가 2-3으로 결정을 고치고 PM이 2-4로 승인한 뒤, PM이 같은 change를 다시 넣는다.

새 기능이면 FDE가 요구사항부터 넣는다.

/nexi-requirements decide
새 요구: 고객 목록을 CSV로 내려받는다.

PM이 2-4처럼 승인한 뒤 /nexi-backlog를 넣고 작업마다 담당 FDE를 정한다. 이미 있는 작업은 다시 만들지 않고 새 결정의 작업만 만든다.

새로 생긴 작업은 Step 4대로 끝낸다. 모두 수용되면 PM이 Step 5를 처음부터 다시 한다.

멈췄을 때

PM과 AI·하네스 운영자가 정한다.

  • 같은 작업에서 REVISE가 세 번 이어졌거나 BLOCK이 나왔다: PM이 판정의 사람이 정할 것과 원인 후보를 읽고(세 번째 REVISE나 예전 형식의 BLOCK이면 원인을 모두 따져 보고) 원인을 정해 이슈에 결정: <원인> — <다음 사람> 차례 댓글을 단다. 원인이 리뷰 독립성이면 댓글 없이 다른 agent가 같은 파일을 다시 리뷰한다. 계약서가 원인이면 댓글은 결정: 계약서 — 개발자 차례이고, 개발자가 4-3의 프롬프트를 다시 넣으면 AI가 작업을 push하고 고친 계약서 초안(담당 FDE가 아니면 FDE 차례 댓글)을 올린다. PM이 4-2처럼 승인한 뒤 4-3부터 이어 간다. 다른 원인은 팀으로 일하기대로 한다. 작업이 너무 크면 PM이 나눈다. 이때 개발자가 commit하지 않은 변경은 그 폴더에 그대로 둔다. 어느 단계에서도 rebase, force push, reset, branch 삭제는 하지 않는다. PM이 이렇게 넣는다. 둘째 줄에 어떻게 나눌지 쓴다.
/nexi-backlog split <N>
<나누는 방법>

AI가 작은 이슈들을 만들어 순서(선행 작업)를 적는다. #<N>이 끝나야 시작할 수 있던 다른 이슈에는 새로 나눈 작업의 번호를 선행 작업으로 적는다. t<N>의 PR은 병합하지 않고 닫은 뒤 #<N>을 닫는다. t<N> branch는 참고용으로 남는다.

개발자는 그 폴더를 그대로 두고 /nexi-init clone으로 옆 폴더에 저장소를 새로 받는다. 이후 개발자는 새 폴더에서 프롬프트를 넣는다. 옛 폴더에 남은 변경 때문에 새 작업의 구현이 멈추지 않게 하기 위해서다. 나눈 작업은 FDE가 /nexi-backlog next로 새 번호를 고른 뒤 4-1부터 main에서 다시 시작한다.

  • BLOCK: 판정을 읽고 계약서를 고칠지, 고객에게 물을지 정한다. 계약서를 고치려면 이슈에 댓글을 달고 FDE가 4-1부터 다시 한다.
  • 일하던 사람이 사용량 한도나 퇴근으로 멈춰야 한다: Claude Code와 Codex를 그냥 닫는다. 돌아오면 같은 폴더에서 다시 열고, 하던 단계의 프롬프트를 그대로 다시 넣는다. AI가 쓰다 만 초안, push하지 못한 commit, 이미 기록한 결과를 알아보고 이어 간다. 다른 사람이 이어받아야 하면 PM과 AI·하네스 운영자가 어떻게 할지 정한다. AI의 답이 끝났더라도 /nexi-implement의 보고에 마지막으로 고친 뒤 모든 검사가 통과한 결과(green)가 없으면 그 단계는 끝나지 않았다.
  • push가 실패했다: 이슈와 PR을 연 채로 둔다. 원인을 해결한 뒤 같은 skill을 다시 넣는다. skill이 이미 만든 commit을 push하고 원격의 해시를 확인한다. 같은 변경을 다시 commit하지 않는다.
  • 정한 것은 이슈 댓글로 남긴다.

부록: 요구사항 원문

Step 1에서 PM이 프롬프트에 아래 넷 가운데 하나를 그대로 붙여 넣는다. 여섯 모듈을 모두 만들면 전체 요구사항을, 하루 안에 팀 흐름을 끝까지 돌려 보려면 초간단 요구사항을 붙인다. 언어는 한국어와 영어 가운데 고른다. 두 글은 같은 요구사항이고 언어만 다르다. 한국어 글에서도 역할(admin, manager, rep), 단계와 상태 값, 기술 이름은 영어로 둔다.

전체 요구사항

한국어

다음 모듈을 갖춘 풀스택 CRM(고객 관계 관리) 시스템을 구현한다.

1. 고객 관리 - 회사 정보, 연락처, 커뮤니케이션 이력, 세분화/태그를 갖춘 고객 CRUD
2. 영업 기회/거래 파이프라인 - 영업 파이프라인 단계(lead, qualified, proposal, negotiation, closed-won/lost), 거래 금액, 성사 확률, 예상 마감일
3. 영업 활동 추적 - 영업 활동(전화, 이메일, 미팅) 기록, 고객/영업 기회와 연결, 활동 로그와 이력
4. 매출 예측 - 기간별(월/분기) 매출 예측, 거래 확률로 가중한 파이프라인, 실적 대비 예측 비교, 대시보드 차트
5. 작업 배정 - 영업 사원에게 작업 생성/배정, 마감일, 우선순위, 상태 추적(todo/in-progress/done), 작업 알림
6. 영업 사원 관리 - 사원 프로필, 역할(admin/manager/rep), 팀 계층, 성과 지표, 할당량(quota) 추적

기술 스택: 프런트엔드는 Next.js 15 (App Router) + TypeScript + Tailwind CSS + shadcn/ui로, 깔끔하고 현대적인 UI로 만든다. 데이터베이스는 Drizzle ORM으로 SQLite를 쓴다. 데모용 seed 데이터를 넣는다. 첫 화면은 KPI 카드, 파이프라인 차트, 최근 활동, 다가오는 작업을 보여 주는 반응형 대시보드다.

English

Implement a full-stack CRM (Customer Relationship Management) system with the following modules:

1. Customer Management - CRUD for customers with company info, contacts, communication history, segmentation/tags
2. Opportunity/Deal Pipeline - Sales pipeline stages (lead, qualified, proposal, negotiation, closed-won/lost), deal values, probability, expected close dates
3. Sales Tracking - Track sales activities (calls, emails, meetings), link to customers/opportunities, activity logs and history
4. Revenue Forecast - Forecast revenue by period (monthly/quarterly), weighted pipeline based on deal probability, actual vs forecast comparison, dashboard charts
5. Task Assignment - Create/assign tasks to sales staff, due dates, priorities, status tracking (todo/in-progress/done), task notifications
6. Sales Staff Management - Staff profiles, roles (admin/manager/rep), team hierarchy, performance metrics, quota tracking

Tech stack: Next.js 15 (App Router) + TypeScript + Tailwind CSS + shadcn/ui for frontend, with a clean modern UI. Use SQLite via Drizzle ORM for the database. Include seed data for demo purposes. The app should have a responsive dashboard landing page with KPI cards, pipeline chart, recent activities, and upcoming tasks.
